## 24.1 The Five Steps: Batch, Forward, Loss, Backward, Step

### 🧭 The Problem First
Ch 20's basic script works, but it mixes concerns (config, data, logging, checkpoints) in one blob. As features pile up (mixed precision, accumulation, distributed training), a messy loop hides bugs.

### 💡 Intuition / Instinct
Every iteration is five steps: **get batch → forward → loss → backward → optimizer step**. Everything else (LR schedule, clipping, accumulation, logging, evaluation, checkpointing) is a *hook* around those five. Structure the code so that the core five stay readable and each hook is a small function.

### 🖼️ Visual Mental Model

```text
 for step in range(start, max_steps):
    lr = schedule(step)                                   ┐ hooks
    for micro in range(accum):                            │
        x,y = next(loader)                  (1) batch      │
        loss = model(x,y) / accum           (2,3)          │
        loss.backward()                     (4)            │
    clip_grad_norm_(...)                                   │
    opt.step(); opt.zero_grad()             (5)            │
    log / eval / checkpoint                               ┘
```

### 📐 The Math, Gently
Tokens per optimizer step = micro_batch × accum × world_size × T. This is **the batch size that matters** for optimization (Ch 26).

### 🛠️ Build It From Scratch

```python
# nanoforge/train.py (part 1: config)
from dataclasses import dataclass, field, asdict

@dataclass
class TrainConfig:

    # model
    model_size: str = "micro"
    vocab_size: int = 4096
    dropout: float = 0.0
    # optimization
    micro_batch: int = 32
    grad_accum: int = 4
    max_steps: int = 5000
    lr: float = 1e-3
    min_lr_ratio: float = 0.1
    warmup_steps: int = 200
    schedule: str = "cosine"          # "cosine" | "wsd"
    decay_frac: float = 0.2           # WSD: fraction of steps spent decaying
    weight_decay: float = 0.1
    beta1: float = 0.9
    beta2: float = 0.95
    grad_clip: float = 1.0
    # system
    dtype: str = "bfloat16"
    compile: bool = False
    seed: int = 1337
    # logging / io
    out_dir: str = "checkpoints/run"

```

### 🔬 Experiment & Observe
Compute the tokens per step for the default: 32 × 4 × 1 × 256 = 32,768 tokens. 5,000 steps = 164M tokens.

### ⚠️ Failure Modes & Debugging
Mixing up "batch size" meanings (per-GPU micro batch vs global batch in sequences vs in tokens) is the #1 source of irreproducible comparisons. **Always report the global batch in tokens.**

### 🧠 Expert Insight
GPT-3 175B used a 3.2M-token global batch; Llama 2 used 4M. Small models do best with much smaller batches (≈ 0.25–0.5M tokens for ~100M-param models; Ch 26).

### 📌 Recap Card

> **Core intuition:** *Keep the heartbeat simple; hang everything else around it.*

## 24.2 LR Schedules: Warmup + Cosine, and WSD

### 🧭 The Problem First
A constant learning rate is too high at the start (random weights, Adam's statistics not yet estimated, so there are loss spikes) and too high at the end (the loss plateaus above what it could reach, as the noisy steps bounce around the minimum).

### 💡 Intuition / Instinct
- **Warmup:** ramp the lr linearly from ~0 to the peak over the first few hundred or thousand steps. It lets Adam's second-moment estimates stabilize and avoids early blowups.
- **Cosine decay:** smoothly lower the lr to ~10% of the peak by the end. As the lr falls, the noise shrinks and the model settles into the valley. The loss often drops noticeably during the decay.
- **WSD (Warmup–Stable–Decay):** warmup, then a long *constant* phase, then a short (10–20%) decay at the end. Advantage: you can decide when to stop, branch off checkpoints from the stable phase and decay them, and continue training later without restarting a cosine schedule.

### 🖼️ Visual Mental Model

```text
 lr  cosine                         WSD
  │   /‾‾‾‾\__                       /‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾\
  │  /       ‾‾\__                  /                 \
  │ /             ‾‾──             /                   \_
  └───────────────────▶ step      └──────────────────────▶ step
```

### 📐 The Math, Gently
Cosine: $\text{lr}(s) = \text{lr}_{min} + \frac12(\text{lr}_{max}-\text{lr}_{min})(1 + \cos(\pi\,p))$, with $p = \frac{s - s_w}{S - s_w}$.
WSD decay (linear, or "1 − sqrt"): $\text{lr}(s) = \text{lr}_{max}\cdot\left(1 - \sqrt{\frac{s - s_d}{S - s_d}}\right)$ during the final decay phase.

### 🛠️ Build It From Scratch

```python
# nanoforge/train.py (part 2: schedules)
import math

def lr_at(step, cfg):
    peak, lo = cfg.lr, cfg.lr * cfg.min_lr_ratio
    if step < cfg.warmup_steps:
        return peak * (step + 1) / cfg.warmup_steps
    if cfg.schedule == "cosine":
        p = min(1.0, (step - cfg.warmup_steps) / max(1, cfg.max_steps - cfg.warmup_steps))
        return lo + 0.5 * (peak - lo) * (1 + math.cos(math.pi * p))
    if cfg.schedule == "wsd":
        decay_start = int(cfg.max_steps * (1 - cfg.decay_frac))
        if step < decay_start: return peak
        p = min(1.0, (step - decay_start) / max(1, cfg.max_steps - decay_start))
        return lo + (peak - lo) * (1 - math.sqrt(p))
    raise ValueError(cfg.schedule)
```

### 🔬 Experiment & Observe
Train micro with: constant lr (no warmup), warmup + constant, warmup + cosine, and WSD, all with the same peak lr and steps. Typically: no-warmup spikes early; constant ends with the highest loss; cosine and WSD end similarly low, with WSD showing a sharp loss drop during its decay phase.

### ⚠️ Failure Modes & Debugging
- Decaying to exactly 0 and then continuing training: stuck. Keep a min lr (or re-warm when resuming WSD).
- Schedule tied to the wrong step counter (micro-steps instead of optimizer steps) makes the decay 4× too fast with accumulation 4.

### 🧠 Expert Insight
- **Loshchilov & Hutter (2016), SGDR:** cosine annealing.
- **Hu et al. (2024), MiniCPM:** popularized WSD.
- **Hägele et al. (2024), "Scaling Laws and Compute-Optimal Training Beyond Fixed Training Durations":** WSD matches cosine while enabling cheap scaling-law studies with a single run and many decays.
- DeepSeek-V3 used a WSD-style multi-step schedule.

### ✅ Check Your Instinct
1. Why warm up?
2. Main practical advantage of WSD over cosine?

<details><summary>Answers</summary>

1. Early updates with random weights and poorly estimated Adam statistics are unstable; warmup keeps them small.
2. You don't need to fix the training length in advance; you can branch and decay from any stable-phase checkpoint.
</details>

### 📌 Recap Card
- Warmup: ~1–5% of steps (a few hundred to a few thousand).
- Cosine to ~10% of the peak, or WSD with a 10–20% decay.
- Schedules are keyed on *optimizer* steps.

> **Core intuition:** *Start gently, explore boldly, then settle carefully.*

## 24.3 Gradient Clipping: A Seatbelt for Gradients

### 🧭 The Problem First
A rare bad batch (weird data, a numerical fluke) can produce a gradient 100× larger than normal. One such step can wreck the weights, and the loss spikes or diverges.

### 💡 Intuition / Instinct
Compute the **global gradient norm** (across all parameters). If it exceeds a threshold c (typically 1.0), scale the entire gradient down so its norm = c. Direction is preserved, magnitude is capped. Normal steps are untouched (their norm is usually below c after early training); outlier steps are tamed.

### 🖼️ Visual Mental Model

```text
 ‖g‖ = 0.4 → unchanged           ‖g‖ = 25 → g × (1/25) → ‖g‖ = 1
 grad-norm log over time:   ▁▂▁▂▁▁█▁▂▁   the spike gets clipped
```

### 📐 The Math, Gently
$\|g\| = \sqrt{\sum_p\|g_p\|^2}$; if $\|g\| > c$: $g \leftarrow g\cdot c/\|g\|$.
With Adam, the updates are roughly normalized anyway, but clipping still matters, because a huge gradient pollutes the moment estimates m and v for many steps.

### 🛠️ Build It From Scratch

```python
import torch
def clip_grad_norm_(params, max_norm):
    grads = [p.grad for p in params if p.grad is not None]
    total = torch.sqrt(sum((g.detach().float() ** 2).sum() for g in grads))
    coef = max_norm / (total + 1e-6)
    if coef < 1:
        for g in grads: g.mul_(coef)
    return total
# check vs torch.nn.utils.clip_grad_norm_ on a random model: identical norms and clipped grads
```

### 🔬 Experiment & Observe
Log the grad norm every step. Typical healthy pattern: large at the start, falling, then slowly *rising* late in training as the lr decays (a known phenomenon). Spikes in the grad norm often precede loss spikes (Ch 27).

### ⚠️ Failure Modes & Debugging
- Clip threshold too low (e.g. 0.1) → every step is clipped, which effectively lowers the lr and slows training. Check the fraction of clipped steps (a small share is healthy).
- With gradient accumulation, clip *after* all micro-batches, not per micro-batch.
- With mixed precision + GradScaler (fp16), **unscale first**, then clip (Ch 25).

### 🧠 Expert Insight
Pascanu et al. (2013). Clip = 1.0 is nearly universal in LLM training (GPT-3, Llama, OLMo). Some recipes also *skip* batches whose grad norm is an extreme outlier (Ch 27).

### ✅ Check Your Instinct
1. Does clipping change the gradient direction?
2. When should you clip with accumulation?

<details><summary>Answers</summary>

1. No, only the magnitude (global scaling).
2. Once, after accumulating all micro-batches, before `opt.step()`.
</details>

### 📌 Recap Card
- Global-norm clipping at 1.0.
- Log the grad norm every step.
- Clip after accumulation, after unscaling.

> **Core intuition:** *Let the gradient steer, but never let it floor the accelerator.*

## 24.4 Gradient Accumulation: Big Batches on Small GPUs

### 🧭 The Problem First
Good LLM training wants batches of ~0.5M tokens. Your GPU fits 16 × 1024 = 16K tokens per forward pass.

### 💡 Intuition / Instinct
Run k micro-batches, calling `backward()` on each **without zeroing** the grads (they add up, Ch 6.5), with each loss divided by k. Then take one optimizer step. Mathematically this is identical to one big batch (except for batch-dependent layers like BatchNorm, which we don't use).

### 🖼️ Visual Mental Model

```text
 micro1: loss/4 → backward ┐
 micro2: loss/4 → backward ├─ grads sum = mean-gradient of the 4×bigger batch
 micro3: loss/4 → backward │
 micro4: loss/4 → backward ┘ → clip → step → zero_grad
```

### 📐 The Math, Gently
$\nabla\frac{1}{kB}\sum_{i=1}^{kB}\ell_i = \sum_{j=1}^k\nabla\frac{1}{k}\left(\frac1B\sum_{i\in\text{micro}_j}\ell_i\right)$.

### 🛠️ Build It From Scratch

```python
# nanoforge/train.py (part 3: one optimizer step with accumulation)
import torch
def train_step(model, opt, batches, cfg, ctx):
    """batches: iterator yielding (x, y); returns (mean loss, grad norm)."""
    total = 0.0
    for micro in range(cfg.grad_accum):
        x, y = next(batches)
        with ctx:                                               # autocast context (Ch 25)
            _, loss = model(x, y)
            loss = loss / cfg.grad_accum
        loss.backward()
        total += loss.item()
    gn = torch.nn.utils.clip_grad_norm_(model.parameters(), cfg.grad_clip)
    opt.step()
    opt.zero_grad(set_to_none=True)
    return total, gn.item()
```

Verify the equivalence:

```python
torch.manual_seed(0)
from nanoforge.models.gpt import GPT, GPTConfig
m1 = GPT(GPTConfig(n_layer=2, n_head=2, n_embd=64, vocab_size=128, block_size=32)); m2 = GPT(m1.cfg); m2.load_state_dict(m1.state_dict())
x = torch.randint(0, 128, (8, 32)); y = torch.randint(0, 128, (8, 32))
m1(x, y)[1].backward()
for i in range(4): (m2(x[2*i:2*i+2], y[2*i:2*i+2])[1] / 4).backward()
print(max((a.grad - b.grad).abs().max().item() for a, b in zip(m1.parameters(), m2.parameters())))  # ~1e-7
```

### 🔬 Experiment & Observe
Train with micro 32 × accum 1 vs micro 8 × accum 4. The loss curves should match per optimizer step (up to dropout/data-order noise); the second uses less memory and takes a bit longer.

### ⚠️ Failure Modes & Debugging
- Forgetting `/ grad_accum`: effectively a k× larger lr.
- Calling `zero_grad` inside the micro loop: only the last micro-batch counts.
- Losses of varying token counts per micro-batch (e.g. masked SFT): dividing by k isn't exact; normalize by the total number of *tokens* across micro-batches instead (Ch 37).
- In DDP, sync gradients only on the last micro-batch (`no_sync`), Ch 31.

### 🧠 Expert Insight
Accumulation trades time for memory. It doesn't reduce compute; parallelism (Ch 31) does. It is also how you keep the *same* global batch when moving between hardware setups, which keeps runs comparable.

### ✅ Check Your Instinct
1. What's wrong if you forget to divide by k?
2. Does accumulation speed up training?

<details><summary>Answers</summary>

1. The gradients are k× too large (like a k× lr; clipping may partially hide it).
2. No; it only enables larger effective batches within memory limits.
</details>

### 📌 Recap Card
- Sum grads over k micro-batches with loss/k.
- One clip + step per k micro-batches.
- Normalize by tokens when micro-batches differ.

> **Core intuition:** *A big batch is just several small batches whose gradients you add before moving.*

## 24.5 Logging: Loss, Grad-Norm, LR, Tokens/sec, MFU

### 🧭 The Problem First
You're paying for GPU hours. Are you using the hardware well? Is training healthy? Without the right numbers you can't tell until it's too late.

### 💡 Intuition / Instinct
Log every few steps: train loss, lr, grad norm, tokens/sec, **MFU** (Model FLOPs Utilization: the fraction of the GPU's peak FLOPs your training actually achieves), and memory. Periodically: val loss, samples, checkpoints. MFU is your efficiency grade: 30–50% is good for small setups, and frontier runs reach ~40–55%.

### 🖼️ Visual Mental Model

```text
 step  loss   lr       gnorm  tok/s    MFU   mem
 100   4.21   5.0e-4   1.8    410K    38%   9.1GB
 110   4.12   5.5e-4   1.2    412K    38%   9.1GB
```

### 📐 The Math, Gently
$\text{MFU} = \frac{\text{achieved FLOPs/s}}{\text{peak FLOPs/s}} = \frac{\text{tok/s}\times(6N + 6LTC)}{\text{peak}}$.
Peak bf16 dense (approximate): RTX 3090 ~71 TFLOPs; RTX 4090 ~165; A100 312; H100 SXM ~989.
Example: a 30M-param model at 400K tok/s: $400\text{K}\times6\times30\text{M} = 7.2\times10^{13}$ = 72 TFLOPs → 44% MFU on a 4090.

### 🛠️ Build It From Scratch

```python
# nanoforge/train.py (part 4: the full loop)
import json, os, time, contextlib
import torch
from nanoforge.models.gpt import GPT, GPTConfig, CONFIGS
from nanoforge.data.loader import make_loader
from nanoforge.optim import make_param_groups
from nanoforge.utils import set_seed, get_device

PEAK_FLOPS = {"NVIDIA GeForce RTX 3090": 71e12, "NVIDIA GeForce RTX 4090": 165e12,
              "NVIDIA A100-SXM4-40GB": 312e12, "NVIDIA A100-SXM4-80GB": 312e12, "NVIDIA H100 80GB HBM3": 989e12,
              "Tesla T4": 65e12, "NVIDIA L4": 121e12}

def estimate_mfu(model, tokens_per_sec, device_name):
    cfg = model.cfg
    flops_per_token = 6 * model.num_params() + 6 * cfg.n_layer * cfg.block_size * cfg.n_embd
    return tokens_per_sec * flops_per_token / PEAK_FLOPS.get(device_name, 100e12)

@torch.no_grad()
def evaluate(model, loader_iter, iters, ctx):
    model.eval(); tot = 0.0
    for _ in range(iters):
        x, y = next(loader_iter)
        with ctx: tot += model(x.to(model.lm_head.weight.device, non_blocking=True), y.to(model.lm_head.weight.device, non_blocking=True))[1].item()
    model.train(); return tot / iters

def main(cfg: "TrainConfig"):
    set_seed(cfg.seed); dev = get_device(); os.makedirs(cfg.out_dir, exist_ok=True)
    mcfg = GPTConfig(**CONFIGS[cfg.model_size], vocab_size=cfg.vocab_size, dropout=cfg.dropout)
    model = GPT(mcfg).to(dev)
    opt = torch.optim.AdamW(make_param_groups(model, cfg.weight_decay), lr=cfg.lr,
                            betas=(cfg.beta1, cfg.beta2), fused=(dev == "cuda"))
    ctx = torch.autocast("cuda", dtype=getattr(torch, cfg.dtype)) if dev == "cuda" else contextlib.nullcontext()
    start_step = 0   # set by resume logic (Ch 25)
    if cfg.compile: model = torch.compile(model)
    train_it = iter(make_loader(cfg.train_index, mcfg.block_size, cfg.micro_batch, cfg.seed, start_step=start_step))
    val_it = iter(make_loader(cfg.val_index, mcfg.block_size, cfg.micro_batch, cfg.seed + 1, num_workers=1))
    def batches():
        while True:
            x, y = next(train_it); yield x.to(dev, non_blocking=True), y.to(dev, non_blocking=True)
    B = batches(); dname = torch.cuda.get_device_name() if dev == "cuda" else "cpu"
    tokens_per_step = cfg.micro_batch * cfg.grad_accum * mcfg.block_size
    print(f"params {model.num_params()/1e6:.1f}M | tokens/step {tokens_per_step} | total {tokens_per_step*cfg.max_steps/1e6:.0f}M")
    log = open(os.path.join(cfg.out_dir, "log.jsonl"), "a"); t0 = time.time()
    for step in range(start_step, cfg.max_steps + 1):
        lr = lr_at(step, cfg)
        for g in opt.param_groups: g["lr"] = lr
        if step % cfg.eval_interval == 0:
            vl = evaluate(model, val_it, cfg.eval_iters, ctx)
            print(f"step {step} | val {vl:.4f}"); log.write(json.dumps({"step": step, "val_loss": vl}) + "\n")
        loss, gn = train_step(model, opt, B, cfg, ctx)
        if step % cfg.log_interval == 0:
            if dev == "cuda": torch.cuda.synchronize()
            dt = (time.time() - t0) / (cfg.log_interval if step > start_step else 1); t0 = time.time()
            tps = tokens_per_step / dt
            rec = {"step": step, "loss": loss, "lr": lr, "grad_norm": gn, "tok_per_s": tps,
                   "mfu": estimate_mfu(model if not cfg.compile else model._orig_mod, tps, dname),
                   "mem_gb": torch.cuda.max_memory_allocated() / 1e9 if dev == "cuda" else 0}
            print(" | ".join(f"{k} {v:.4g}" if isinstance(v, float) else f"{k} {v}" for k, v in rec.items()))
            log.write(json.dumps(rec) + "\n"); log.flush()
        # checkpointing added in Ch 25

if __name__ == "__main__":
    import sys
    cfg = TrainConfig()
    for arg in sys.argv[1:]:                                   # --key=value overrides
        k, v = arg.lstrip("-").split("="); t = type(getattr(cfg, k))
        setattr(cfg, k, v.lower() == "true" if t is bool else t(v))
    main(cfg)
```

### ⚠️ Failure Modes & Debugging
- Timing without `cuda.synchronize()` measures kernel *launch* time, not execution; the numbers look impossibly fast.
- `loss.item()` every micro-step forces a GPU sync (a small slowdown). Fine at our scale; at scale, accumulate the loss on the GPU and sync rarely.
- Very low MFU (< 10%) usually means a data-loader bottleneck, tiny matrices, or no bf16.

### 🧠 Expert Insight
- **PaLM (2022)** defined MFU (and HFU, which includes recomputation).
- Weights & Biases / TensorBoard are standard dashboards. The `wandb` flag is left to you as an exercise (`wandb.log(rec)`).

### ✅ Check Your Instinct
1. What does 5% MFU suggest?
2. Why synchronize before timing?

<details><summary>Answers</summary>

1. The GPU is mostly idle or inefficient: a data bottleneck, small batch/matrices, no mixed precision, or Python overhead.
2. CUDA ops are asynchronous; without a sync you time only the launches.
</details>

### 📌 Recap Card
- Log loss, lr, grad norm, tok/s, MFU, memory.
- MFU = tok/s × 6N / peak.
- Synchronize before timing.

> **Core intuition:** *What you don't measure, you can't fix, and GPUs are too expensive to guess about.*
