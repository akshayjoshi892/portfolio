## 50.1 Choosing a Dataset and a Compute Budget

### 🧭 The Problem First
You can train *something* on *anything*. The question is what's worth training: which corpus gives you a model that's measurably good at something, with the compute you actually have, in a time frame you can sustain? Most failed capstones fail here, by choosing a corpus that's too small, too messy, impossible to evaluate, or a model far too big for the budget.

### 💡 Intuition / Instinct
A good Capstone domain has four properties:
1. **Enough text:** at least ~20M tokens of your domain after cleaning; 100M–1B is comfortable. Less than that and you should plan on **mixing** with general-domain data (Ch 22.5) and treating the domain data as the specialization.
2. **Clear rights:** you're allowed to train on it and to share the resulting model (Ch 21.2). Your own notes, public-domain books, permissively licensed code and documentation, and openly licensed papers are safe starting points.
3. **Evaluable:** you can write questions with checkable answers (Ch 36.1). If you can't tell a good output from a bad one, you can't improve the model.
4. **You care about it:** you'll spend weeks reading its outputs.

Examples that work well: a programming language's documentation + permissive code; a non-English language's public-domain literature and Wikipedia; a scientific subfield's open-access papers; a technical manual collection; a legal corpus with public-domain status.

Then set the **compute budget** before choosing the model: GPU type × hours × realistic MFU (30–45%, Ch 24.5). Keep ~25% in reserve for pilot runs, ablations, evals, restarts and post-training. Only then use scaling laws to split the remaining compute between parameters N and tokens D (Ch 26.3). If your data can't feed a compute-optimal run, you're **data-limited**: train a smaller model on the data you have (up to ~4 epochs; Ch 27.4) and spend the spare compute on ablations and post-training, or add general-domain data.

A final consideration: **inference**. If the model will be served a lot, a smaller model trained on more tokens than Chinchilla-optimal ("overtrained") is cheaper to serve at the same quality (Ch 26, 45.5).

### 🖼️ Visual Mental Model

```text
 budget (GPU·hours × peak × MFU) ─▶ minus 25% reserve ─▶ C for pretraining
                                                            │
 corpus tokens × ≤4 epochs (+ general data) ─▶ usable D ────┤
                                                            ▼
                         compute-optimal (N, D) from Ch 26 ── is D_opt ≤ usable D?
                              yes: train (N_opt, D_opt)      no: data-limited → N ≈ D/20, bank the spare compute
                                                                                 or mix in general data
```

### 📐 The Math, Gently
Budget: $C = \text{peak} \times \text{MFU} \times n_{gpu} \times 3600\cdot\text{hours} \times (1 - \text{reserve})$.

Compute-optimal split (Ch 26.3): $N_{opt} \approx G\,(C/6)^{\beta/(\alpha+\beta)}$, $D_{opt} = C/(6N_{opt})$, which lands near 20 tokens per parameter.

**Overtraining factor k:** keeping C fixed, $N = N_{opt}/\sqrt{k}$ and $D = k^{1/2}D_{opt}$ gives $D/N = k\cdot D_{opt}/N_{opt}$. The loss penalty is small for modest k (the loss surface is flat near the optimum), while serving cost falls ∝ N.

**Worked example:** one RTX 4090 for 24 hours at 35% MFU: $165\text{e}12 \times 0.35 \times 86{,}400 \approx 5.0\times10^{18}$ FLOPs, or $3.7\times10^{18}$ after a 25% reserve. Compute-optimal: ~146M parameters on ~4.3B tokens. With a 300M-token domain corpus (1.2B usable at 4 epochs), you're data-limited: ~60M parameters on 1.2B tokens, using only ~12% of the pretraining budget, unless you mix in ~5B general tokens, in which case the plan becomes ~146M parameters on 4.3B tokens (less than one epoch of the mixture).

### 🛠️ Build It From Scratch

```python
# scripts/capstone_plan.py
import argparse, math
from nanoforge.scaling import chinchilla_optimal, chinchilla_loss, GPU_PEAK_BF16

def plan(corpus_tokens, gpu="RTX4090", n_gpus=1, hours=24.0, mfu=0.35, max_epochs=4.0,
         general_tokens=0, overtrain=1.0, reserve=0.25):
    """Pick model size N and training tokens D for a compute budget, respecting how much data exists.
    reserve: fraction of the compute kept back for ablations, evals, restarts and post-training.
    overtrain > 1 trades training compute for a smaller, cheaper-to-serve model (more tokens per parameter)."""
    C = GPU_PEAK_BF16[gpu] * mfu * n_gpus * hours * 3600 * (1 - reserve)
    N_opt, D_opt = chinchilla_optimal(C)
    N = N_opt / math.sqrt(overtrain); D = C / (6 * N)                     # keep C fixed while shifting N ↔ D
    available = max_epochs * corpus_tokens + general_tokens               # unique-ish tokens we may use
    notes = []
    if D > available:                                                     # data-limited: not enough tokens for this compute
        D = available; N = D / (20 * overtrain)                           # keep ~20 tokens/param rather than inflating N
        notes.append(f"data-limited: only {available/1e9:.2f}B usable tokens -> using {6*N*D/C:.1%} of the budget; "
                     "add general-domain data to use the rest, or spend it on more ablations / post-training")
    epochs = D / (corpus_tokens + general_tokens) if corpus_tokens + general_tokens else float("inf")
    if epochs > 4: notes.append(f"{epochs:.1f} epochs over the data: expect diminishing returns beyond ~4 (Ch 27.4)")
    return {"compute_flops": 6 * N * D, "budget_flops": C, "N_params": N, "D_tokens": D, "tokens_per_param": D / N,
            "epochs": epochs, "chinchilla_loss_estimate": chinchilla_loss(N, D), "notes": notes}

def nearest_config(N, configs):
    """configs: {name: n_params}. Returns the largest config not bigger than 1.5 × N."""
    ok = {k: v for k, v in configs.items() if v <= 1.5 * N}
    return max(ok, key=ok.get) if ok else min(configs, key=configs.get)

if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--corpus_tokens", type=float, required=True, help="tokens in YOUR corpus after cleaning")
    ap.add_argument("--general_tokens", type=float, default=0.0, help="extra general-domain tokens (e.g. TinyStories/FineWeb)")
    ap.add_argument("--gpu", default="RTX4090"); ap.add_argument("--n_gpus", type=int, default=1)
    ap.add_argument("--hours", type=float, default=24); ap.add_argument("--mfu", type=float, default=0.35)
    ap.add_argument("--overtrain", type=float, default=1.0)
    a = ap.parse_args()
    p = plan(a.corpus_tokens, a.gpu, a.n_gpus, a.hours, a.mfu, general_tokens=a.general_tokens, overtrain=a.overtrain)
    sizes = {"nano": 0.8e6, "micro": 10e6, "mini": 50e6, "small": 125e6}        # approximate (Ch 0 size ladder)
    print(f"compute for pretraining : {p['compute_flops']:.2e} of {p['budget_flops']:.2e} FLOPs available")
    print(f"model size              : {p['N_params']/1e6:.0f}M params  -> closest config: {nearest_config(p['N_params'], sizes)}")
    print(f"training tokens         : {p['D_tokens']/1e9:.2f}B ({p['tokens_per_param']:.0f} tokens/param, {p['epochs']:.1f} epochs)")
    print(f"Chinchilla-law loss est.: {p['chinchilla_loss_estimate']:.2f} (MassiveText units; use only for relative comparisons)")
    for n in p["notes"]: print("NOTE:", n)
```

### ⚠️ Failure Modes & Debugging
- **Choosing the model size first** ("I want a 1B model") and discovering it needs a month of GPU time.
- **Counting documents or words instead of tokens.**
- **Unevaluable domains** (e.g. "creative writing in my style") with no plan for evaluation: fine for fun, weak for a Capstone.
- **Private or licensed data** you can't share: you can still do the Capstone, but you can't publish the model or data, so plan the write-up accordingly.

### 🧠 Expert Insight
- **Hoffmann et al. (2022)** for compute-optimal sizing; **Muennighoff et al. (2023), "Scaling Data-Constrained Language Models":** up to ~4 epochs of repeated data is nearly as good as fresh data; returns diminish quickly after that.
- **Sardana & Frankle (2023), "Beyond Chinchilla-Optimal":** accounting for inference demand favours smaller, longer-trained models. Many open small models are trained at hundreds to thousands of tokens per parameter.
- **Domain-adaptive continued pretraining** (Gururangan et al., 2020, "Don't Stop Pretraining") on top of a general open model is the most compute-efficient route to a strong domain model in practice. The Capstone trains from scratch because the point is to own every step; mention the continued-pretraining alternative in your write-up.

## 50.2 Data → Tokenizer → Pretrain (With Scaling-Law Planning)

### 🧭 The Problem First
You have a plan. Now you have to turn raw files into a trained base model through about a dozen steps, each of which can fail silently, and a multi-hour run that must survive crashes. How do you run the pipeline so that a mistake at step 9 doesn't force you to redo steps 1–8, and so that you catch problems in minutes rather than after a day of training?

### 💡 Intuition / Instinct
Treat the Capstone as a **pipeline of stages** with explicit inputs and outputs, where each stage is skipped if its output already exists (like `make`). Then follow three rules:
1. **Inspect every artefact.** Read 20 cleaned documents; decode 20 tokenized samples; plot the token-length histogram; check the train/val split has no overlap. Ten minutes of looking prevents most expensive mistakes (Ch 21–23).
2. **Pilot before you commit.** Run the full training config for ~1–2% of the steps. Check: the initial loss ≈ ln V, the loss falls smoothly, tokens/s and MFU are what the planner assumed, memory fits, and checkpoint → resume works (Ch 24–25). Only then launch the real run.
3. **Confirm the size choice at small scale.** Train 3 small models (e.g. 1/16, 1/4, 1× of a tiny budget), fit the loss curve (Ch 26.4), and check your chosen size sits near the optimum *for your data*.

### 🖼️ Visual Mental Model

```text
 raw/ ──▶ [tokenizer] ──▶ tokenizer.json
      └─▶ [data: clean → dedup → filter → shard → pack] ──▶ train/val .bin shards + index
                                                                   │
            [pilot: 1–2% of steps] ── checks OK? ── no ──▶ fix, rerun pilot
                                          │ yes
            [pretrain: WSD schedule, QK-norm, checkpoints every N steps, resume on crash]
                                          │
                                   base checkpoint ──▶ eval_base (bpb, domain suite)
```

### 📐 The Math, Gently
**Steps from tokens:** $\text{steps} = D / (B_{micro}\cdot \text{accum}\cdot T \cdot n_{gpu})$. With D = 4.3B, micro-batch 16, accumulation 16 and T = 1,024 on one GPU: 4.3e9 / 262,144 ≈ 16,400 steps.

**Wall-clock check:** $\text{hours} \approx 6ND / (\text{peak}\cdot\text{MFU}\cdot 3600)$. If the pilot's measured MFU is lower than planned, recompute *before* launching; either accept the longer run or shrink D.

**Warmup-Stable-Decay (WSD, Ch 24.2)** is the most convenient schedule for a Capstone: the stable phase can be extended if you get more compute, and a short decay (10–20% of steps) at any point gives a usable checkpoint.

### 🛠️ Build It From Scratch
The pipeline runner. A JSON config names every path, so the whole Capstone is reproducible from one file:

```python
# scripts/capstone.py
"""The whole Capstone as a restartable pipeline. Each stage runs one command and is considered done when
its output exists. Rerunning skips finished stages, so a crash or a change only costs the stages after it."""
import argparse, json, pathlib, shlex, subprocess, sys, time

P = sys.executable
def stages(c):
    ck, d = c["ckpt_dir"], c["data_dir"]
    return [
        ("tokenizer", [P, "scripts/train_tokenizer.py", "--input", c["raw_glob"], "--vocab", str(c["vocab"]),
                       "--out", c["tokenizer"]], c["tokenizer"]),
        ("data",      [P, "scripts/prepare_data.py", "--inputs", c["raw_glob"], "--tokenizer", c["tokenizer"],
                       "--out", d, "--near_dedup"], f"{d}/train_index.json"),
        ("pilot",     [P, "-m", "nanoforge.train", "--arch=llama", f"--model_size={c['size']}", f"--vocab_size={c['vocab']}",
                       f"--train_index={d}/train_index.json", f"--val_index={d}/val_index.json",
                       f"--max_steps={c['pilot_steps']}", f"--out_dir={ck}/pilot"], f"{ck}/pilot/ckpt_final.pt"),
        ("pretrain",  [P, "-m", "nanoforge.train", "--arch=llama", f"--model_size={c['size']}", f"--vocab_size={c['vocab']}",
                       f"--train_index={d}/train_index.json", f"--val_index={d}/val_index.json",
                       f"--max_steps={c['steps']}", "--schedule=wsd", "--qk_norm=true", f"--out_dir={ck}/base"],
                      f"{ck}/base/ckpt_final.pt"),
        ("eval_base", [P, "scripts/eval_harness.py", "--ckpt", f"{ck}/base/ckpt_final.pt", "--tokenizer", c["tokenizer"],
                       "--suite", c["eval_glob"], "--val_texts", c["val_texts"], "--out", "reports/base.json"], "reports/base.json"),
        ("sft",       [P, "scripts/sft.py", "--base", f"{ck}/base/ckpt_final.pt", "--data", c["sft_data"],
                       "--tokenizer", c["tokenizer"], "--out", f"{ck}/sft"], f"{ck}/sft/ckpt_final.pt"),
        ("eval_sft",  [P, "scripts/eval_harness.py", "--ckpt", f"{ck}/sft/ckpt_final.pt", "--tokenizer", c["tokenizer"],
                       "--suite", c["eval_glob"], "--val_texts", c["val_texts"], "--chat", "--out", "reports/sft.json"],
                      "reports/sft.json"),
        ("dpo",       [P, "scripts/dpo.py", "--sft", f"{ck}/sft/ckpt_final.pt", "--pairs", c["pref_data"],
                       "--tokenizer", c["tokenizer"], "--out", f"{ck}/dpo"], f"{ck}/dpo/ckpt_final.pt"),
        ("eval_dpo",  [P, "scripts/eval_harness.py", "--ckpt", f"{ck}/dpo/ckpt_final.pt", "--tokenizer", c["tokenizer"],
                       "--suite", c["eval_glob"], "--val_texts", c["val_texts"], "--chat", "--out", "reports/dpo.json"],
                      "reports/dpo.json"),
        ("gate",      [P, "scripts/gate.py", "reports/sft.json", "reports/dpo.json"], None),
        ("quant",     [P, "scripts/capstone_quant.py", "--ckpt", f"{ck}/dpo/ckpt_final.pt", "--tokenizer", c["tokenizer"],
                       "--val_texts", c["val_texts"], "--out", "reports/quant.json"], "reports/quant.json"),
    ]

def run(config_path, only=None, start=None, dry_run=False):
    c = json.load(open(config_path))
    pathlib.Path("reports").mkdir(exist_ok=True)
    started = start is None
    for name, cmd, out in stages(c):
        started = started or name == start
        if not started or (only and name not in only): continue
        if out and pathlib.Path(out).exists():
            print(f"[skip] {name}: {out} exists"); continue
        print(f"[run ] {name}: {' '.join(shlex.quote(x) for x in cmd)}")
        if dry_run: continue
        t0 = time.time(); r = subprocess.run(cmd)
        print(f"[done] {name} in {(time.time() - t0) / 60:.1f} min (exit {r.returncode})")
        if r.returncode != 0: sys.exit(f"stage {name} failed; fix it and rerun (finished stages are skipped)")

if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--config", default="capstone.json"); ap.add_argument("--only", nargs="*")
    ap.add_argument("--start"); ap.add_argument("--dry_run", action="store_true")
    a = ap.parse_args(); run(a.config, a.only, a.start, a.dry_run)
```

### 🔬 Experiment & Observe
1. Tokenizer: train 8k, 16k and 32k vocabularies; measure bytes/token on held-out domain text and the embedding-parameter share for your model size (Ch 16.4). Choose, and justify the choice in one sentence.

### ⚠️ Failure Modes & Debugging
- **Tokenizer trained on different text than the model** (e.g. on uncleaned data): the vocabulary wastes slots on boilerplate.
- **Validation data that leaked into training** through near-duplicates: suspiciously low val loss. Dedup *across* the split (Ch 21.5).
- **Launching the long run without a resume test:** the first crash costs you the run.
- **Changing the config mid-run** without noting it: your write-up can no longer describe what you trained. Log every intervention (Ch 27.3).

### 🧠 Expert Insight
- Open, fully documented training reports (**OLMo**, **Pythia**, **SmolLM**, **MiniCPM**'s WSD analysis) are the best references for what a complete, working small-model recipe looks like; compare yours against one of them.
- **nanoGPT and its "speedrun" descendants** show how much a well-tuned small run can achieve, and are a good sanity reference for your tokens/s and loss.

## 50.3 Eval → SFT → Preference Tuning

### 🧭 The Problem First
Your base model writes fluent domain text, but it doesn't answer questions, follow instructions, or know when to stop. Post-training fixes that, and can also quietly break it: SFT can erase domain knowledge, preference tuning can make it verbose or sycophantic. How do you improve the model step by step without regressing?

### 💡 Intuition / Instinct
Build the **evaluation harness first** and run it at every stage (Ch 35–36). Each post-training stage must pass a **regression gate** against the previous one before it's accepted:

1. **Eval suite** (fixed before post-training, never trained on):
   - bits-per-byte on held-out domain text (did we damage the base knowledge?),
   - a domain QA suite with checkable answers (Ch 36.1),
   - a small general suite (e.g. a few hundred HellaSwag or simple arithmetic items) to track forgetting,
   - a safety/over-refusal set appropriate to the domain (Ch 42.4),
   - a pairwise judge comparison against the previous stage on ~100 open-ended prompts (Ch 36.2).
2. **SFT** (Ch 37–38) on a mix: domain instruction data (templated from your documents and synthetic from a strong model, grounded and verified: Ch 42.1), a general instruction slice (~15–30%) as replay against forgetting, and optionally RAG-style (Ch 46) and tool-use (Ch 47) examples.
3. **Preference tuning** (Ch 39–40): DPO on pairs from your SFT model's own samples, judged by a stronger model or by you. Optionally **GRPO** (Ch 41) if your domain has verifiable answers (calculations, code with tests, exact lookups).

### 🖼️ Visual Mental Model

```text
 base ──eval──▶ report_base
   │ SFT (domain + replay + RAG/tool)
 sft  ──eval──▶ report_sft  ──gate(base→sft: domain QA ↑ required, bpb not much worse)──▶ accept?
   │ DPO (self-sampled pairs, judged)   [+ GRPO if verifiable]
 dpo  ──eval──▶ report_dpo  ──gate(sft→dpo: no significant regressions; judge win-rate ↑)──▶ accept?
```

### 📐 The Math, Gently
**Regression gate:** for each suite, compute the paired bootstrap CI of the accuracy difference on the *same items* (Ch 35.5). Block promotion if the difference is significantly negative *and* larger than a tolerance (e.g. 2 points). Require a significant improvement on the suites the stage was meant to improve.

**Replay fraction:** forgetting grows with the SFT learning rate × steps and with the distance between the SFT data and pretraining data. Mixing a fraction r of pretraining-like text (or general instructions) into SFT bounds the drift; r ≈ 0.1–0.3 is typical (Ch 37.4).

**DPO β** (Ch 40.1): smaller β allows the policy to move further from the SFT reference. Track the KL to the reference and the average response length; a length increase of more than ~30% is a warning sign of verbosity bias from the judge.

### 🛠️ Build It From Scratch
The regression gate:

```python
# scripts/gate.py
import argparse, json, sys
from nanoforge.eval.stats import paired_bootstrap

def gate(old_report, new_report, max_drop=0.02, bpb_tolerance=0.02, must_improve=()):
    """Promote the new checkpoint only if no suite regresses significantly (paired bootstrap on shared item ids)
    by more than `max_drop`, bits-per-byte doesn't worsen by more than `bpb_tolerance` (relative),
    and every suite in `must_improve` improves significantly. Returns (ok, reasons)."""
    ok, reasons = True, []
    for name, new in new_report["suites"].items():
        old = old_report["suites"].get(name)
        if old is None: reasons.append(f"{name}: new suite, no comparison"); continue
        o = {r["id"]: r["correct"] for r in old["results"]}; n = {r["id"]: r["correct"] for r in new["results"]}
        ids = sorted(set(o) & set(n))
        diff, (lo, hi) = paired_bootstrap([n[i] for i in ids], [o[i] for i in ids])
        line = f"{name}: {diff:+.3f} [{lo:+.3f}, {hi:+.3f}] (n={len(ids)})"
        if hi < 0 and diff < -max_drop:                                  # significant AND large
            ok = False; line += "  REGRESSION"
        if name in must_improve and lo <= 0:
            ok = False; line += "  required improvement not significant"
        reasons.append(line)
    if "bpb" in old_report and "bpb" in new_report:
        rel = (new_report["bpb"] - old_report["bpb"]) / old_report["bpb"]
        reasons.append(f"bpb: {old_report['bpb']:.4f} -> {new_report['bpb']:.4f} ({rel:+.1%})")
        if rel > bpb_tolerance: ok = False; reasons[-1] += "  REGRESSION"
    return ok, reasons

if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("old"); ap.add_argument("new")
```

```python
    """After merge_lora, replace each LoRALinear by its (merged) base Linear so the checkpoint has plain keys."""
    for module in list(model.modules()):
        for name, child in list(module.named_children()):
            if isinstance(child, LoRALinear): setattr(module, name, child.base)
    for p in model.parameters(): p.requires_grad_(True)
    return model

def save_final(model, out_dir):
    os.makedirs(out_dir, exist_ok=True)
    torch.save({"model": model.state_dict(), "model_config": dataclasses.asdict(model.cfg)},
               os.path.join(out_dir, "ckpt_final.pt"))
```

**Building the preference pairs** from your own SFT model (on-policy data works better than someone else's pairs):
1. Take ~1,000–3,000 domain prompts (held out from SFT).
2. Sample 2–4 responses per prompt from the SFT model at temperature ~0.8 (Ch 13).
3. Judge pairs with a strong model using a rubric specific to your domain (accuracy, completeness, concision, safety), in both orders to cancel position bias (Ch 36.2); keep only consistent verdicts.
4. Spot-check 50 pairs by hand, and record the agreement rate in your write-up.

### 🔬 Experiment & Observe
1. SFT: sweep the replay fraction r ∈ {0, 0.15, 0.3}. Plot domain QA accuracy vs general-suite accuracy (and domain bpb). Choose the Pareto point.
2. Full fine-tuning vs LoRA (r = 16, 64): compare scores, training memory and time. Record both in the write-up.
3. DPO: sweep β ∈ {0.05, 0.1, 0.3}; track judge win-rate against SFT, response length and domain QA accuracy. Beware of a win-rate increase that's entirely explained by longer answers.
4. Run `gate.py` after every stage and keep the reports; the sequence of reports is the backbone of your results section.

### ⚠️ Failure Modes & Debugging
- **Training on eval items** via synthetic data generated from the same documents the QA suite was written from: decontaminate (Ch 35.4) with n-gram overlap against the eval set.
- **The chat template differs between SFT, eval and serving:** the model sees prompts it wasn't trained on. Use the one `ChatFormatter` everywhere (Ch 37.2).
- **DPO on pairs from a different model:** off-policy pairs work less well; sample from your own SFT model.
- **Reward hacking by the judge:** length, flattery, confident tone. Use rubrics, length-controlled comparisons, and read samples.

### 🧠 Expert Insight
- **Ouyang et al. (2022), InstructGPT** introduced the SFT → preference-model → RL pipeline; **Tunstall et al. (2023), Zephyr** showed that distilled SFT + DPO on AI-judged pairs is a strong recipe for small open models.
- **Lambert et al. (2024), Tülu 3:** a fully open post-training recipe (SFT → DPO → RL with verifiable rewards) with its data, code and evals: the best reference for a modern, complete pipeline.
- **Regression gating** is standard practice for model releases; large labs run hundreds of evals per candidate checkpoint.

### ✅ Check Your Instinct
1. Why sample preference pairs from your own SFT model?
2. Why must the eval set be fixed before post-training starts?

<details><summary>Answers</summary>

1. DPO learns most from distinctions among outputs the policy actually produces (on-policy); pairs from another model may be easy to separate for reasons irrelevant to your model's mistakes.
2. Otherwise you'll (consciously or not) tune the evals to the model's strengths; a fixed, pre-registered suite keeps the comparison honest.
</details>

### 📌 Recap Card
- Fixed eval suite → SFT with replay → on-policy DPO (→ GRPO if verifiable).
- Gate each stage with paired statistics; require the intended improvement.
- One chat template everywhere; decontaminate synthetic data; watch length.

> **Core intuition:** *Every post-training step is a trade. The eval harness is how you know whether you got a good deal.*

## 50.4 Quantize → Serve → Chat UI

### 🧭 The Problem First
Your aligned model lives in a checkpoint file. Nobody else can use it. Turn it into something people can talk to, at an acceptable speed, on hardware you actually have, with a clear statement of what it can and can't do.

### 💡 Intuition / Instinct
Three steps, each using a chapter's tools:
1. **Choose the deployment precision** with the quantization report (Ch 44.5): bf16 vs INT8 vs INT4 (RTN/AWQ/GPTQ), judged on bpb, mean KL, *your harness scores* and speed. Pick the smallest format whose harness scores stay within your gate tolerance.
2. **Serve** with the continuous-batching engine and streaming API (Ch 45.4), optionally with RAG over your corpus (Ch 46) and the constrained JSON mode (Ch 43.3).
3. **Add a chat UI and a model card.** The UI is a single HTML page that streams from your API. The model card tells users what the model is for, how it was trained and evaluated, and where it fails.

### 🖼️ Visual Mental Model

```text
 dpo checkpoint ─▶ quant report ─▶ chosen format (e.g. INT8 or INT4-g128)
                                       │
 browser ⇄ GET /  (chat page)          ▼
         ⇄ POST /v1/generate (SSE) ─▶ engine (paged KV, continuous batching) ─▶ model
         (optional) /v1/rag ─▶ hybrid retrieval ─▶ cited answers
 + MODEL_CARD.md: intended use, data, evals, limitations, safety
```

### 📐 The Math, Gently
**Will it fit?** Weights: $N \times b_w$ bytes. KV cache per token: $2 L H_{kv} D \times b_{kv}$ bytes (Ch 30.2). For the "mini" config (~50M parameters, L = 8, H_kv = 2, D = 64) in bf16: weights ≈ 100 MB and KV ≈ 4 KB per token, so even 64 concurrent 1,024-token conversations need only ~270 MB of KV. Small models are easy to serve; the bottleneck is usually Python overhead, not memory (Ch 45.3).

**Latency target:** TPOT under ~50 ms (20+ tokens/s per user) feels fluid in chat. Measure it under load with `load_test` (Ch 45.3).

## 50.5 Write-Up Template and Grading Rubric

### 🧭 The Problem First
You've done the work. Now make it legible: to a future employer, a collaborator, a reviewer, or yourself in a year. And assess it honestly: what level have you actually reached?

### 💡 Intuition / Instinct
A good write-up is a **reproducible argument**: here's what I set out to do, here's exactly what I did, here's the evidence (with error bars), here's what didn't work, and here's how you can reproduce it. The rubric below turns "is this good?" into specific, checkable criteria, at four levels, so you can see both where you are and what the next level requires.

### 🖼️ Visual Mental Model

```text
 write-up:  question → setup → pipeline → results (tables + CIs + samples) → ablations → failures → limitations → reproduce
 rubric:    8 criteria × 4 levels   (Beginner → Intermediate → Advanced → Expert)
```

### 📐 The Math, Gently
Every number in the results section carries its uncertainty: accuracy with a 95% CI (Ch 35.5), differences between stages with paired bootstrap CIs, training-run comparisons with multiple seeds where affordable (Ch 49.2). One rule of thumb: if two numbers' CIs overlap heavily, don't write "improved"; write "no significant difference".

### 🛠️ Build It From Scratch
**The write-up template** (`WRITEUP.md`, 4–8 pages):

```text
# <Title>: a <N>M-parameter language model for <domain>, built from scratch

## 1. Goal
The question or capability, why it matters, and the success criteria defined BEFORE training.

## 2. Data
Sources, licenses, sizes (raw → cleaned → deduped → filtered, in tokens), mixing ratios,

## 7. Evaluation

## 8. Deployment
Quantization report, chosen format, serving benchmarks (TTFT/TPOT p50/p99, throughput), cost estimate.

## 9. Analysis

## 10. What didn't work

## 11. Limitations & safety
```

| **Deployment** | Generates text from a script | Streaming server with the chat template and EOS handling | Quantized model chosen with a quality/speed report; continuous batching; load-tested with p50/p99 | RAG and/or tools integrated with their own evals; speculative decoding or other speed work; cost analysis |

**Suggested scopes by tier** (adjust to your budget):
- **Beginner:** Llama-nano/micro on 10–50M tokens; SFT on a few hundred examples; a script that chats. A weekend to a week.

- **Advanced:** Llama-mini on 1–5B tokens with a scaling sweep; SFT + DPO with gates; quantized, load-tested deployment; model card. 3–6 weeks.

### ⚠️ Failure Modes & Debugging
