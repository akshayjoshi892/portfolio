## 30.1 Why Generation Recomputes, and How to Cache K and V

### 🧭 The Problem First
Our `generate()` calls `model(idx)` on the *whole* sequence every step. To produce token 1000, it recomputes the keys and values of tokens 1–999, which were already computed on the previous steps.

### 💡 Intuition / Instinct
In causal attention, a past token's K and V never change when new tokens are added (they only depend on that token and earlier ones). So **cache them**. Each new step:
1. Run the model on *only the new token*.
2. At each layer, compute its q, k, v; **append** its k, v to that layer's cache.
3. Attend the new q over all cached keys and values.

The per-step cost drops from O(T) tokens of compute to O(1) token (plus attention over T cached entries).

### 🖼️ Visual Mental Model

```text
 step t:  new token ─▶ q_t, k_t, v_t
          cache_K = [k_1 ... k_{t-1}] + k_t
          cache_V = [v_1 ... v_{t-1}] + v_t
          out_t = softmax(q_t · cache_Kᵀ / √d) · cache_V
 prefill: process the prompt in parallel once, filling the cache
 decode:  one token at a time, reading the cache
```

### 📐 The Math, Gently
Without a cache: generating N tokens after a prompt of P costs $\sum_{t=P}^{P+N} 2N_{params}\cdot t$ FLOPs, roughly quadratic in length. With a cache: $≈ 2N_{params}(P + N)$ + attention reads. For P = 1000 and N = 1000, that's about 750× fewer FLOPs for the linear layers.

### 🛠️ Build It From Scratch

```python
# nanoforge/models/kv_cache.py
import torch

class KVCache:
    """Preallocated per-layer cache. k/v: (B, H_kv, T_max, D)."""
    def __init__(self, n_layer, B, H_kv, T_max, D, device, dtype):
        self.k = torch.zeros(n_layer, B, H_kv, T_max, D, device=device, dtype=dtype)
        self.v = torch.zeros_like(self.k)
        self.pos = 0                                        # number of cached positions
    def update(self, layer, k_new, v_new):
        """k_new/v_new: (B, H_kv, t, D). Writes at [pos:pos+t]; returns views up to the new length."""
        t = k_new.size(2)
        self.k[layer, :, :, self.pos:self.pos + t] = k_new
        self.v[layer, :, :, self.pos:self.pos + t] = v_new
        return self.k[layer, :, :, :self.pos + t], self.v[layer, :, :, :self.pos + t]
    def advance(self, t): self.pos += t
```

Cache-aware attention (added to `CausalSelfAttention` from Ch 18):

```python
# in CausalSelfAttention
    def forward(self, x, cache=None, layer_idx=None):
        B, T, C = x.shape; H, D = self.n_head, C // self.n_head
        q, k, v = self.c_attn(x).split(self.n_embd, dim=2)
        q = q.view(B, T, H, D).transpose(1, 2); k = k.view(B, T, H, D).transpose(1, 2); v = v.view(B, T, H, D).transpose(1, 2)
        if cache is not None:
            k, v = cache.update(layer_idx, k, v)            # now (B, H, pos+T, D)
        # causal only needed when T > 1 (prefill); a single new query attends to all cached keys
        is_causal = cache is None or T > 1
        if cache is not None and T > 1 and cache.pos > 0:
            # prefill-in-chunks with an existing cache: build an explicit offset causal mask
            Tk = k.size(2); qi = torch.arange(Tk - T, Tk, device=x.device)[:, None]; kj = torch.arange(Tk, device=x.device)[None]
            y = torch.nn.functional.scaled_dot_product_attention(q, k, v, attn_mask=(kj <= qi))
        else:
            y = torch.nn.functional.scaled_dot_product_attention(q, k, v, is_causal=is_causal)
        return self.c_proj(y.transpose(1, 2).contiguous().view(B, T, C))
```

Thread the cache through `Block` and `GPT`, and add `generate_cached`:

```python
# in Block:   def forward(self, x, cache=None, layer_idx=None):
#                 x = x + self.attn(self.ln_1(x), cache, layer_idx); x = x + self.mlp(self.ln_2(x)); return x
# in GPT:
    def forward_cached(self, idx, cache):
        B, T = idx.shape
        pos = torch.arange(cache.pos, cache.pos + T, device=idx.device)
        x = self.transformer.wte(idx) + self.transformer.wpe(pos)
        for i, blk in enumerate(self.transformer.h): x = blk(x, cache, i)
        cache.advance(T)
        return self.lm_head(self.transformer.ln_f(x[:, -1:, :]))   # (B, 1, V)

    @torch.no_grad()
    def generate_cached(self, idx, max_new_tokens, temperature=1.0, top_k=None):
        from nanoforge.sampling import top_k_filter
        cfg = self.cfg; B = idx.size(0); D = cfg.n_embd // cfg.n_head
        cache = KVCache(cfg.n_layer, B, cfg.n_head, min(cfg.block_size, idx.size(1) + max_new_tokens), D,
                        idx.device, self.lm_head.weight.dtype)
        logits = self.forward_cached(idx, cache)                      # prefill
        for _ in range(max_new_tokens):
            l = logits[:, -1, :].float() / max(temperature, 1e-6)
            nxt = torch.multinomial(torch.softmax(top_k_filter(l, top_k), -1), 1)
            idx = torch.cat([idx, nxt], 1)
            if idx.size(1) >= cache.k.size(3): break
            logits = self.forward_cached(nxt, cache)                  # decode: one token
        return idx
```

### 🔬 Experiment & Observe
Time `generate` vs `generate_cached` for 500 new tokens with the micro model. Expect a 5–50× speedup, growing with length.

### ⚠️ Failure Modes & Debugging
- Wrong position ids for the new token (restarting at 0), which breaks the positional encoding. Use `cache.pos`.
- Applying the causal mask to the single decode query → it attends only to key 0. With T = 1 there must be no mask.
- Exceeding the preallocated `T_max` → index error. Stop or use sliding windows.

### 🧠 Expert Insight
Every inference engine is built around the KV cache: HF `past_key_values`, vLLM's PagedAttention (Ch 45), and prefix caching (reusing the cache across requests with the same system prompt).

### ✅ Check Your Instinct
1. Why can past K/V be cached in causal models but not bidirectional ones?
2. What's recomputed per decode step with a cache?

<details><summary>Answers</summary>

1. In causal models, past tokens never attend to future tokens, so their K/V never change; in bidirectional models they would.
2. Only the new token's forward pass (all layers) and its attention over the cache.
</details>

### 📌 Recap Card
- Cache K, V per layer; append each step.
- Prefill in parallel, then decode one token at a time.
- Position ids continue from `cache.pos`; no mask for single-token decode.

> **Core intuition:** *Don't reread the whole book to write the next word; keep notes on what you've read.*

## 30.2 KV-Cache Memory Math

### 🧭 The Problem First
"Why can't I serve more users / longer contexts?" The weights fit, but memory runs out anyway.

### 💡 Intuition / Instinct
The cache stores K and V for **every layer, every KV head, every position, every sequence in the batch**. It grows linearly with context and batch, and for long contexts it can exceed the weights.

### 🖼️ Visual Mental Model

```text
 bytes = 2 (K,V) × L × H_kv × D × T × B × bytes_per_elem
 Llama-2-7B (MHA: H_kv=32, D=128, L=32), fp16, T=4096, B=1:
   2·32·32·128·4096·2 B = 2.1 GB per sequence    (weights: 13.5 GB)
 B=16 → 34 GB of cache!
```

### 📐 The Math, Gently
Per token: $2 L H_{kv} D\cdot b$ bytes. Llama-2-7B: 2 × 32 × 32 × 128 × 2 = 524 KB/token. Llama-3-8B (GQA, H_kv = 8): 131 KB/token, **4× smaller**.

### 🛠️ Build It From Scratch

```python
def kv_cache_gb(L, H_kv, D, T, B=1, bytes_per=2):
    return 2 * L * H_kv * D * T * B * bytes_per / 1e9
for name, L, Hkv, D in [("Llama2-7B MHA", 32, 32, 128), ("Llama3-8B GQA", 32, 8, 128), ("Llama3-70B GQA", 80, 8, 128)]:
    print(f"{name:15s}: {kv_cache_gb(L, Hkv, D, 8192):.2f} GB per 8K-token sequence")
```

### 🔬 Experiment & Observe
Compute the maximum concurrent 4K-token users on a 24 GB GPU serving a quantized 4-bit 8B model (~5 GB weights) with an fp16 cache: (24 − 5 − ~2 overhead) / (0.131 MB × 4096) ≈ 31 users. With an 8-bit KV cache, ~63.

### ⚠️ Failure Modes & Debugging
Serving OOMs at high concurrency are almost always the KV cache. Limit the max sequence length and batch, or quantize the cache.

### 🧠 Expert Insight
KV-cache compression is a hot area: GQA/MQA (30.3), MLA (DeepSeek-V2: low-rank latent KV), KV quantization (FP8/INT4 caches), sliding windows (Mistral), and token eviction (H2O, StreamingLLM).

<details><summary>Answers</summary>

</details>

### 📌 Recap Card
- Cache bytes = 2·L·H_kv·D·T·B·b.
- It grows with context × batch and often exceeds the weights.
- Reduce it via GQA/MQA, quantization, windows.

> **Core intuition:** *Every token you remember costs memory in every layer.*

## 30.3 Multi-Query and Grouped-Query Attention From Scratch

### 🧭 The Problem First
The cache is big because every query head has its own K/V head. And decode is memory-bound (Ch 28.2): reading the huge cache each step dominates the latency.

### 💡 Intuition / Instinct
- **MQA (multi-query):** all H query heads share **one** K/V head. The cache is H× smaller and decode much faster, at a small quality cost.
- **GQA (grouped-query):** split the query heads into G groups, each sharing one K/V head (1 < G < H). The cache is H/G× smaller with quality close to MHA. The sweet spot: Llama 2 70B and Llama 3 use H = 32/64 query heads with 8 KV heads.

Implementation: project to fewer K/V heads, then **repeat** (expand) each KV head across its group before attention (or use a kernel that indexes it directly).

### 🖼️ Visual Mental Model

```text
 MHA:  Q1 Q2 Q3 Q4 Q5 Q6 Q7 Q8        GQA (G=2):  Q1 Q2 Q3 Q4 | Q5 Q6 Q7 Q8        MQA: Q1..Q8
       K1 K2 K3 K4 K5 K6 K7 K8                     K1          | K2                     K1
```

### 📐 The Math, Gently
Params for K/V projections: MHA $2C^2$; GQA $2C\cdot(H_{kv}D)$. Cache reduction factor = $H/H_{kv}$.
Uptraining (Ainslie et al., 2023): convert an MHA checkpoint into GQA by **mean-pooling** the K/V heads within each group, then continue training ~5% of the original steps.

### 🛠️ Build It From Scratch

```python
# nanoforge/models/attention.py (append)
import torch, torch.nn as nn, torch.nn.functional as F

def repeat_kv(x, n_rep):
    """(B, H_kv, T, D) -> (B, H_kv*n_rep, T, D)"""
    if n_rep == 1: return x
    B, Hkv, T, D = x.shape
    return x[:, :, None].expand(B, Hkv, n_rep, T, D).reshape(B, Hkv * n_rep, T, D)

class GQAttention(nn.Module):
    def __init__(self, n_embd, n_head, n_kv_head, bias=False):
        super().__init__()
        assert n_head % n_kv_head == 0
        self.H, self.Hkv, self.D = n_head, n_kv_head, n_embd // n_head
        self.wq = nn.Linear(n_embd, n_head * self.D, bias=bias)
        self.wk = nn.Linear(n_embd, n_kv_head * self.D, bias=bias)
        self.wv = nn.Linear(n_embd, n_kv_head * self.D, bias=bias)
        self.wo = nn.Linear(n_head * self.D, n_embd, bias=bias); self.wo.RESIDUAL_SCALE = True
    def forward(self, x, rope=None, cache=None, layer_idx=None):
        B, T, C = x.shape
        q = self.wq(x).view(B, T, self.H, self.D).transpose(1, 2)            # (B, H, T, D)
        k = self.wk(x).view(B, T, self.Hkv, self.D).transpose(1, 2)          # (B, Hkv, T, D)
        v = self.wv(x).view(B, T, self.Hkv, self.D).transpose(1, 2)
        if rope is not None:
            cos, sin = rope; q, k = apply_rope_offset(q, k, cos, sin, cache.pos if cache else 0)
        if cache is not None: k, v = cache.update(layer_idx, k, v)           # cache stores Hkv heads only!
        k, v = repeat_kv(k, self.H // self.Hkv), repeat_kv(v, self.H // self.Hkv)
        y = F.scaled_dot_product_attention(q, k, v, is_causal=(cache is None or T > 1))
        return self.wo(y.transpose(1, 2).contiguous().view(B, T, C))

def apply_rope_offset(q, k, cos, sin, offset):
    from nanoforge.models.rope import apply_rope
    T = q.size(2)
    return apply_rope(q, cos[offset:offset + T], sin[offset:offset + T]), apply_rope(k, cos[offset:offset + T], sin[offset:offset + T])

def mha_to_gqa_weights(wk_mha, n_head, n_kv_head):
    """Mean-pool MHA K (or V) projection weights (H*D, C) into GQA (Hkv*D, C)."""
    HD, C = wk_mha.shape; D = HD // n_head; g = n_head // n_kv_head
    return wk_mha.view(n_kv_head, g, D, C).mean(1).reshape(n_kv_head * D, C)
```

(For simplicity the cached prefill case above uses `is_causal` only when there's no prior cache; the full offset-mask version is in 30.1. Ch 32 integrates GQA into the Llama-style model properly.)

### 🔬 Experiment & Observe
Train micro variants with H = 8 and H_kv ∈ {8, 4, 2, 1} on TinyStories. Compare the val loss (small differences) against the KV-cache size and decode speed (large differences). Plot quality vs cache size.

### ⚠️ Failure Modes & Debugging
- Repeating KV heads in the wrong order (interleaved vs grouped): query head h must map to KV head h // (H/H_kv). The `expand` layout above does exactly this.
- Caching the *repeated* K/V instead of the compact ones destroys the memory benefit.

### 🧠 Expert Insight
- **Shazeer (2019), "Fast Transformer Decoding: One Write-Head is All You Need"** (MQA).
- **Ainslie et al. (2023), GQA.** Used by Llama 2 70B, Llama 3 (all sizes), Mistral, Qwen 2+, Gemma 2.
- **DeepSeek-V2 (2024) MLA:** compresses K/V into a low-rank latent (~93% cache reduction vs MHA) with strong quality.

### 📌 Recap Card
- MQA: 1 KV head; GQA: G KV heads shared by groups.
- The cache shrinks by H/H_kv; quality stays near MHA for GQA.
- Cache the compact K/V; repeat at compute time.
