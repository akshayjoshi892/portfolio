## 25.1 Floating-Point Formats: FP32, FP16, BF16, FP8 Bit by Bit

### 🧭 The Problem First
FP32 (4 bytes) is safe but slow: tensor cores run 8–16× faster in 16-bit, and memory bandwidth halves. But 16-bit numbers have less range or precision. Which do we lose, and does it matter?

### 💡 Intuition / Instinct
A float = sign × mantissa × 2^exponent. **Exponent bits set the range** (how big or small a number can be). **Mantissa bits set the precision** (how finely you can distinguish neighbouring values).
- FP16: 5 exponent bits, 10 mantissa bits. Good precision, *tiny range* (max 65,504; small gradients underflow to 0).
- BF16: 8 exponent bits (the same range as FP32!), 7 mantissa bits. Coarse precision but no overflow or underflow worries. **The LLM default.**
- FP8 (E4M3/E5M2): 1 byte. Needs careful per-tensor scaling; used on H100+ for matmuls.

### 🖼️ Visual Mental Model

```text
 FP32  s|eeeeeeee|mmmmmmmmmmmmmmmmmmmmmmm   range 1e±38, ~7 decimal digits
 FP16  s|eeeee|mmmmmmmmmm                  range 6e-8..65504, ~3.3 digits
 BF16  s|eeeeeeee|mmmmmmm                  range 1e±38, ~2.4 digits
 FP8   s|eeee|mmm (E4M3)  max 448          s|eeeee|mm (E5M2) max 57344
```

### 📐 The Math, Gently
Machine epsilon (the gap after 1.0) = $2^{-\text{mantissa bits}}$: FP32 1.2e-7, FP16 9.8e-4, BF16 7.8e-3.
Consequence: in BF16, $1.0 + 0.001 = 1.0$ (the update is lost). That is why **weights and optimizer states stay in FP32** (master weights), while matmuls run in BF16.

### 🛠️ Build It From Scratch

```python
import torch, struct
def bits(x, dtype):
    t = torch.tensor([x], dtype=dtype)
    raw = t.view(torch.int16 if t.element_size() == 2 else torch.int32).item() & ((1 << (8 * t.element_size())) - 1)
    return format(raw, f"0{8*t.element_size()}b")
for dt in [torch.float32, torch.float16, torch.bfloat16]:
    print(dt, bits(3.14159, dt), torch.finfo(dt).max, torch.finfo(dt).eps, torch.finfo(dt).tiny)

print(torch.tensor(1.0, dtype=torch.bfloat16) + torch.tensor(0.001, dtype=torch.bfloat16))  # 1.0 (lost!)
print(torch.tensor(70000.0, dtype=torch.float16))   # inf (overflow)
print(torch.tensor(1e-8, dtype=torch.float16))      # 0 (underflow)
print(torch.tensor(1e-8, dtype=torch.bfloat16))     # fine
```

### 🔬 Experiment & Observe
Sum 10,000 copies of 0.0001 in each dtype, sequentially. FP32 ≈ 1.0; BF16 gets stuck well below 1 once the running sum makes each 0.0001 smaller than half an ulp. This is why reductions (softmax sums, LayerNorm statistics, the loss) are computed in FP32.

### ⚠️ Failure Modes & Debugging
- FP16 overflow in attention logits or activations → inf → NaN. Use BF16 if the hardware supports it (Ampere+).
- Keeping *weights* in BF16 with small lrs: updates round to zero and training stalls. Keep FP32 master weights.

### 🧠 Expert Insight
- **Micikevicius et al. (2017), "Mixed Precision Training":** FP32 master weights + loss scaling.
- **Kalamkar et al. (2019):** BF16 for DL.
- **Micikevicius et al. (2022), FP8 formats.** DeepSeek-V3 (2024) trained largely in FP8 with fine-grained (block-wise) scaling.

### ✅ Check Your Instinct
1. Why is BF16 preferred over FP16 for LLMs?
2. Why keep master weights in FP32?

<details><summary>Answers</summary>

1. Same range as FP32, so no overflow/underflow and no loss scaling needed.
2. Small updates would be rounded away in 16-bit.
</details>

### 📌 Recap Card
- Exponent = range; mantissa = precision.
- BF16: FP32 range, low precision; FP16: precise but narrow range.
- FP32 master weights and reductions.

> **Core intuition:** *Compute coarsely, accumulate carefully.*

## 25.2 Autocast and Loss Scaling

### 🧭 The Problem First
We want matmuls in 16-bit, but softmax, norms and the loss in FP32, without hand-casting every op.

### 💡 Intuition / Instinct
`torch.autocast` automatically runs each op in the right precision: matmuls and convolutions in BF16/FP16, sensitive ops (softmax, log, norms, reductions, loss) in FP32. The parameters stay FP32; autocast casts them on the fly.

For **FP16 only**, small gradients underflow to 0. **Loss scaling:** multiply the loss by a large factor S (e.g. 2¹⁶) before backward so the gradients are shifted into FP16's range, then divide them by S before the optimizer step. `GradScaler` adjusts S dynamically: it halves S if inf/NaN appears (and skips that step), and grows it periodically. BF16 doesn't need this.

### 🖼️ Visual Mental Model

```text
 params (fp32) ─cast─▶ bf16 matmuls ─▶ fp32 softmax/LN/loss ─▶ backward ─▶ grads (fp32 params)
 fp16 only:  loss×S ─▶ backward ─▶ grads×S ─▶ unscale (÷S) ─▶ check inf ─▶ step or skip
```

### 📐 The Math, Gently
FP16's smallest subnormal ≈ 6e-8. Gradients of ~1e-9 vanish; with S = 65,536 they become ~6.5e-5, which is representable.

### 🛠️ Build It From Scratch

```python
# in train.py: precision setup
import contextlib, torch
def make_precision(dtype_name, device):
    if device != "cuda": return contextlib.nullcontext(), None
    dtype = {"bfloat16": torch.bfloat16, "float16": torch.float16, "float32": torch.float32}[dtype_name]
    if dtype == torch.bfloat16 and not torch.cuda.is_bf16_supported():
        print("bf16 not supported (pre-Ampere GPU, e.g. T4) -> using fp16 + GradScaler"); dtype = torch.float16
    ctx = torch.autocast("cuda", dtype=dtype) if dtype != torch.float32 else contextlib.nullcontext()
    scaler = torch.amp.GradScaler("cuda") if dtype == torch.float16 else None
    return ctx, scaler

def train_step_amp(model, opt, batches, cfg, ctx, scaler):
    total = 0.0
    for _ in range(cfg.grad_accum):
        x, y = next(batches)
        with ctx:
            _, loss = model(x, y); loss = loss / cfg.grad_accum
        (scaler.scale(loss) if scaler else loss).backward()
        total += loss.item()
    if scaler: scaler.unscale_(opt)                       # unscale BEFORE clipping
    gn = torch.nn.utils.clip_grad_norm_(model.parameters(), cfg.grad_clip)
    if scaler: scaler.step(opt); scaler.update()           # skips the step if inf/nan found
    else: opt.step()
    opt.zero_grad(set_to_none=True)
    return total, gn.item()
```

Replace `train_step` in `train.py` with `train_step_amp`, and build `ctx, scaler = make_precision(cfg.dtype, dev)`.

### 🔬 Experiment & Observe
Time a micro training step in fp32 vs bf16 (vs fp16+scaler on a T4). Expect a 2–3× speedup on Ampere+. The final losses should match within noise.

### ⚠️ Failure Modes & Debugging
- Clipping *before* `unscale_` clips the scaled gradients, which is wrong.
- The loss scale collapsing toward 0 repeatedly signals real NaNs in the model (not just overflow). Debug with `torch.autograd.set_detect_anomaly(True)` on a small run.
- Casting the model to `.half()` entirely (pure fp16 weights) instead of autocast breaks the optimizer precision.

### 🧠 Expert Insight
Frontier training uses BF16 autocast with FP32 master weights and optimizer states; FP8 matmuls with delayed or block scaling on H100/B200 (Transformer Engine, DeepSeek-V3); and sometimes BF16 optimizer states with stochastic rounding to save memory.

### ✅ Check Your Instinct
1. Why doesn't BF16 need loss scaling?
2. Where must clipping happen with a GradScaler?

<details><summary>Answers</summary>

1. Its exponent range equals FP32's, so gradients don't underflow.
2. After `scaler.unscale_(opt)`, before `scaler.step(opt)`.
</details>

### 📌 Recap Card
- Autocast: 16-bit matmuls, FP32 sensitive ops.
- FP16 → GradScaler; BF16 → none.
- Unscale → clip → step.

> **Core intuition:** *Let the math that tolerates noise run fast, and protect the math that doesn't.*

## 25.3 Checkpoint Contents: Model, Optimizer, Scheduler, RNG, Data Position

### 🧭 The Problem First
Saving just `model.state_dict()` isn't enough to continue training. Resuming would reset Adam's moments (causing a loss spike), restart the data from the beginning (repeating data), and change the randomness.

### 💡 Intuition / Instinct
A **training checkpoint** captures *everything* that determines the future of the run:
- model weights (FP32);
- optimizer state (Adam's m and v, step count), which is 2× the model size;
- the step number (the scheduler is a pure function of the step);
- the RNG states (Python, NumPy, torch CPU and CUDA);
- the data position (step and seed, so the loader can fast-forward, Ch 23.2);
- the configs (model + train) and the tokenizer hash.

An **inference checkpoint** needs only the weights + config (+ tokenizer): much smaller, and best stored as safetensors.

### 🖼️ Visual Mental Model

```text
 ckpt_step_5000.pt
 ├── model:      state_dict (fp32)          1×
 ├── optimizer:  m, v, step                  2×
 ├── step: 5000, seed: 1337
 ├── rng: {python, numpy, torch, cuda}
 ├── train_config, model_config, tokenizer_hash
 └── metrics: best_val
```

### 📐 The Math, Gently
Checkpoint size ≈ 12 bytes/param (4 for FP32 weights + 8 for Adam). 1B params ≈ 12 GB; 70B ≈ 840 GB (hence sharded checkpoints at scale).

### 🛠️ Build It From Scratch

```python
# nanoforge/checkpoint.py
import os, random, json, numpy as np, torch
from dataclasses import asdict

def rng_state():
    s = {"python": random.getstate(), "numpy": np.random.get_state(), "torch": torch.get_rng_state()}
    if torch.cuda.is_available(): s["cuda"] = torch.cuda.get_rng_state_all()
    return s

def set_rng_state(s):
    random.setstate(s["python"]); np.random.set_state(s["numpy"]); torch.set_rng_state(s["torch"])
    if "cuda" in s and torch.cuda.is_available(): torch.cuda.set_rng_state_all(s["cuda"])

def save_checkpoint(path, model, opt, step, train_cfg, model_cfg, extra=None, scaler=None):
    raw = getattr(model, "_orig_mod", model)                       # unwrap torch.compile
    ckpt = {"model": raw.state_dict(), "optimizer": opt.state_dict(), "step": step,
            "train_config": asdict(train_cfg), "model_config": asdict(model_cfg),
            "rng": rng_state(), "extra": extra or {}}
    if scaler is not None: ckpt["scaler"] = scaler.state_dict()
    tmp = path + ".tmp"
    torch.save(ckpt, tmp); os.replace(tmp, path)                   # atomic: never leave a half-written file

def load_checkpoint(path, model, opt=None, scaler=None, map_location="cpu"):
    ckpt = torch.load(path, map_location=map_location, weights_only=False)
    raw = getattr(model, "_orig_mod", model); raw.load_state_dict(ckpt["model"])
    if opt is not None: opt.load_state_dict(ckpt["optimizer"])
    if scaler is not None and "scaler" in ckpt: scaler.load_state_dict(ckpt["scaler"])
    set_rng_state(ckpt["rng"])
    return ckpt

def export_inference(path, model, model_cfg, tokenizer_path):
    from safetensors.torch import save_file
    raw = getattr(model, "_orig_mod", model)
    sd = {k: v.detach().to(torch.bfloat16).contiguous() for k, v in raw.state_dict().items() if k != "lm_head.weight"}  # tied
    save_file(sd, path, metadata={"config": json.dumps(asdict(model_cfg)), "tokenizer": tokenizer_path, "tied": "true"})
```

(`safetensors` refuses to store shared tensors, so we drop the tied `lm_head.weight` and re-tie on load. Install `safetensors` via pip.)

### 🔬 Experiment & Observe
Save a checkpoint at step 1000 and inspect its size vs `num_params × 12`. Then load it into a fresh model and verify the val loss matches exactly.

### ⚠️ Failure Modes & Debugging
- Non-atomic saves plus a crash mid-write gives a corrupted "latest" checkpoint. Write to a temp file and rename (done above), and keep the last 2–3 checkpoints.
- Saving the compiled model's `state_dict` adds an `_orig_mod.` prefix to the keys. Unwrap first (done).
- `torch.load` defaults to `weights_only=True` in recent PyTorch; our checkpoint contains Python objects (RNG states), so pass `weights_only=False` for *your own trusted* files only. Never unpickle untrusted checkpoints: use safetensors for sharing.

### 🧠 Expert Insight
Large-scale training uses **sharded, asynchronous checkpointing** (PyTorch DCP, the FSDP state-dict APIs): every GPU writes its shard in parallel while training continues. Meta reported frequent hardware interruptions during Llama 3 training (419 unexpected interruptions over 54 days), so checkpoint frequency is a cost-optimization problem.

### ✅ Check Your Instinct
1. Why save the optimizer state?
2. Why is `pickle`-based loading of untrusted checkpoints dangerous?

<details><summary>Answers</summary>

1. Resetting Adam's moments causes large early updates → a loss spike, and changes the run.
2. Unpickling can execute arbitrary code; safetensors stores only tensors.
</details>

### 📌 Recap Card
- Training checkpoint: model + optimizer + step + RNG + data position + configs.
- Atomic writes; keep several checkpoints.
- Share weights via safetensors.

> **Core intuition:** *A checkpoint must contain the entire future of the run, not just its present.*

## 25.4 Exact Resumption and Fault Tolerance

### 🧭 The Problem First
The run crashes at step 7,340. You restart from the step 7,000 checkpoint. Does the loss curve continue *exactly* as if nothing happened? If not, your experiment has changed, and debugging spikes becomes impossible.

### 💡 Intuition / Instinct
Exact resumption needs deterministic *everything after the checkpoint*: the same weights and optimizer state (loaded), the same lr (a function of the step), the same data order (the loader fast-forwards to step × micro-batches × accum), and the same RNG (restored). GPU non-determinism (atomic adds) introduces tiny differences, but they should be negligible.

The resume logic:
1. Find the latest valid checkpoint in `out_dir`.
2. Load everything and set `start_step = ckpt["step"] + 1`.
3. Rebuild the data iterator starting at `start_step`.
4. Continue.

### 🖼️ Visual Mental Model

```text
 run A: ─────────────────────────────────▶ (no crash)
 run B: ──────────── crash │ resume from ckpt ──────▶
 loss curves overlap after resume (within GPU noise) ✓
```

### 📐 The Math, Gently
Data fast-forward: samples consumed per rank = start_step × grad_accum × micro_batch.

### 🛠️ Build It From Scratch

```python
# in train.py main(), after building model/opt/scaler:
import glob
def latest_checkpoint(out_dir):
    cks = sorted(glob.glob(os.path.join(out_dir, "ckpt_*.pt")), key=lambda p: int(p.split("_")[-1].split(".")[0]))
    return cks[-1] if cks else None

start_step = 0
ck = latest_checkpoint(cfg.out_dir)
if ck:
    state = load_checkpoint(ck, model, opt, scaler, map_location=dev)
    start_step = state["step"] + 1
    print(f"resumed from {ck} at step {start_step}")
train_it = iter(make_loader(cfg.train_index, mcfg.block_size, cfg.micro_batch, cfg.seed,
                            start_step=start_step * cfg.grad_accum))

# in the loop, after train_step:
if step > 0 and step % cfg.ckpt_interval == 0:
    save_checkpoint(os.path.join(cfg.out_dir, f"ckpt_{step:07d}.pt"), model, opt, step, cfg, mcfg, scaler=scaler)
    for old in sorted(glob.glob(os.path.join(cfg.out_dir, "ckpt_*.pt")))[:-3]: os.remove(old)   # keep last 3
```

### 🔬 Experiment & Observe
Run the test. If the curves diverge right after the resume, check in this order: the optimizer state, the lr at resume, the data offset, the RNG. Plot both curves overlaid.

### ⚠️ Failure Modes & Debugging
- The loader restarts at step 0 → the model re-sees early data (a loss dip, then a rise).
- The optimizer isn't restored → a loss spike right after the resume.
- `step` off by one → one repeated step (minor, but it breaks exactness).
- Changing `micro_batch`/`grad_accum` between runs changes the data mapping. Keep the global batch in tokens the same and recompute the offset.

### 🧠 Expert Insight
Frontier runs automate this with health checks (NaN detection, hung collectives, straggler detection), automatic restarts from the last checkpoint, and sometimes "rewinding" further back to skip bad data (Ch 27).
