## 33.1 Conditional Computation: Many Specialists, Few Active

### 🧭 The Problem First
Dense models use *every* parameter for *every* token. Knowledge scales with parameters, but so does the cost per token. Can we have a 400B-parameter model that costs as much per token as a 40B one?

### 💡 Intuition / Instinct
Replace the single MLP in a block with **E expert MLPs** plus a small **router** that picks the top-k experts for each token (typically k = 1–8 out of 8–256). Each token uses only k experts, so compute ∝ k, while the capacity ∝ E. It's like a hospital: every patient sees one or two relevant specialists, not all the doctors. Recall from Ch 19.3 that the MLP is a key–value memory; MoE is a *much bigger* memory with sparse access.

### 🖼️ Visual Mental Model

```text
 token x ─▶ router: softmax(x W_r) → top-2: expert 3 (0.6), expert 7 (0.4)
         ─▶ y = 0.6·E3(x) + 0.4·E7(x)          (other experts not computed)
```

### 📐 The Math, Gently
Total params ≈ dense params + (E − 1) × MLP params per layer; **active** params per token ≈ attention + k × MLP.
Mixtral 8×7B: 46.7B total, ~12.9B active (k = 2 of 8). DeepSeek-V3: 671B total, 37B active.
Training FLOPs ≈ 6 × N_active × D.

Predict: at equal *active* params and tokens, will an MoE beat a dense model on val loss? (Yes, typically noticeably, but at a higher memory cost.)

### ⚠️ Failure Modes & Debugging
MoE saves FLOPs, not memory. All E experts must be stored (and served), which is a big deal for deployment.

- **Jacobs et al. (1991)**, **Shazeer et al. (2017), "Outrageously Large Neural Networks"** (sparsely-gated MoE).
- **Lepikhin et al. (2020), GShard**; **Fedus et al. (2021), Switch Transformer** (k = 1).

## 33.2 Router Design: Top-k Gating

### 🧭 The Problem First
How does a token choose its experts, differentiably, when the choice "top-k" is discrete?

### 💡 Intuition / Instinct
The router is a linear layer: logits = x·W_r (one score per expert). Take the top-k scores; the gate weights are the softmax over those k (or the softmax over all E, then keep the top-k and optionally renormalize). The discrete selection has no gradient, but **the gate weights do**: an expert that helps gets its weight increased through the loss, so the router learns which experts suit which tokens.

### 🖼️ Visual Mental Model

```text
 logits (E=8): [0.1, 2.3, -0.5, 1.9, 0.0, 0.4, -1.2, 0.8]
 top-2: expert1 (2.3), expert3 (1.9) → softmax over [2.3, 1.9] = [0.60, 0.40]
```

### 📐 The Math, Gently
$g = \text{softmax}(\text{TopK}(xW_r))$, $y = \sum_{i\in\text{TopK}} g_i E_i(x)$.
The gradient reaches $W_r$ through the $g_i$ (the selected experts only). Noisy top-k (Shazeer 2017) adds noise to the logits during training for exploration.
DeepSeek-V3 uses **sigmoid** affinities with top-k, and normalizes among the selected ones.

### 🛠️ Build It From Scratch

```python
import torch, torch.nn as nn, torch.nn.functional as F
class TopKRouter(nn.Module):
    def __init__(self, C, E, k, noise_std=0.0):
        super().__init__(); self.w = nn.Linear(C, E, bias=False); self.k, self.noise = k, noise_std
    def forward(self, x):                                # x: (N, C) flattened tokens
        logits = self.w(x).float()                       # (N, E), router in fp32 for stability
        if self.training and self.noise > 0: logits = logits + torch.randn_like(logits) * self.noise
        probs = F.softmax(logits, -1)                    # used for the balance loss
        topv, topi = torch.topk(probs, self.k, dim=-1)   # (N, k)
        gates = topv / topv.sum(-1, keepdim=True)        # renormalize among selected
        return gates, topi, probs, logits
r = TopKRouter(16, 8, 2); g, i, p, _ = r(torch.randn(5, 16)); print(g, i)
```

### 🔬 Experiment & Observe
After training (33.4), log which experts each token type is routed to (e.g. digits, punctuation, names). Often you'll find syntactic/lexical specializations more than "topic" experts.

### ⚠️ Failure Modes & Debugging
- Running the router in bf16 → precision issues in the near-ties, causing unstable routing. Compute the router in fp32.
- k = 1 with no noise or balancing → early collapse onto one expert.

### 🧠 Expert Insight
**Expert choice routing (Zhou et al., 2022):** experts pick their top tokens (perfect balance, but tokens may get 0 experts; awkward for causal decoding). Token-choice top-k remains the standard for decoder LLMs.

### ✅ Check Your Instinct

</details>

### 📌 Recap Card
- Router = linear → top-k → gate weights.
- Gradients flow via the gates of the selected experts.
- Router in fp32.

> **Core intuition:** *The router is a receptionist learning which specialist helps each patient.*

## 33.3 Load-Balancing Losses and Capacity Factors

### 🧭 The Problem First
Left alone, routing collapses: a few experts get most tokens (they improve, so they get even more tokens), and the others starve. Hardware-wise, overloaded experts become bottlenecks and memory spikes.

### 💡 Intuition / Instinct
1. **Auxiliary load-balancing loss:** penalize the *product* of each expert's fraction of tokens ($f_i$) and its mean router probability ($P_i$). It's minimized when both are uniform, and it nudges the router toward even usage.
2. **Capacity factor:** each expert processes at most $\text{cap} = \text{CF}\cdot\frac{kN}{E}$ tokens per batch; overflow tokens are dropped (they pass through via the residual). CF = 1.0–1.25.
3. **Router z-loss:** keep the router logits small (as in Ch 27).
4. **Aux-loss-free balancing (DeepSeek-V3):** add a per-expert *bias* to the routing scores (used only for selection), nudged up for underloaded and down for overloaded experts after each step. There is no gradient interference with the main loss.

### 🖼️ Visual Mental Model

```text
 tokens per expert without balancing:  ██████████ ███ ▏ ▏ █ ▏ ▏ ▏
 with balancing:                       ███ ███ ███ ██ ███ ███ ██ ███
```

### 📐 The Math, Gently
Switch-style aux loss: $\mathcal{L}_{aux} = \alpha\cdot E\sum_{i=1}^E f_i P_i$, with $f_i$ = fraction of token-assignments routed to expert i, $P_i$ = mean router probability for expert i, and α ≈ 0.01. Under uniform routing, $f_i = P_i = 1/E$ gives $\mathcal{L}_{aux} = \alpha$.
Capacity: N = 4096 tokens, k = 2, E = 8, CF = 1.25 give cap = 1.25 × 8192/8 = 1280 per expert.

### 🛠️ Build It From Scratch

```python
def load_balance_loss(probs, topi, E):
    """probs: (N, E) router softmax; topi: (N, k) selected experts."""
    N, k = topi.shape
    counts = torch.zeros(E, device=probs.device).scatter_add_(0, topi.flatten(), torch.ones(N * k, device=probs.device))
    f = counts / (N * k)                     # fraction of assignments per expert
    P = probs.mean(0)                        # mean router prob per expert
    return E * (f * P).sum()

class BiasBalancer:
    """DeepSeek-V3-style aux-loss-free balancing: adjust selection bias by load."""
    def __init__(self, E, gamma=1e-3, device="cpu"): self.bias = torch.zeros(E, device=device); self.gamma = gamma
    @torch.no_grad()
    def update(self, topi, E):
        load = torch.bincount(topi.flatten(), minlength=E).float()
        self.bias += self.gamma * torch.sign(load.mean() - load)     # raise underloaded, lower overloaded
```

### 🔬 Experiment & Observe
Train an MoE with aux coefficient 0, 0.01 and 0.1. Plot the expert-usage histogram and the val loss. 0 → collapse; 0.1 → balanced but the loss is slightly worse (interference); 0.01 → a good trade-off. Try the bias balancer with 0 aux loss.

### ⚠️ Failure Modes & Debugging
- Token dropping at a low capacity factor hurts quality. Monitor the drop rate (< 1–2%).
- An aux loss computed per micro-batch vs globally changes the behaviour. Be consistent.

### 🧠 Expert Insight
- **Fedus et al. (2021), Switch:** aux loss + capacity factor.
- **Zoph et al. (2022), ST-MoE:** router z-loss for stability.
- **Wang et al. (2024) / DeepSeek-V3:** auxiliary-loss-free load balancing via bias terms (plus a small sequence-wise balance loss).

### ✅ Check Your Instinct
1. Why does routing collapse without balancing?
2. Capacity per expert for N = 8192, k = 1, E = 16, CF = 1.0?

<details><summary>Answers</summary>

</details>

### 📌 Recap Card
- Aux loss $E\sum f_iP_i$ (α ≈ 0.01) or bias-based balancing.
- Capacity factor caps the tokens per expert; overflow is dropped.
- Router z-loss for stability.

> **Core intuition:** *Without a queue manager, everyone lines up at the most popular doctor.*

## 33.4 Implementing an MoE Layer; Fine-Grained and Shared Experts

### 🧭 The Problem First
We need an efficient MoE layer that drops into the Llama block in place of the SwiGLU MLP.

### 💡 Intuition / Instinct
Flatten the tokens to (N, C) → route → **group the tokens by expert** (sort by expert id) → run each expert on its batch → scatter the outputs back, weighted by the gates → sum over the k choices.
**Fine-grained experts (DeepSeekMoE):** split each expert into m smaller ones and route to m·k of them. There are many more combinations, so better specialization at the same compute.
**Shared experts:** 1–2 experts that *every* token uses (capturing common knowledge), plus routed experts for specialization.

### 🖼️ Visual Mental Model

```text
 x (N,C) → router → (topi, gates)
 sort assignments by expert → [e0 tokens][e1 tokens]...[eE tokens]
 for e: y_e = Expert_e(x[idx_e]) * gate
 out = scatter_add(y_e back to token positions) + SharedExpert(x)
```

### 📐 The Math, Gently
Fine-grained: E' = mE experts of hidden size F/m, choose k' = mk. The active compute is the same; the number of possible combinations $\binom{E'}{k'}$ is vastly larger.

### 🛠️ Build It From Scratch

```python
# nanoforge/models/moe.py
import math, torch, torch.nn as nn, torch.nn.functional as F

class Expert(nn.Module):
    def __init__(self, C, H):
        super().__init__()
        self.w_gate, self.w_up, self.w_down = nn.Linear(C, H, bias=False), nn.Linear(C, H, bias=False), nn.Linear(H, C, bias=False)
        self.w_down.RESIDUAL_SCALE = True
    def forward(self, x): return self.w_down(F.silu(self.w_gate(x)) * self.w_up(x))

class MoE(nn.Module):
    def __init__(self, C, n_experts=8, top_k=2, expert_hidden=None, n_shared=0, aux_coef=0.01,
                 capacity_factor=None, bias_balance=False):
        super().__init__()
        H = expert_hidden or 64 * math.ceil(int(8 * C / 3) / 64)
        self.E, self.k, self.aux_coef, self.cf = n_experts, top_k, aux_coef, capacity_factor
        self.router = nn.Linear(C, n_experts, bias=False)
        self.experts = nn.ModuleList([Expert(C, H) for _ in range(n_experts)])
        self.shared = nn.ModuleList([Expert(C, H) for _ in range(n_shared)])
        self.register_buffer("sel_bias", torch.zeros(n_experts), persistent=True)
        self.bias_balance = bias_balance
        self.aux_loss = torch.tensor(0.0); self.last_load = None

    def forward(self, x):                                   # (B, T, C)
        B, T, C = x.shape; xf = x.view(-1, C); N = xf.size(0)
        logits = self.router(xf).float()                    # (N, E)
        probs = F.softmax(logits, -1)
        sel = probs + (self.sel_bias if self.bias_balance else 0)
        _, topi = torch.topk(sel, self.k, dim=-1)           # selection may use bias
        gates = probs.gather(1, topi); gates = gates / gates.sum(-1, keepdim=True)   # weights don't use bias
        # aux loss
        counts = torch.bincount(topi.flatten(), minlength=self.E).float()
        self.last_load = counts.detach()
        self.aux_loss = self.aux_coef * self.E * ((counts / (N * self.k)) * probs.mean(0)).sum() if self.training else torch.tensor(0.0, device=x.device)
        # dispatch: flatten (token, choice) pairs, sort by expert
        flat_e = topi.flatten()                             # (N*k,)
        flat_tok = torch.arange(N, device=x.device).repeat_interleave(self.k)
        flat_g = gates.flatten().to(x.dtype)
        order = torch.argsort(flat_e, stable=True)
        flat_e, flat_tok, flat_g = flat_e[order], flat_tok[order], flat_g[order]
        out = torch.zeros_like(xf)
        cap = None if self.cf is None else int(self.cf * N * self.k / self.E)
        starts = torch.cumsum(torch.bincount(flat_e, minlength=self.E), 0) - torch.bincount(flat_e, minlength=self.E)
        for e in range(self.E):
            n_e = int(counts[e].item())
            if n_e == 0: continue
            s = int(starts[e].item()); idx = slice(s, s + (min(n_e, cap) if cap else n_e))   # drop overflow
            tok = flat_tok[idx]
            out.index_add_(0, tok, self.experts[e](xf[tok]) * flat_g[idx, None])
        for sh in self.shared: out = out + sh(xf)
        return out.view(B, T, C)

    @torch.no_grad()
    def update_bias(self, gamma=1e-3):
        if self.bias_balance and self.last_load is not None:
            self.sel_bias += gamma * torch.sign(self.last_load.mean() - self.last_load)
```

### ⚠️ Failure Modes & Debugging
- The Python loop over experts is slow; use grouped/batched GEMM (e.g. `torch._grouped_mm`, MegaBlocks) for speed.
- `torch.compile` and data-dependent shapes: MoE dispatch causes graph breaks unless handled carefully.
- Forgetting to add the aux loss to the total loss means no balancing.

### 🧠 Expert Insight
- **Dai et al. (2024), DeepSeekMoE:** fine-grained + shared experts.
- **Gale et al. (2022), MegaBlocks:** dropless MoE via block-sparse kernels.
- **Qwen1.5-MoE, OLMoE (2024):** open fine-grained MoEs with detailed ablations.

### 📌 Recap Card
