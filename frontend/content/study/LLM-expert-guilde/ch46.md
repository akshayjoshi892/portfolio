## 46.1 Why Models Need an External Memory

### 🧭 The Problem First
Ask your domain model about a document added last week: it has never seen it. Ask about a specific number in a 300-page manual it *was* trained on: it produces a confident, plausible and wrong value. Fine-tune it on the manual: it improves a little, still hallucinates specifics, and you'd have to retrain every time the manual changes.

### 💡 Intuition / Instinct
Parameters are a lossy, compressed memory (Ch 1.1, 5.7). They're good at *skills* and general knowledge, bad at exact, rare or fresh facts. The context window, by contrast, is a perfect short-term memory: anything in the prompt can be copied exactly (the induction heads of Ch 48.3 are the copying machinery).

**RAG** = look things up first, then answer with the relevant text in context:
1. **Index** your documents once: split them into chunks and store them in a searchable form.
2. At query time, **retrieve** the few chunks most relevant to the question.
3. **Generate** an answer conditioned on the question *and* the retrieved chunks, ideally citing them.

It's an open-book exam instead of a closed-book one. The model's job shifts from *remembering* to *reading and reasoning*, which small models do much better.

RAG vs fine-tuning isn't either/or: fine-tuning teaches style, format and domain skills (Ch 37–38), and RAG supplies facts. The strongest systems fine-tune the model *to use* retrieved context well.

### 🖼️ Visual Mental Model

```text
 OFFLINE                                    ONLINE
 documents ─▶ chunk ─▶ embed ─▶ index       question ─▶ embed ─▶ search index ─▶ top-k chunks
                     └─▶ BM25 index                    └─▶ BM25 ───────────────┘      │
                                                                         fuse + rerank ▼
                                            prompt = system + chunks [1..k] + question ─▶ LLM ─▶ answer [1][3]
```

### 📐 The Math, Gently
Think of RAG as a latent-variable model: the answer y depends on a retrieved document z,

$$p(y \mid x) = \sum_{z \in \text{top-}k} p_\eta(z \mid x)\; p_\theta(y \mid x, z)$$

with a retriever $p_\eta(z\mid x) \propto \exp(\text{sim}(x, z))$ and a generator $p_\theta$. In practice we don't sum: we concatenate the top-k chunks into one context and let attention do the "marginalization". The formula still explains the two failure modes: the right z isn't retrieved (retriever failure), or it's retrieved but ignored or misread (generator failure). Evaluation (46.4) measures each separately.

### 🛠️ Build It From Scratch
The smallest possible RAG loop, to see the whole thing before we improve each part (retrieval here is plain keyword overlap):

```python
# nanoforge/apps/rag_minimal.py
import re

def words(t): return set(re.findall(r"\w+", t.lower()))

def retrieve_keyword(question, chunks, k=3):
    q = words(question)
    return sorted(chunks, key=lambda c: -len(q & words(c["text"])))[:k]

RAG_SYSTEM = ("Answer the question using ONLY the numbered sources. Cite sources like [1]. "
              "If the sources do not contain the answer, say you don't know.")

def build_rag_messages(question, retrieved):
    ctx = "\n\n".join(f"[{i + 1}] ({c['source']})\n{c['text']}" for i, c in enumerate(retrieved))
    return [{"role": "system", "content": RAG_SYSTEM},
            {"role": "user", "content": f"Sources:\n{ctx}\n\nQuestion: {question}"}]

def rag_answer(llm_chat_fn, question, chunks, k=3, retriever=retrieve_keyword):
    hits = retriever(question, chunks, k)
    return llm_chat_fn(build_rag_messages(question, hits)), hits
```

`llm_chat_fn(messages) -> str` can be your served model (Ch 45) or any other chat model; everything in this chapter is written against that interface.

### 🔬 Experiment & Observe
Take 20 questions about specific facts in your Capstone corpus. Answer them (a) closed-book with your SFT model and (b) with `rag_answer` over the corpus chunks. Count correct answers and confident wrong answers. Even this crude retriever usually cuts hallucinated specifics sharply, and exposes the next problem: keyword overlap misses paraphrases.

### ⚠️ Failure Modes & Debugging
- **The model ignores the sources** and answers from memory: it wasn't trained to use context. Add RAG-style examples to SFT (Ch 37): question + sources → cited answer, including "not in the sources" cases.
- **The answer is in the sources but split across chunk boundaries:** chunking problem (46.2).
- **Prompt injection through documents:** retrieved text is *untrusted data* (Ch 42.4). Keep the instructions in the system message, mark sources clearly as data, and never let retrieved text trigger tools with side effects.

### 🧠 Expert Insight
- **Lewis et al. (2020), "Retrieval-Augmented Generation for Knowledge-Intensive NLP Tasks":** coined RAG (with the marginalization formula above).
- **Guu et al. (2020), REALM** and **Borgeaud et al. (2022), RETRO:** retrieval built into pretraining; RETRO matched a 25× larger model on some benchmarks by retrieving from 2 trillion tokens.
- **Shi et al. (2023), REPLUG** and **Asai et al. (2024), Self-RAG:** treat the LM as a black box, or train it to decide when to retrieve and to critique its own use of sources.
- Long context windows (Ch 32.2) don't make retrieval obsolete: they make it more forgiving (retrieve more, less precisely), but cost grows with context length and models still miss facts buried in the middle of very long contexts.

### ✅ Check Your Instinct
1. Why is RAG better than fine-tuning for fresh or exact facts?
2. What are the two components whose failures you must measure separately?

<details><summary>Answers</summary>

1. Parameters are lossy compressed memory and require retraining to update; retrieved text in context can be copied exactly and updated by re-indexing.
2. The retriever (was the right chunk found?) and the generator (did it use the chunk correctly and faithfully?).
</details>

### 📌 Recap Card
- Parameters = skills + fuzzy knowledge; context = exact, fresh facts.
- Index → retrieve → generate with citations.
- Fine-tune the model to *use* sources; treat sources as untrusted data.

> **Core intuition:** *Don't make the model remember everything. Teach it to look things up and read carefully.*

## 46.2 Embedding Models, Chunking and Vector Search From Scratch

### 🧭 The Problem First
"How do I reset the controller?" should match a passage that says "To restore factory settings on the control unit, hold...", which shares no keywords. We need a notion of similarity based on *meaning*, and a way to search millions of chunks by it in milliseconds.

### 💡 Intuition / Instinct
- **Embeddings:** map each text to a vector so that texts with similar meaning end up close together (Ch 12.2, but for whole passages). A language model's hidden states already encode meaning, but not in a geometry where "question" and "passage that answers it" are close. **Contrastive training** fixes that: pull matching (question, passage) pairs together, push everything else in the batch apart.
- **Chunking:** a whole document is too coarse to embed as one vector (its meaning is an average of many topics), and a single sentence lacks context. Chunks of ~200–500 tokens with a small overlap, split at natural boundaries (headings, paragraphs), are a robust default.
- **Vector search:** exact search is one matrix multiply (queries × all chunk vectors) followed by top-k. It's fine up to ~1M chunks on a GPU. Beyond that, **approximate nearest neighbour (ANN)** indexes trade a little recall for a lot of speed, for example by clustering the vectors (IVF) and only searching the few clusters nearest the query.

### 🖼️ Visual Mental Model

```text
 contrastive batch (B pairs):           similarity matrix S = Q Pᵀ / τ   (B × B)
   q₁ ↔ p₁                                     p₁   p₂   p₃   p₄
   q₂ ↔ p₂                                q₁ [ ██   ░    ░    ░  ]   target: the diagonal
   q₃ ↔ p₃                                q₂ [ ░    ██   ░    ░  ]   cross-entropy per row
   q₄ ↔ p₄                                q₃ [ ░    ░    ██   ░  ]   = "which passage is mine?"
                                          q₄ [ ░    ░    ░    ██ ]

 IVF index:  k-means centroids ●  — each chunk vector lives in its nearest centroid's list
             query ★ → probe the nprobe nearest centroids → exact search inside those lists only
```

### 📐 The Math, Gently
**Embedding:** mean-pool the final hidden states over the non-padding tokens, then L2-normalize: $e(x) = \frac{\bar h}{\|\bar h\|}$. With unit vectors, cosine similarity is the dot product.

**InfoNCE loss** with in-batch negatives, for query embeddings $q_i$ and passage embeddings $p_j$:

$$\mathcal{L} = -\frac{1}{B}\sum_{i=1}^B \log \frac{\exp(q_i\cdot p_i/\tau)}{\sum_{j=1}^B \exp(q_i \cdot p_j/\tau)}$$

This is exactly cross-entropy (Ch 5.5) on the rows of the similarity matrix, with the diagonal as the labels. The temperature τ ≈ 0.02–0.1 sharpens the distribution. Bigger batches mean more negatives and a harder, more informative task. **Hard negatives** (passages that look relevant but aren't, e.g. BM25 hits that don't contain the answer) add more signal still.

**IVF cost:** with N vectors in c clusters, a query compares against c centroids plus ~nprobe·N/c vectors instead of N. With N = 10⁷, c = 4,096 and nprobe = 16, that's ~43,000 comparisons instead of 10 million.

### 🛠️ Build It From Scratch
**Chunking** on paragraph boundaries, with overlap, measured in tokens:

```python
# nanoforge/apps/chunk.py
import re

def chunk_document(text, source, tok, max_tokens=300, overlap_tokens=50):
    """Greedy packing of paragraphs into chunks of <= max_tokens; consecutive chunks share ~overlap_tokens."""
    paras = [p.strip() for p in re.split(r"\n\s*\n", text) if p.strip()]
    pieces = []
    for p in paras:                                          # split paragraphs that are too long on their own
        ids = tok.encode(p)
        for i in range(0, len(ids), max_tokens): pieces.append(tok.decode(ids[i:i + max_tokens]))
    chunks, cur, cur_len = [], [], 0
    for piece in pieces:
        n = len(tok.encode(piece))
        if cur and cur_len + n > max_tokens:
            chunks.append("\n\n".join(cur))
            keep, kept = [], 0                               # carry the tail paragraphs over as overlap
            for q in reversed(cur):
                m = len(tok.encode(q))
                if kept + m > overlap_tokens: break
                keep.insert(0, q); kept += m
            cur, cur_len = keep, kept
        cur.append(piece); cur_len += n
    if cur: chunks.append("\n\n".join(cur))
    return [{"id": f"{source}#{i}", "source": source, "text": c} for i, c in enumerate(chunks)]
```

**Embedding model:** reuse your Llama trunk as an encoder, then train it contrastively.

```python
# nanoforge/apps/embed.py
import torch, torch.nn.functional as F

class Embedder(torch.nn.Module):
    """Mean-pooled, L2-normalized final hidden states of a Llama trunk (Ch 32)."""
    def __init__(self, llama, pad_id):
        super().__init__(); self.m, self.pad_id = llama, pad_id
    def forward(self, ids):                                   # ids: (B, T), right-padded with pad_id
        m = self.m; x = m.tok_emb(ids)
        for layer in m.layers: x = layer(x, m.rope_cos, m.rope_sin)
        h = m.norm(x)                                         # (B, T, C)
        mask = (ids != self.pad_id).unsqueeze(-1).to(h.dtype)
        return F.normalize((h * mask).sum(1) / mask.sum(1).clamp_min(1), dim=-1)   # (B, C)

def pad_batch(seqs, pad_id, max_len):
    seqs = [s[:max_len] for s in seqs]; T = max(len(s) for s in seqs)
    return torch.tensor([s + [pad_id] * (T - len(s)) for s in seqs])

def info_nce(q, p, tau=0.05):
    """q, p: (B, C) unit vectors; row i of p is the positive for row i of q (extra rows of p = hard negatives)."""
    logits = q @ p.T / tau                                    # (B, B + n_hard)
    return F.cross_entropy(logits.float(), torch.arange(q.size(0), device=q.device))

def train_embedder(emb, tok, pairs, pad_id, steps=1000, B=64, lr=2e-5, max_len=256, device="cuda", hard_negs=None):
    """pairs: list of (query, passage) strings, e.g. synthetic questions generated from your chunks (Ch 42.1)."""
    import random
    opt = torch.optim.AdamW(emb.parameters(), lr=lr, weight_decay=0.01)
    emb.train()
    for step in range(steps):
        batch = random.sample(pairs, B)
        q = emb(pad_batch([tok.encode(a) for a, _ in batch], pad_id, max_len).to(device))
        passages = [b for _, b in batch] + ([random.choice(hard_negs) for _ in range(B // 4)] if hard_negs else [])
        p = emb(pad_batch([tok.encode(b) for b in passages], pad_id, max_len).to(device))
        loss = info_nce(q, p)
        opt.zero_grad(); loss.backward(); torch.nn.utils.clip_grad_norm_(emb.parameters(), 1.0); opt.step()
        if step % 100 == 0: print(step, loss.item())
    return emb.eval()

@torch.no_grad()
def embed_texts(emb, tok, texts, pad_id, B=128, max_len=512, device="cuda"):
    out = [emb(pad_batch([tok.encode(t) for t in texts[i:i + B]], pad_id, max_len).to(device)).float().cpu()
           for i in range(0, len(texts), B)]
    return torch.cat(out)                                     # (N, C) unit vectors
```

**Vector search:** exact, plus an IVF index built with k-means.

```python
# nanoforge/apps/vector_index.py
import torch

class FlatIndex:
    def __init__(self, vecs): self.vecs = vecs                # (N, C) unit vectors
    def search(self, q, k=10):                                # q: (Q, C)
        s = q @ self.vecs.T                                   # (Q, N) cosine similarities
        top = s.topk(min(k, s.size(1)), dim=1)
        return top.values, top.indices

def kmeans(x, c, iters=20, seed=0):
    g = torch.Generator().manual_seed(seed)
    cent = x[torch.randperm(x.size(0), generator=g)[:c]].clone()
    for _ in range(iters):
        assign = (x @ cent.T).argmax(1)                       # spherical k-means: nearest by cosine
        for j in range(c):
            members = x[assign == j]
            if len(members): cent[j] = torch.nn.functional.normalize(members.mean(0), dim=0)
    return cent, (x @ cent.T).argmax(1)

class IVFIndex:
    def __init__(self, vecs, n_lists=None, iters=20):
        n_lists = n_lists or max(1, int(vecs.size(0) ** 0.5))
        self.vecs = vecs
        self.cent, assign = kmeans(vecs, n_lists, iters)
        self.lists = [torch.nonzero(assign == j).flatten() for j in range(n_lists)]
    def search(self, q, k=10, nprobe=8):
        vals, idxs = [], []
        near = (q @ self.cent.T).topk(min(nprobe, self.cent.size(0)), dim=1).indices    # (Q, nprobe)
        for qi in range(q.size(0)):
            cand = torch.cat([self.lists[j] for j in near[qi].tolist()])
            s = self.vecs[cand] @ q[qi]
            top = s.topk(min(k, s.numel()))
            vals.append(top.values); idxs.append(cand[top.indices])
        return vals, idxs

def recall_vs_flat(ivf, flat, queries, k=10, nprobe=8):
    """Fraction of the exact top-k that the IVF search also returns."""
    _, exact = flat.search(queries, k); _, approx = ivf.search(queries, k, nprobe)
    return sum(len(set(e.tolist()) & set(a.tolist())) for e, a in zip(exact, approx)) / exact.numel()
```

### 🔬 Experiment & Observe
1. **Training data for free:** for each chunk of your corpus, generate 2–3 questions it answers with a capable model (the grounded generation of Ch 42.1). That gives thousands of (question, chunk) pairs. Hold out 10% of the *chunks* (not just the questions) for evaluation.
2. Measure recall@5 on held-out questions for: (a) the untrained mean-pooled Llama, (b) after InfoNCE training, (c) after adding BM25 hard negatives. The untrained model is usually poor; contrastive training transforms it.
3. Build an IVF index over your chunk embeddings (replicate them with small noise to reach ~100k vectors if your corpus is small) and plot `recall_vs_flat` and query time vs `nprobe`. Recall rises quickly and saturates, while time grows linearly. Then repeat with *random* unit vectors: recall rises much more slowly, because random high-dimensional data has no cluster structure (Ch 3.6). Real embeddings are clustered, which is why IVF works.
4. Sweep chunk size (100, 300, 800 tokens) and measure recall@5 and end-to-end answer accuracy (46.4). Smaller chunks retrieve precisely but lose context; larger chunks do the opposite.

### ⚠️ Failure Modes & Debugging
- **Embedding queries and passages with different preprocessing** (e.g. a prefix like "query: " on one side only at inference): if you train with prefixes, use them consistently.
- **Not normalizing vectors:** dot products then favour long passages with large norms.
- **Duplicate chunks in a batch** (the same passage for two queries) create false negatives in InfoNCE; dedupe within each batch.
- **Stale index:** documents change but vectors don't. Re-embed on update, and store the model version with the index: vectors from different embedding models are not comparable.
- **Chunk boundaries cutting tables or code:** use structure-aware splitting for these (Ch 23.5).

### 🧠 Expert Insight
- **Karpukhin et al. (2020), DPR:** dual encoders trained with in-batch negatives beat BM25 on open-domain QA.
- **Oord et al. (2018), InfoNCE;** **Wang et al. (2022), E5** and **Xiao et al. (2023), BGE:** large-scale weakly supervised contrastive pretraining followed by fine-tuning; the recipe behind most open embedding models. Decoder-LLM-based embedders (e.g. E5-Mistral, 2024) now lead many benchmarks.
- **Kusupati et al. (2022), Matryoshka embeddings:** train so that prefixes of the vector are themselves good embeddings, letting you truncate vectors for speed.
- **ANN libraries:** FAISS (IVF, PQ, HNSW), HNSW graphs (Malkov & Yashunin, 2018) and ScaNN. Product quantization (PQ) compresses vectors ~10–30× for billion-scale search.

### 📌 Recap Card
- Chunk ~200–500 tokens on natural boundaries with overlap.
- Embedder = mean-pool + normalize, trained with InfoNCE (in-batch + hard negatives).
- Exact search = one matmul + top-k; IVF = cluster, probe a few lists.
- Keep the index versioned with the embedding model.

> **Core intuition:** *Train the geometry so that a question lands next to its answer, then search the neighbourhood.*

## 46.3 Hybrid Retrieval (BM25 + Dense) and Reranking

### 🧭 The Problem First
Your dense retriever handles paraphrases well, then fails on "error code E-4012" or a person's surname: exact identifiers that the embedding blurs into "some error code". BM25 nails those but misses paraphrases. And both return the right chunk at rank 7 when you only pass the top 3 to the model.

### 💡 Intuition / Instinct
- **Lexical (BM25)** and **semantic (dense)** retrieval make *different* mistakes, so combining them catches more than either alone.
- **Fusion:** scores from different retrievers aren't comparable (BM25 scores are unbounded, cosines are in [−1, 1]), but *ranks* are. **Reciprocal Rank Fusion (RRF)** just adds 1/(k + rank) from each list.
- **Reranking:** retrieval must be fast, so it encodes the query and passage *separately* (a bi-encoder) and compares vectors. A **cross-encoder** reads the query and passage *together*, so attention can compare them word by word. It's much more accurate but too slow for millions of passages, so use it only on the top ~50 candidates. Retrieve wide and cheap, then rerank narrow and expensive.

### 🖼️ Visual Mental Model

```text
 query ─┬─ BM25 top-50 ──┐
        └─ dense top-50 ─┴─ RRF fuse ─▶ top-50 ─▶ cross-encoder / LLM reranker ─▶ top-5 ─▶ generator
            cheap, recall-oriented                  expensive, precision-oriented
```

### 📐 The Math, Gently
**BM25** score of document d for query terms $q_1..q_n$:

$$\text{BM25}(d, q) = \sum_{i} \text{IDF}(q_i)\cdot \frac{f(q_i, d)\,(k_1 + 1)}{f(q_i, d) + k_1\left(1 - b + b\,\frac{|d|}{\text{avgdl}}\right)}, \qquad \text{IDF}(t) = \ln\!\left(1 + \frac{N - n_t + 0.5}{n_t + 0.5}\right)$$

where f is the term frequency in d, $n_t$ the number of documents containing t, and N the number of documents. Term frequency saturates (controlled by $k_1 \approx 1.2$), and long documents are penalized (controlled by $b \approx 0.75$). Rare terms have high IDF, which is exactly why BM25 is good at identifiers.

**RRF:** $\text{score}(d) = \sum_{r \in \text{retrievers}} \frac{1}{k + \text{rank}_r(d)}$ with k = 60. A document ranked 1st by one retriever and absent from another still scores well; one ranked 5th by both scores better.

**LLM as a pointwise reranker:** score = $\log p(\text{"Yes"}) - \log p(\text{"No"})$ for a prompt "Does this passage answer the question? Answer Yes or No." This turns any instruction-tuned model into a cross-encoder without extra training (a trained cross-encoder is better and faster).

### 🛠️ Build It From Scratch

```python
# nanoforge/apps/bm25.py
import math, re
from collections import Counter, defaultdict

def tokenize_words(text): return re.findall(r"\w+", text.lower())

class BM25:
    def __init__(self, docs, k1=1.2, b=0.75):
        self.k1, self.b = k1, b
        self.tf = [Counter(tokenize_words(d)) for d in docs]
        self.len = [sum(t.values()) for t in self.tf]
        self.avgdl = sum(self.len) / max(1, len(docs))
        df = Counter(w for t in self.tf for w in t)
        N = len(docs)
        self.idf = {w: math.log(1 + (N - n + 0.5) / (n + 0.5)) for w, n in df.items()}
        self.postings = defaultdict(list)                    # word -> docs containing it (inverted index)
        for i, t in enumerate(self.tf):
            for w in t: self.postings[w].append(i)
    def search(self, query, k=10):
        scores = defaultdict(float)
        for w in set(tokenize_words(query)):
            idf = self.idf.get(w)
            if idf is None: continue
            for i in self.postings[w]:                       # only documents that contain the word
                f = self.tf[i][w]
                scores[i] += idf * f * (self.k1 + 1) / (f + self.k1 * (1 - self.b + self.b * self.len[i] / self.avgdl))
        return sorted(scores.items(), key=lambda x: -x[1])[:k]   # [(doc_idx, score)]
```

```python
# nanoforge/apps/hybrid.py
import torch

def rrf(rankings, k=60, top=None):
    """rankings: list of ranked lists of doc ids. Returns fused [(doc_id, score)] best first."""
    scores = {}
    for ranked in rankings:
        for rank, d in enumerate(ranked):
            scores[d] = scores.get(d, 0.0) + 1.0 / (k + rank + 1)
    fused = sorted(scores.items(), key=lambda x: -x[1])
    return fused[:top] if top else fused

class HybridRetriever:
    def __init__(self, chunks, bm25, index, embed_query_fn):
        self.chunks, self.bm25, self.index, self.embed_q = chunks, bm25, index, embed_query_fn
    def __call__(self, question, k=5, wide=50, reranker=None):
        lex = [i for i, _ in self.bm25.search(question, wide)]
        _, dense = self.index.search(self.embed_q(question)[None], wide)
        dense = dense[0].tolist()                             # Flat and IVF both return per-query rows
        fused = [i for i, _ in rrf([lex, dense], top=wide)]
        cands = [self.chunks[i] for i in fused]
        if reranker is not None: cands = reranker(question, cands)
        return cands[:k]

RERANK_PROMPT = "Passage:\n{p}\n\nQuestion: {q}\n\nDoes the passage contain the answer to the question? Answer Yes or No."

@torch.no_grad()
def make_llm_reranker(model, tok, chat, yes_id, no_id, device="cuda", max_passage_tokens=400):
    """Pointwise LLM reranker: score = logit(Yes) - logit(No) at the first answer position."""
    def rerank(question, cands):
        scores = []
        for c in cands:
            p = tok.decode(tok.encode(c["text"])[:max_passage_tokens])
            ids = chat.prompt_for_generation([{"role": "user", "content": RERANK_PROMPT.format(p=p, q=question)}])
            logits, _ = model(torch.tensor([ids], device=device))
            l = logits[0, -1].float()
            scores.append((l[yes_id] - l[no_id]).item())
        order = sorted(range(len(cands)), key=lambda i: -scores[i])
        return [cands[i] for i in order]
    return rerank
```

(`yes_id`/`no_id` are the token ids of "Yes" and "No" as the first token of an assistant reply; check how your tokenizer splits them. Batch the reranker calls on a real deployment: 50 candidates is 50 prefills.)

### 🔬 Experiment & Observe
On your held-out question set, report recall@5 and MRR for: BM25 alone, dense alone, RRF hybrid, and hybrid + reranking. Then split the questions into "contains an identifier/number/name" vs "paraphrased", and report each subset. Typically BM25 wins the first subset, dense the second, and hybrid + rerank beats both overall.

### ⚠️ Failure Modes & Debugging
- **Fusing raw scores** (e.g. BM25 score + cosine): one retriever dominates by scale. Use RRF or normalize carefully.
- **Reranking too few candidates:** if the right chunk isn't in the fused top-50, the reranker can't save it. Check recall@50 of the first stage.
- **Reranker position bias / length bias:** LLM rerankers can favour longer passages; truncate consistently.
- **BM25 tokenization mismatch:** "E-4012" tokenizes to "e" and "4012". Test your identifiers and adjust the word regex.

### 🧠 Expert Insight
- **Robertson & Zaragoza (2009), "The Probabilistic Relevance Framework: BM25 and Beyond".** BM25 remains a strong baseline and was hard to beat on out-of-domain benchmarks (BEIR, Thakur et al., 2021).
- **Cormack et al. (2009), RRF:** simple, robust, parameter-light.
- **Nogueira & Cho (2019), BERT cross-encoder reranking;** **Khattab & Zaharia (2020), ColBERT:** late interaction (per-token vectors) sits between bi- and cross-encoders in cost and accuracy.
- **Sun et al. (2023), RankGPT:** listwise reranking with LLMs.
- **Contextual retrieval:** prepending a short, LLM-generated description of each chunk's place in its document (e.g. "From the 2024 maintenance manual, section on hydraulics:") before embedding and BM25 indexing measurably reduces retrieval failures.

### ✅ Check Your Instinct
1. Why does BM25 beat dense retrieval on rare identifiers?
2. Why fuse ranks rather than scores?
3. Why is a cross-encoder more accurate than a bi-encoder, and why can't it replace it?

<details><summary>Answers</summary>

1. Rare terms get high IDF and must match exactly, while a dense embedding compresses the passage's meaning and blurs exact strings.
2. Scores from different retrievers live on different, uncalibrated scales; ranks are comparable.
3. It attends across query and passage jointly, but it must run once per (query, passage) pair, so it's far too slow to apply to the whole corpus.
</details>

### 📌 Recap Card
- BM25 (exact terms) + dense (meaning) → RRF fusion.
- Retrieve wide and cheap (top-50), rerank narrow and expensive (top-5).
- Check first-stage recall@50 before blaming the reranker.

> **Core intuition:** *Two retrievers that fail differently are better than one that fails consistently; a careful reader then picks the best few.*

## 46.4 Evaluating RAG

### 🧭 The Problem First
A user reports a wrong answer. Was the right chunk never retrieved? Retrieved but ranked too low? In the prompt but ignored? Or used, but the model added an unsupported claim? Without component-level metrics, every fix is a guess.

### 💡 Intuition / Instinct
Evaluate the pipeline at three levels, on a fixed labelled set of questions:
1. **Retrieval:** is a relevant chunk in the top-k? (recall@k, MRR). This needs "gold" chunk labels, which you get for free if the questions were generated from specific chunks (46.2).
2. **Grounding (faithfulness):** is every claim in the answer supported by the retrieved sources? A judge model checks claims against the context (Ch 36.2).
3. **Answer quality:** is the answer correct (vs a reference answer) and does it address the question? Also: does the system *abstain* when the answer isn't in the corpus?

The diagnostic power comes from the combinations: low recall → fix retrieval; high recall but low correctness → fix the generator (prompting, SFT on RAG data); correct but unfaithful → the model is answering from memory, which is dangerous when the memory is wrong.

### 🖼️ Visual Mental Model

```text
 question ──▶ retrieved chunks ──▶ answer
               │                    │
        recall@k, MRR        faithfulness (answer ⊆ chunks?)
        (vs gold chunk)      correctness (answer ≈ reference?)
                             abstention on unanswerable questions

 diagnosis:  recall low ─▶ retriever | recall ok, correctness low ─▶ generator | unfaithful ─▶ grounding training
```

### 📐 The Math, Gently
**Recall@k** $= \frac{1}{|Q|}\sum_q \mathbb{1}[\text{gold}(q) \in \text{top}_k(q)]$.
**MRR** $= \frac{1}{|Q|}\sum_q \frac{1}{\text{rank of first gold chunk}}$ (0 if absent).
**Faithfulness** = supported claims / total claims, averaged over answers.
**Abstention:** on unanswerable questions, the fraction where the model says it doesn't know (want high); on answerable ones, the fraction where it wrongly abstains (want low). It's the same two-sided measurement as refusals vs over-refusals (Ch 42.3).

Report all of these with confidence intervals (Ch 35.5); RAG eval sets are usually small (100–500 questions), so differences of a few points are often noise.

### 🛠️ Build It From Scratch

```python
# nanoforge/eval/rag_eval.py
import json

def retrieval_metrics(results, ks=(1, 5, 20)):
    """results: list of {"gold": set of chunk ids, "retrieved": [chunk ids in rank order]}."""
    out = {f"recall@{k}": 0.0 for k in ks}; mrr = 0.0
    for r in results:
        for k in ks: out[f"recall@{k}"] += bool(r["gold"] & set(r["retrieved"][:k]))
        rank = next((i + 1 for i, c in enumerate(r["retrieved"]) if c in r["gold"]), None)
        mrr += 1 / rank if rank else 0.0
    n = max(1, len(results))
    return {**{k: v / n for k, v in out.items()}, "mrr": mrr / n}

CLAIMS_PROMPT = "Split the answer into short, independent factual claims. Return a JSON list of strings.\n\nAnswer: {a}"
SUPPORT_PROMPT = "Sources:\n{ctx}\n\nClaim: {c}\n\nIs the claim fully supported by the sources? Answer SUPPORTED or UNSUPPORTED."
CORRECT_PROMPT = ("Question: {q}\nReference answer: {ref}\nCandidate answer: {a}\n\n"
                  "Does the candidate convey the same answer as the reference (wording may differ)? Answer YES or NO.")
ABSTAIN_MARKERS = ("don't know", "do not know", "not in the sources", "cannot find", "no information")

def faithfulness(judge_fn, answer, retrieved):
    try: claims = json.loads(judge_fn(CLAIMS_PROMPT.format(a=answer)))
    except (json.JSONDecodeError, TypeError): return None
    if not claims: return None
    ctx = "\n\n".join(f"[{i + 1}] {c['text']}" for i, c in enumerate(retrieved))
    ok = [judge_fn(SUPPORT_PROMPT.format(ctx=ctx, c=c)).strip().upper().startswith("SUPPORTED") for c in claims]
    return sum(ok) / len(ok)

def evaluate_rag(items, retriever, answer_fn, judge_fn, k=5):
    """items: {"question", "gold_chunks": [...], "reference": str or None (None = unanswerable)}.
    retriever(question, k) -> chunks; answer_fn(question, chunks) -> str."""
    ret, rows = [], []
    for it in items:
        chunks = retriever(it["question"], k=20)
        ret.append({"gold": set(it["gold_chunks"]), "retrieved": [c["id"] for c in chunks]})
        answer = answer_fn(it["question"], chunks[:k])
        abstained = any(m in answer.lower() for m in ABSTAIN_MARKERS)
        row = {"question": it["question"], "answer": answer, "abstained": abstained,
               "answerable": it["reference"] is not None}
        if it["reference"] is not None and not abstained:
            row["correct"] = judge_fn(CORRECT_PROMPT.format(q=it["question"], ref=it["reference"], a=answer)).strip().upper().startswith("YES")
            row["faithfulness"] = faithfulness(judge_fn, answer, chunks[:k])
        rows.append(row)
    ans = [r for r in rows if r["answerable"]]; unans = [r for r in rows if not r["answerable"]]
    faith = [r["faithfulness"] for r in ans if r.get("faithfulness") is not None]
    return {**retrieval_metrics([r for r, it in zip(ret, items) if it["reference"] is not None]),
            "correct": sum(r.get("correct", False) for r in ans) / max(1, len(ans)),
            "faithfulness": sum(faith) / max(1, len(faith)),
            "wrong_abstention": sum(r["abstained"] for r in ans) / max(1, len(ans)),
            "correct_abstention": sum(r["abstained"] for r in unans) / max(1, len(unans)),
            "rows": rows}
```

Build the eval set from three sources: questions generated from held-out chunks (with gold chunk ids and reference answers), a few dozen **real** user-style questions you label by hand, and ~15% **unanswerable** questions that sound plausible for your domain but aren't covered by the corpus.

### 🔬 Experiment & Observe
Run `evaluate_rag` on four configurations and fill in the table:

| Config | recall@5 | correct | faithful | wrong abstain | correct abstain |
|---|---|---|---|---|---|
| closed-book (no retrieval) | — | | | | |
| BM25, k = 5 | | | | | |
| hybrid + rerank, k = 5 | | | | | |
| hybrid + rerank + RAG-SFT model | | | | | |

"RAG-SFT" means fine-tuning your model (Ch 37–38, LoRA is enough) on (sources + question → cited answer) examples, including unanswerable ones with "I don't know". It usually improves faithfulness and abstention more than any retrieval change.

### ⚠️ Failure Modes & Debugging
- **Judging with the same model that generated the answers:** self-preference inflates scores (Ch 36.2). Use a stronger or different judge and spot-check 50 judgements by hand.
- **Abstention detection by keywords is brittle:** instruct the model to use a fixed phrase for "not in the sources" during RAG-SFT, then detect that phrase.
- **An eval set generated from the same chunks the embedder was trained on:** retrieval looks perfect. Use held-out chunks.
- **Only measuring end-to-end accuracy:** you can't tell which component to fix.

### 🧠 Expert Insight
- **Es et al. (2024), RAGAS:** reference-free metrics (faithfulness, answer relevance, context precision/recall) with LLM judges; the claim-decomposition approach above follows the same idea.
- **Liu et al. (2024), "Lost in the Middle":** models use information at the start and end of the context better than in the middle. Put the best-ranked chunks first (or first and last).
- **Min et al. (2023), FActScore:** atomic-claim verification for measuring factual precision.
- **Attributed QA / citation evaluation:** check that each cited source actually supports the sentence citing it, not just that the answer is supported somewhere.

### ✅ Check Your Instinct
1. Recall@5 is 0.92 but correctness is 0.55. Where do you look first?
2. Why include unanswerable questions?

<details><summary>Answers</summary>

1. The generator: the right chunks are usually in context, but the model isn't using them well (prompting, chunk ordering, RAG-specific fine-tuning).
2. To measure whether the system abstains instead of hallucinating when the corpus lacks the answer; without them, a model that always answers confidently looks good.
</details>

### 📌 Recap Card
- Measure retrieval (recall@k, MRR), grounding (faithfulness) and answers (correctness, abstention) separately.
- Gold chunks from generated questions; add real and unanswerable questions.
- Different judge model; hand-check; confidence intervals.

> **Core intuition:** *A RAG system is a pipeline; measure each stage, or you'll fix the wrong one.*
