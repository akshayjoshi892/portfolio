## 1.1 An LLM Is a Compression Machine: "Predict the Next Token" Is the Whole Idea

### 🧭 The Problem First

Suppose you want a computer that can answer questions, write code, translate, summarize and chat. The classic approach is to write a separate program for each skill: a translator, a summarizer, a Q&A system. Each needs hand-labelled data and hand-designed rules. This approach failed for fifty years because language is too big, too messy and too interconnected to split into neat tasks.

The question is: **is there one simple task that, if solved well enough, forces the solver to learn all of these skills at once?**

### 💡 Intuition / Instinct

Yes: **guess the next word.**

Imagine a friend reading a mystery novel aloud who stops mid-sentence: *"...and the detective finally revealed that the murderer was ___."* To guess well, you need grammar, vocabulary, the plot, the characters, the author's style, and even some psychology. The *better* you are at guessing the next word, the *more* you must understand.

That is the entire secret of LLMs. We never teach them translation or arithmetic directly. We give them trillions of words and one instruction: **"predict what comes next."** To lower their error, they are *forced* to build internal models of grammar, facts, reasoning and style, because those models make predictions better.

The second instinct is **prediction = compression.** If you can predict the next word perfectly, you do not need to store it: you just regenerate it. A model that predicts well has squeezed the regularities of text into its parameters. An LLM is a lossy, compressed, *queryable* copy of the patterns in its training data.

> **Intuition:** An LLM is not a database of sentences. It is a *compressed theory of text*: the set of rules and regularities that make text predictable.

### 🖼️ Visual Mental Model

```text
     "The cat sat on the"
              │
              ▼
   ┌─────────────────────┐
   │     LLM  f(θ)       │   θ = billions of numbers (parameters)
   └─────────────────────┘
              │
              ▼
   probability over every possible next token:
      mat   ████████████  0.41
      floor ██████        0.18
      sofa  ████          0.11
      roof  ██            0.05
      ...   (50,000 more tokens with small probabilities)
```

Generation is just a loop around this box:

```text
text → [predict] → pick a token → append it → [predict] → pick → append → ...
```

### 📐 The Math, Gently

A piece of text is a sequence of tokens $x_1, x_2, \dots, x_T$ (for now, think "token ≈ word piece"). The **chain rule of probability** says any joint probability can be factored into next-step conditionals:

$$
P(x_1, x_2, \dots, x_T) = P(x_1)\,P(x_2 \mid x_1)\,P(x_3 \mid x_1, x_2)\cdots = \prod_{t=1}^{T} P(x_t \mid x_{<t})
$$

This is not an approximation. It is an exact identity. So if a model $P_\theta(x_t \mid x_{<t})$ can predict the next token given the past, it defines a probability for *every possible text*. The model is trained to make real text likely, by minimizing the average **negative log-likelihood**:

$$
\mathcal{L}(\theta) = -\frac{1}{T}\sum_{t=1}^{T} \log P_\theta(x_t \mid x_{<t})
$$

**Tiny worked example.** Take the text "a b a" and a model that assigns:
- $P(x_1 = a) = 0.5$
- $P(x_2 = b \mid a) = 0.25$
- $P(x_3 = a \mid a, b) = 0.8$

Joint probability $= 0.5 \times 0.25 \times 0.8 = 0.1$.
Loss $= -\frac{1}{3}(\ln 0.5 + \ln 0.25 + \ln 0.8) = -\frac{1}{3}(-0.693 - 1.386 - 0.223) = 0.767$ nats.

A perfect model would give each true token probability 1, so the loss would be 0. A model that guesses uniformly over 3 symbols gets $\ln 3 = 1.099$. Our model beats random guessing but is far from perfect. **Training = pushing that number down.**

### 🛠️ Build It From Scratch

```python
# ch01_chain_rule.py : compute the probability and loss of a text under a toy "model"
import math

# A toy model: a dictionary mapping context (tuple of previous tokens) -> distribution over next token
toy_model = {
    ():          {"a": 0.5, "b": 0.3, "c": 0.2},
    ("a",):      {"a": 0.25, "b": 0.25, "c": 0.5},
    ("a", "b"):  {"a": 0.8, "b": 0.1, "c": 0.1},
}

def sequence_logprob(tokens, model):
    """Sum of log P(x_t | x_<t) over the sequence (chain rule)."""
    total = 0.0
    for t, tok in enumerate(tokens):
        context = tuple(tokens[:t])            # everything before position t
        p = model[context][tok]                # model's probability of the true next token
        print(f"P({tok!r} | {context}) = {p}")
        total += math.log(p)
    return total

tokens = ["a", "b", "a"]
lp = sequence_logprob(tokens, toy_model)
print(f"joint probability = {math.exp(lp):.4f}")          # 0.1000
print(f"loss (avg NLL)    = {-lp / len(tokens):.4f} nats") # 0.7675
```

### 🔬 Experiment & Observe

1. Change `P("a" | ("a","b"))` from 0.8 to 0.99. **Predict** before running: the loss should drop. (It becomes ≈ 0.695.)
2. Change it to 0.01. The loss explodes (≈ 2.23), because $-\ln(0.01) = 4.6$. **Lesson:** a confident wrong prediction is punished far more than a hesitant one.
3. Make every distribution uniform (1/3 each). The loss becomes exactly $\ln 3 ≈ 1.0986$. This is the "know-nothing" baseline. Remember this idea: **a fresh LLM starts at about $\ln(\text{vocab size})$.**

### ⚠️ Failure Modes & Debugging

- **Probability 0 → `math.log(0)` raises a ValueError** (or gives `-inf` in NumPy). Real models avoid this because softmax never outputs exactly 0. When you count frequencies (Ch 11), you need *smoothing*.
- **Forgetting to average.** Summing gives a loss that grows with length, so you cannot compare texts of different lengths. Always report the *per-token* loss.
- **Mixing log bases.** `math.log` is natural log (nats). `math.log2` gives bits. 1 nat = 1.4427 bits. Papers use both, so always check.

### 🧠 Expert Insight

- **Shannon (1948), "A Mathematical Theory of Communication":** introduced modelling English as a sequence of predictions, and showed humans could guess next letters with surprisingly low entropy.
- **Bengio et al. (2003), "A Neural Probabilistic Language Model":** replaced counting with neural networks.
- **Radford et al. (2019), GPT-2, "Language Models are Unsupervised Multitask Learners":** showed that next-token prediction alone yields translation, summarization and Q&A with no task-specific training.
- **Delétang et al. (2023), "Language Modeling Is Compression":** made the compression view rigorous; a large LM compresses images and audio better than PNG/FLAC when used with arithmetic coding.

Frontier labs still train with *exactly* this loss during pretraining. Everything else (RLHF, reasoning, tool use) is built on top.

<details><summary>Answers</summary>

2. $\ln(50000) ≈ 10.82$ nats.

### 📌 Recap Card
- An LLM models $P(\text{next token} \mid \text{previous tokens})$.
- The chain rule makes this an exact model of whole texts.
- Training minimizes average negative log-likelihood (cross-entropy).
- Uniform guessing gives loss $\ln V$; perfect prediction gives 0.
- Confident mistakes are punished heavily.
- Good prediction requires understanding, so understanding *emerges*.

> **Core intuition:** *To predict text well, you must model the world that produced it.*

## 1.2 The Full Lifecycle Map: Data → Tokenizer → Pretrain → Post-train → Inference

### 🧭 The Problem First

Beginners often think "training an LLM" is one step. Then they meet words like *tokenizer*, *SFT*, *RLHF*, *KV cache* and *quantization*, and have no idea where each one fits. Without a pipeline map, you cannot debug: is my chatbot bad because of the data, the architecture, the fine-tuning, or the decoding?

### 💡 Intuition / Instinct

Think of raising a professional:

| Stage | Human analogy | LLM stage |
|---|---|---|
| Gather books | Build a library | **Data collection & cleaning** |
| Learn the alphabet | Decide the units of reading | **Tokenizer training** |
| Read everything for years | General education | **Pretraining** (next-token prediction on trillions of tokens) |
| Job training | Learn to follow instructions | **SFT** (supervised fine-tuning) |
| Feedback from a mentor | Learn what people prefer | **Preference tuning** (RLHF, DPO, GRPO) |
| Working efficiently | Speaking fluently, fast | **Inference optimization** (KV cache, quantization, batching) |
| Being hired | Serving clients | **Deployment** |

Pretraining gives *knowledge and capability*. Post-training gives *behaviour and format*. Inference engineering gives *speed and cost*.

### 🖼️ Visual Mental Model

```text
 ┌──────────┐   ┌───────────┐   ┌────────────┐   ┌──────────────┐   ┌────────────┐
 │ Raw data │──▶│ Tokenizer │──▶│ Pretraining│──▶│ Post-training│──▶│ Inference  │
 │ (TBs of  │   │ text→ids  │   │ base model │   │ SFT → RLHF/  │   │ quantize,  │
 │  text)   │   │ (BPE)     │   │ "document  │   │ DPO → chat   │   │ KV cache,  │
 │ clean,   │   │           │   │ completer" │   │ assistant    │   │ serve      │
 │ dedup    │   │ Part 3    │   │ Parts 4,6,7│   │ Part 10      │   │ Part 11    │
 │ Part 5   │   └───────────┘   └────────────┘   └──────────────┘   └────────────┘
 └──────────┘                        ▲                   │
                                     └──── Evaluation (Part 9) at every stage
```

### 📐 The Math, Gently

The compute cost of each stage is wildly different. A useful rule (derived in Ch 26): training FLOPs ≈ $6 \times N \times D$, where $N$ is the number of parameters and $D$ the number of training tokens.

Worked example, a 7B model:
- Pretraining on 2T tokens: $6 × 7×10^9 × 2×10^{12} = 8.4×10^{22}$ FLOPs.
- SFT on 100M tokens: $6 × 7×10^9 × 10^8 = 4.2×10^{18}$ FLOPs, which is **20,000× cheaper**.

That is why pretraining is done rarely, by big labs, while fine-tuning is something *you* can do on one GPU.

### 🛠️ Build It From Scratch

A skeleton of the pipeline, with every stage as a stub you will fill in over the book:

```python
# ch01_pipeline_map.py : the whole book as function stubs
def collect_and_clean(raw_texts):            # Part 5
    return [t.strip() for t in raw_texts if len(t.strip()) > 0]

def train_tokenizer(texts):                  # Part 3 (for now: characters)
    vocab = sorted(set("".join(texts)))
    stoi = {ch: i for i, ch in enumerate(vocab)}
    itos = {i: ch for ch, i in stoi.items()}
    return stoi, itos

def pretrain(ids):                           # Parts 4, 6, 7 (for now: bigram counts)
    counts = {}
    for a, b in zip(ids, ids[1:]):
        counts.setdefault(a, {}).setdefault(b, 0)
        counts[a][b] += 1
    return counts

def post_train(model):                       # Part 10 (identity for now)
    return model

def infer(model, start_id, n, itos):         # Part 11 (greedy for now)
    out, cur = [start_id], start_id
    for _ in range(n):
        nxt = model.get(cur)
        if not nxt: break
        cur = max(nxt, key=nxt.get)          # pick the most frequent follower
        out.append(cur)
    return "".join(itos[i] for i in out)

texts = collect_and_clean(["hello world ", "  hello there  ", ""])
stoi, itos = train_tokenizer(texts)
ids = [stoi[c] for c in " ".join(texts)]
model = post_train(pretrain(ids))
print(infer(model, stoi["h"], 10, itos))
```

### 🔬 Experiment & Observe
- Add more texts and watch the greedy output change.
- Notice that greedy decoding loops (`"hello hello hello"`-style). You will fix this with sampling in Ch 13.

### ⚠️ Failure Modes & Debugging
- **Blaming the wrong stage.** A model that answers in the wrong *format* is a post-training problem. A model that doesn't *know* facts is a pretraining/data problem. A model that is *slow* is an inference problem.
- **Train/inference mismatch.** Using a different tokenizer at inference than at training time gives garbage. It is the #1 bug in custom pipelines.

### 🧠 Expert Insight
- **Ouyang et al. (2022), InstructGPT:** established the pretrain → SFT → RLHF recipe.
- **Touvron et al. (2023), Llama 2:** documented the full modern pipeline openly.
- Modern frontier pipelines add *mid-training* (continued pretraining on high-quality/long-context data) and large-scale RL for reasoning (Ch 41).

### ✅ Check Your Instinct
1. Your model writes fluent text but never follows instructions. Which stage do you fix?
2. Why is SFT so much cheaper than pretraining?
3. *(Coding)* Make `infer` stop when it hits a space character.

**Predict before you run:** what happens to `infer` if the start character only appears at the end of the training text?

<details><summary>Answers</summary>

1. Post-training (SFT).
2. It uses far fewer tokens; compute scales with $N \times D$.
3. Add `if itos[cur] == " ": break`.

Predict: it has no recorded followers, so `model.get(cur)` is `None` and generation stops immediately.
</details>

### 📌 Recap Card
- Pipeline: data → tokenizer → pretrain → post-train → inference, with evaluation throughout.
- Pretraining = knowledge; post-training = behaviour; inference = speed and cost.
- Compute ≈ $6ND$; pretraining dominates cost.
- Always diagnose *which stage* a problem comes from.

> **Core intuition:** *Every LLM technique improves one arrow in one pipeline.*

## 1.3 What Parameters, Training and Inference Physically Are

### 🧭 The Problem First

"The model has 7 billion parameters" sounds abstract. But you will soon need to answer questions like *"will this fit on my GPU?"* and *"why is generation slow?"*. For that, you need a physical picture.

### 💡 Intuition / Instinct

A **parameter** is just one floating-point number stored in memory. A model is a *very long list of numbers* plus a *fixed recipe* (the architecture) for combining them with the input.

- **Inference** = run the recipe: multiply inputs by those numbers, many times.
- **Training** = run the recipe, measure the error, compute which direction to nudge *each* number (the gradient), and nudge them all a tiny bit. Repeat millions of times.

Picture a giant mixing desk with billions of knobs. Training is an automated engineer who, after each song, nudges every knob slightly in the direction that makes the song sound better.

### 🖼️ Visual Mental Model

```text
 GPU memory during TRAINING (per parameter, mixed precision with Adam):
 ┌──────────┬──────────┬──────────────┬───────────────┬───────────────┐
 │ weight   │ gradient │ fp32 master  │ Adam moment m │ Adam moment v │
 │ 2 bytes  │ 2 bytes  │ 4 bytes      │ 4 bytes       │ 4 bytes       │
 └──────────┴──────────┴──────────────┴───────────────┴───────────────┘
   ≈ 16 bytes / parameter  (+ activations)

 GPU memory during INFERENCE:
 ┌──────────┐
 │ weight   │  2 bytes (bf16), 1 byte (int8), 0.5 byte (int4) + KV cache
 └──────────┘
```

### 📐 The Math, Gently

Memory for weights = (number of parameters) × (bytes per parameter).

| Model | Params | bf16 inference | int4 inference | Adam training (~16 B/param) |
|---|---|---|---|---|
| GPT-2 small | 124M | 0.25 GB | 0.06 GB | 2 GB |
| 7B | 7×10⁹ | 14 GB | 3.5 GB | 112 GB |
| 70B | 7×10¹⁰ | 140 GB | 35 GB | 1.1 TB |

Worked example: can you *fine-tune* a 1B model fully on a 24 GB GPU? $10^9 × 16 = 16$ GB for states, plus activations, so it is tight but feasible. A 7B model? 112 GB, so no. That is why LoRA exists (Ch 38).

### 🛠️ Build It From Scratch

```python
# ch01_params.py : count parameters and bytes of a tiny network, by hand and with PyTorch
import torch
import torch.nn as nn

model = nn.Sequential(
    nn.Linear(16, 32),   # weights 16*32 + bias 32 = 544
    nn.ReLU(),
    nn.Linear(32, 4),    # weights 32*4 + bias 4   = 132
)
n_params = sum(p.numel() for p in model.parameters())
print("params:", n_params)                                   # 676
print("bytes fp32:", n_params * 4, "| bf16:", n_params * 2)

for name, p in model.named_parameters():
    print(f"{name:10s} shape={tuple(p.shape)} dtype={p.dtype}")

def gb(n_params, bytes_per_param):
    return n_params * bytes_per_param / 1e9
for n in [124e6, 7e9, 70e9]:
    print(f"{n/1e9:6.2f}B  infer-bf16 {gb(n,2):7.1f} GB | train-adam {gb(n,16):8.1f} GB")
```

### 🔬 Experiment & Observe
- Change the hidden size 32 → 64 and **predict** the new count first: $16·64+64+64·4+4 = 1348$.
- Notice that parameters scale roughly with (width)². Doubling width ≈ quadruples the params of the hidden layers.

### ⚠️ Failure Modes & Debugging
- **CUDA out of memory** during training when inference worked fine: training needs about 8× more memory than bf16 inference, before counting activations.
- **Confusing "B" (billion params) with "GB".** A 7B model is 14 GB in bf16, not 7 GB.

### 🧠 Expert Insight
- **Rajbhandari et al. (2020), ZeRO:** introduced the 16-bytes-per-parameter accounting and how to shard it across GPUs (Ch 31).
- **Dettmers et al. (2023), QLoRA:** fine-tunes a 65B model on one 48 GB GPU by quantizing weights to 4 bits (Ch 38).

### 📌 Recap Card
- Parameter = one number; model = numbers + recipe.
- Inference: bytes ≈ params × 2 (bf16).
- Training with Adam: ≈ 16 bytes/param + activations.
- Memory, not FLOPs, is usually your first wall.

> **Core intuition:** *An LLM is a file of numbers; every engineering question is about moving and multiplying those numbers.*

## 1.4 A 60-Line Toy That Learns to Autocomplete

### 🧭 The Problem First

Theory without a running model feels hollow. Before we build each piece carefully, let's see the *whole* loop (data → tokens → model → loss → gradient → update → generate) work once, so later chapters feel like "zooming in", not "wandering".

### 💡 Intuition / Instinct

We will build the smallest real neural language model: a **bigram** model that looks at one character and predicts the next. It is a table of learnable scores: for each character, a row of scores for what comes next. Training nudges the scores so real next characters get higher probability. Tiny, but it has *every* ingredient of GPT: embedding lookup, logits, softmax, cross-entropy, backprop, optimizer, sampling.

### 🖼️ Visual Mental Model

```text
 input char id ──▶ [ table W : (V, V) ] ──▶ row of V logits ──▶ softmax ──▶ probs
    (B,)                                          (B, V)                     (B, V)
                                                    │
                        cross-entropy vs true next char ──▶ loss ──▶ backward ──▶ update W
```

### 📐 The Math, Gently

For current character $i$, the logits are row $W_i \in \mathbb{R}^V$. The probability of next character $j$ is:

$$
P(j \mid i) = \frac{e^{W_{ij}}}{\sum_k e^{W_{ik}}}
$$

The loss for one pair is $-\log P(j \mid i)$. Its gradient with respect to the logits is beautifully simple (derived in Ch 7):

$$
\frac{\partial \mathcal{L}}{\partial W_{ik}} = P(k \mid i) - \mathbb{1}[k = j]
$$

*"Push the true answer's score up by (1 − its probability) and push every other score down by its probability."*

Mini example: vocabulary {a, b}, $W_a = [0, 0]$, so $P = [0.5, 0.5]$. The true next char is b, so the gradient is $[0.5, -0.5]$. With learning rate 1, $W_a$ becomes $[-0.5, 0.5]$, giving $P(b|a) = e^{0.5}/(e^{-0.5}+e^{0.5}) ≈ 0.73$. One step and the model learned.

### 🛠️ Build It From Scratch

```python
# ch01_toy_gpt.py : a complete (tiny) neural language model in ~60 lines
import torch
import torch.nn.functional as F

torch.manual_seed(1337)
text = ("to be or not to be that is the question "
        "whether tis nobler in the mind to suffer ") * 50

# 1) TOKENIZER: characters <-> integers
chars = sorted(set(text))
V = len(chars)
stoi = {c: i for i, c in enumerate(chars)}
itos = {i: c for c, i in stoi.items()}
encode = lambda s: [stoi[c] for c in s]
decode = lambda ids: "".join(itos[i] for i in ids)
data = torch.tensor(encode(text), dtype=torch.long)        # (N,)
print(f"vocab size V={V}, tokens N={len(data)}")

# 2) MODEL: a (V, V) table of logits, the simplest possible LM
W = torch.zeros((V, V), requires_grad=True)

# 3) TRAINING LOOP
B, lr = 256, 5.0
for step in range(301):
    ix = torch.randint(0, len(data) - 1, (B,))             # random positions (B,)
    x, y = data[ix], data[ix + 1]                          # current char, next char (B,), (B,)
    logits = W[x]                                          # (B, V)  row lookup = embedding
    loss = F.cross_entropy(logits, y)                      # scalar, avg -log p(true)
    W.grad = None
    loss.backward()                                        # dL/dW
    with torch.no_grad():
        W -= lr * W.grad                                   # gradient descent step
    if step % 50 == 0:
        print(f"step {step:3d} | loss {loss.item():.3f}")

# 4) GENERATION: sample one char at a time
def generate(start, n=80):
    ids = encode(start)
    for _ in range(n):
        probs = F.softmax(W[ids[-1]], dim=-1)              # (V,)
        ids.append(torch.multinomial(probs, 1).item())     # sample, don't argmax
    return decode(ids)

print(generate("t"))
print(f"uniform baseline loss = ln(V) = {torch.log(torch.tensor(float(V))):.3f}")
```

Expected output: the loss starts at $\ln V ≈ 2.94$ and drops to about 1.9–2.0. The generated text is gibberish that *looks* English-ish ("to thes be nobe..."), because the model only sees one character of context.

### 🔬 Experiment & Observe
1. **Learning rate:** try `lr=0.1` (slow), `lr=50` (unstable). Predict the curves first.
2. **Batch size:** try `B=8`. The loss becomes noisy but still falls.
3. **Greedy vs sampling:** replace `multinomial` with `argmax`. Watch it loop forever on the same pattern.
4. **The wall:** no matter how long you train, the loss plateaus near 1.9. **Why?** One character of context is not enough. Every chapter from 11 to 20 is about *giving the model more context*.

### ⚠️ Failure Modes & Debugging
- **Forgetting `W.grad = None`**: gradients accumulate across steps and training explodes.
- **Updating without `torch.no_grad()`**: PyTorch tries to track the update itself and raises an error about in-place ops on a leaf tensor.
- **`y` has the wrong dtype**: `cross_entropy` needs `torch.long` targets.
- **Initial loss far above ln V**: your initialization is too confident. Starting at zeros gives exactly ln V. This check is one of the most useful sanity tests in the whole field.

### 🧠 Expert Insight
Karpathy's *makemore* and *nanoGPT* follow exactly this progression. The only differences between this toy and GPT-4-class models are: (1) how logits are computed from context (a transformer instead of a table lookup), (2) scale, (3) tokenizer, and (4) post-training. **The loss, the optimizer loop and the sampling are the same.**

3. *(Coding, easy)* Print the 5 most likely characters after `"t"`.
4. *(Coding, harder)* Replace the manual update with `torch.optim.Adam([W], lr=0.1)`.

**Predict before you run:** the loss at step 0 with `W = torch.randn(V, V) * 5`?

<details><summary>Answers</summary>

1. With all logits 0, softmax is uniform, so $-\ln(1/V) = \ln V$.
2. The model's (unnormalized log) belief about which character follows character $i$; softmax of the row ≈ the bigram frequencies.
3. `torch.topk(F.softmax(W[stoi['t']], -1), 5)` then decode the indices.
4. `opt = torch.optim.Adam([W], lr=0.1)`; `opt.zero_grad(); loss.backward(); opt.step()`.

Predict: much higher than ln V (around 10+), because random confident logits are usually confidently wrong.
</details>

### 📌 Recap Card
- Ingredients: tokenizer, model producing logits, softmax, cross-entropy, backprop, optimizer, sampling.
- Sanity check: the initial loss should be ≈ ln V.
- The bigram wall is caused by too little context.
- GPT = the same loop with a far better "logits from context" function.

> **Core intuition:** *Every LLM is this loop; only the function inside the box gets smarter.*

## 1.5 How to Study This Book

### 🧭 The Problem First
