## 31.1 Data Parallel (DDP) and All-Reduce

### 🧭 The Problem First
Training on 20B tokens at 100K tok/s takes 2.3 days. With 8 GPUs, can we do it in 7 hours?

### 💡 Intuition / Instinct
**Data parallelism:** every GPU holds a full copy of the model and processes *different* data. After backward, the GPUs **average their gradients** (all-reduce), so every copy takes the identical optimizer step and stays in sync. Mathematically it's gradient accumulation across GPUs (Ch 24.4), and the global batch = per-GPU batch × number of GPUs.

**Ring all-reduce:** each GPU sends and receives only ~2× the gradient size in total, regardless of the number of GPUs, so it scales well.

### 🖼️ Visual Mental Model

```text
 GPU0: batch0 → grads0 ┐
 GPU1: batch1 → grads1 ├─ all-reduce (average) ─▶ every GPU has mean(grads) → identical step
 GPU2: batch2 → grads2 │
 GPU3: batch3 → grads3 ┘
 DDP overlaps the all-reduce of later layers' grads with backward of earlier layers (buckets)
```

### 📐 The Math, Gently
Ring all-reduce time ≈ $2\frac{(n-1)}{n}\cdot\frac{S}{\text{bandwidth}}$ for gradient size S. For 1B params in bf16 (2 GB) over NVLink (~300 GB/s effective): ≈ 13 ms, easily hidden behind backward. Over 10 Gb/s Ethernet (~1.25 GB/s): ≈ 3.2 s per step, which is catastrophic. **The interconnect matters.**

### 🛠️ Build It From Scratch

```python
# scripts/ddp_allreduce_demo.py : run with  torchrun --nproc_per_node=2 scripts/ddp_allreduce_demo.py
import os, torch, torch.distributed as dist
def main():
    backend = "nccl" if torch.cuda.is_available() else "gloo"
    dist.init_process_group(backend)
    rank, world = dist.get_rank(), dist.get_world_size()
    dev = f"cuda:{rank}" if backend == "nccl" else "cpu"
    if backend == "nccl": torch.cuda.set_device(rank)
    g = torch.full((4,), float(rank + 1), device=dev)          # pretend gradient
    dist.all_reduce(g, op=dist.ReduceOp.SUM); g /= world         # average
    print(f"rank {rank}: averaged grad {g.tolist()}")            # all ranks: mean(1..world)
    dist.destroy_process_group()
if __name__ == "__main__": main()
```

DDP in our trainer:

```python
# nanoforge/distributed.py
import os, torch, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

def setup_distributed():
    if "RANK" not in os.environ: return 0, 1, 0, False
    backend = "nccl" if torch.cuda.is_available() else "gloo"
    dist.init_process_group(backend)
    rank, world, local = dist.get_rank(), dist.get_world_size(), int(os.environ["LOCAL_RANK"])
    if torch.cuda.is_available(): torch.cuda.set_device(local)
    return rank, world, local, True

def wrap_ddp(model, local_rank):
    return DDP(model, device_ids=[local_rank] if torch.cuda.is_available() else None)

# train_step with DDP: only sync grads on the last micro-step
import contextlib
def ddp_train_step(model, opt, batches, cfg, ctx, is_ddp):
    total = 0.0
    for micro in range(cfg.grad_accum):
        sync = (micro == cfg.grad_accum - 1)
        maybe_nosync = model.no_sync() if (is_ddp and not sync) else contextlib.nullcontext()
        with maybe_nosync:
            x, y = next(batches)
            with ctx: _, loss = model(x, y); loss = loss / cfg.grad_accum
            loss.backward(); total += loss.item()
    gn = torch.nn.utils.clip_grad_norm_(model.parameters(), cfg.grad_clip)
    opt.step(); opt.zero_grad(set_to_none=True)
    return total, gn.item()
```

In `train.py`: call `setup_distributed()`, build the loader with `rank, world_size`, wrap the model with `wrap_ddp`, only rank 0 logs/evaluates/saves, and use `model.module` for the raw model. Launch:

```bash
torchrun --standalone --nproc_per_node=2 -m nanoforge.train --model_size=micro
```

### 🔬 Experiment & Observe
With 2 GPUs: tokens/sec should be ≈ 1.9× a single GPU (at the same per-GPU micro-batch). Keep the *global* batch constant (halve grad_accum) to reproduce the single-GPU loss curve.

### ⚠️ Failure Modes & Debugging
- All ranks reading the same data (forgetting rank-based sharding) → the effective batch is the same data repeated.
- Rank-dependent control flow (e.g. rank 0 skipping a forward) → a hang in the collective.
- Saving the checkpoint from every rank simultaneously → file clobbering. Save on rank 0, with `dist.barrier()`.

### 🧠 Expert Insight
- **Li et al. (2020), "PyTorch Distributed":** DDP bucketing and overlap.
- **Sergeev & Del Balso (2018), Horovod**, which popularized ring all-reduce for DL.
- DDP is the right default whenever the model + optimizer fit on one GPU.

<details><summary>Answers</summary>

1. The sum (or average) of a tensor across all ranks, with the result on every rank.
2. To avoid redundant communication; syncing once after accumulation is equivalent.
</details>

### 📌 Recap Card
- DDP: replicate the model, split the data, average the gradients.
- Ring all-reduce ≈ 2× gradient size of traffic per GPU.
- Shard the data by rank; only rank 0 does I/O.

## 31.2 ZeRO Stages 1–3 and FSDP

### 🧭 The Problem First
DDP replicates **everything**: 16 bytes/param on every GPU. A 7B model needs 112 GB of model states per GPU, so it doesn't fit on 80 GB even before activations.

### 💡 Intuition / Instinct
**ZeRO (Zero Redundancy Optimizer): stop replicating, start sharding.** With N GPUs:
- **Stage 1:** shard the **optimizer states** (Adam m, v, fp32 master): each GPU updates only its 1/N slice.
- **Stage 2:** also shard the **gradients** (reduce-scatter instead of all-reduce).
- **Stage 3:** also shard the **parameters**: each GPU holds 1/N of the weights and **all-gathers** a layer's full weights just before using it, then frees them.

**FSDP** (Fully Sharded Data Parallel) is PyTorch's native ZeRO-3.

### 🖼️ Visual Mental Model

```text
 per-GPU memory for model states (Ψ params, N GPUs, mixed precision + Adam):
 DDP:     2Ψ + 2Ψ + 12Ψ           = 16Ψ
 ZeRO-1:  2Ψ + 2Ψ + 12Ψ/N
 ZeRO-2:  2Ψ + (2Ψ + 12Ψ)/N
 ZeRO-3:  (2Ψ + 2Ψ + 12Ψ)/N = 16Ψ/N
 FSDP forward per layer: all-gather params → compute → free; backward: all-gather → compute → reduce-scatter grads
```

### 📐 The Math, Gently
7B on 8 GPUs with ZeRO-3: 16 × 7e9 / 8 = 14 GB/GPU for model states ✓ (plus activations).
Communication: ZeRO-3 ≈ 1.5× DDP's volume (an extra all-gather in the forward), usually acceptable on NVLink.

### 🛠️ Build It From Scratch

```python
# nanoforge/distributed.py (append): FSDP wrapping (PyTorch 2.x)
import functools, torch
from torch.distributed.fsdp import FullyShardedDataParallel as FSDP, MixedPrecision, ShardingStrategy
from torch.distributed.fsdp.wrap import transformer_auto_wrap_policy

def wrap_fsdp(model, block_cls, bf16=True, strategy="full"):
    policy = functools.partial(transformer_auto_wrap_policy, transformer_layer_cls={block_cls})
    mp = MixedPrecision(param_dtype=torch.bfloat16, reduce_dtype=torch.float32, buffer_dtype=torch.bfloat16) if bf16 else None
    strat = {"full": ShardingStrategy.FULL_SHARD, "grad_op": ShardingStrategy.SHARD_GRAD_OP,
             "hybrid": ShardingStrategy.HYBRID_SHARD}[strategy]
    return FSDP(model, auto_wrap_policy=policy, mixed_precision=mp, sharding_strategy=strat,
                device_id=torch.cuda.current_device(), use_orig_params=True)
# usage: model = wrap_fsdp(GPT(cfg).cuda(), Block)
# optimizer must be created AFTER wrapping. Checkpoint with torch.distributed.checkpoint (DCP)
# or FSDP.state_dict_type(model, StateDictType.FULL_STATE_DICT, ...) on rank 0.
```

A conceptual ZeRO-1 in ~25 lines (for understanding):

```python
import torch, torch.distributed as dist
class ZeRO1AdamW:
    """Each rank owns a contiguous slice of the flattened params and its Adam state."""
    def __init__(self, params, lr=3e-4, betas=(0.9, 0.95), wd=0.1, eps=1e-8):
        self.params = [p for p in params if p.requires_grad]
        self.rank, self.world = dist.get_rank(), dist.get_world_size()
        flat = torch.cat([p.detach().flatten().float() for p in self.params])
        n = flat.numel(); self.chunk = (n + self.world - 1) // self.world
        self.lo, self.hi = self.rank * self.chunk, min(n, (self.rank + 1) * self.chunk)
        self.master = flat[self.lo:self.hi].clone()              # fp32 master slice
        self.m = torch.zeros_like(self.master); self.v = torch.zeros_like(self.master)
        self.lr, self.b1, self.b2, self.wd, self.eps, self.t, self.n = lr, *betas, wd, eps, 0, n
    @torch.no_grad()
    def step(self):
        self.t += 1
        g = torch.cat([p.grad.flatten().float() for p in self.params])
        dist.all_reduce(g); g /= self.world                      # (ZeRO-2 would reduce-scatter instead)
        gs = g[self.lo:self.hi]
        self.m.mul_(self.b1).add_(gs, alpha=1 - self.b1); self.v.mul_(self.b2).addcmul_(gs, gs, value=1 - self.b2)
        mh, vh = self.m / (1 - self.b1 ** self.t), self.v / (1 - self.b2 ** self.t)
        self.master.mul_(1 - self.lr * self.wd).add_(-self.lr * mh / (vh.sqrt() + self.eps))
        full = torch.zeros(self.chunk * self.world, device=g.device)
        dist.all_gather_into_tensor(full, torch.nn.functional.pad(self.master, (0, self.chunk - self.master.numel())))
        off = 0
        for p in self.params:
            k = p.numel(); p.copy_(full[off:off + k].view_as(p)); off += k
```

(This simplified version decays every parameter; add a per-parameter decay mask to match `make_param_groups`.)

### 🔬 Experiment & Observe
On 2 GPUs, measure the peak memory per GPU for DDP vs FSDP(`grad_op`) vs FSDP(`full`) with the mini model. The model-state memory drops as predicted; throughput drops slightly with full sharding.

### ⚠️ Failure Modes & Debugging
- Creating the optimizer before FSDP wrapping → the optimizer holds references to unsharded params.
- Saving FSDP checkpoints naively gives sharded fragments. Use DCP or a full-state-dict context.
- `use_orig_params=True` is needed for `torch.compile` and per-parameter optimizer groups.

### 🧠 Expert Insight
- **Rajbhandari et al. (2020), ZeRO**; **ZeRO-Offload/Infinity** (offload to CPU/NVMe).
- **Zhao et al. (2023), PyTorch FSDP.** FSDP2 (`fully_shard`, per-parameter DTensor sharding) is the newer API.
- Llama 3 used FSDP-style sharding in combination with TP/PP/CP.

### ✅ Check Your Instinct
1. Per-GPU model-state memory for 13B params with ZeRO-3 on 16 GPUs?
2. What extra communication does ZeRO-3 add?

<details><summary>Answers</summary>

1. 16 × 13e9 / 16 = 13 GB.
2. All-gathering the parameters before each layer's forward and backward.
</details>

### 📌 Recap Card
- ZeRO-1: shard the optimizer; ZeRO-2: + grads; ZeRO-3/FSDP: + params.
- Memory 16Ψ → 16Ψ/N.
- Wrap per block; create the optimizer after wrapping; use proper sharded checkpoints.

> **Core intuition:** *Don't give every worker a full copy of the library; give each a shelf and share on demand.*

## 31.3 Tensor Parallelism (Megatron-Style Column/Row Splits)

### 🧭 The Problem First
FSDP still computes each layer's full matmul on one GPU (after gathering the weights). For huge layers (C = 16K), a single layer's activations and compute may be too large, and FSDP's all-gathers become expensive at very large scale.

### 💡 Intuition / Instinct
Split **each matrix multiplication** across GPUs:
- **Column-parallel** Linear: split W's output columns, so each GPU computes a slice of the output features. No communication is needed for the forward.
- **Row-parallel** Linear: split W's input rows, so each GPU computes a partial sum and an all-reduce combines them.

Megatron's trick: MLP = column-parallel `c_fc` → GELU (elementwise, so it works on slices!) → row-parallel `c_proj` → **one all-reduce**. Attention: split the *heads* across GPUs (each GPU owns H/N heads) → one all-reduce after `c_proj`. So there are 2 all-reduces per block in the forward.

### 🖼️ Visual Mental Model

```text
 MLP with TP=2:
 x (full) ─┬─ GPU0: x @ W_fc[:, :2C] → gelu → @ W_proj[:2C, :] → partial y0 ┐
           └─ GPU1: x @ W_fc[:, 2C:] → gelu → @ W_proj[2C:, :] → partial y1 ┴─ all-reduce → y
```

### 📐 The Math, Gently
$Y = \text{GELU}(XA)B$. Split $A = [A_1, A_2]$ by columns and $B = \begin{bmatrix}B_1\\B_2\end{bmatrix}$ by rows: $Y = \text{GELU}(XA_1)B_1 + \text{GELU}(XA_2)B_2$. Each term lives on one GPU; the sum = all-reduce.
Communication per block ≈ 2 all-reduces of B×T×C activations (forward) + 2 (backward), so TP needs very fast links (NVLink, within a node).

### 🛠️ Build It From Scratch

```python
# single-process simulation proving the math of Megatron MLP splitting
import torch, torch.nn.functional as F
torch.manual_seed(0)
B, T, C, N = 2, 4, 8, 2                         # N = tensor-parallel degree
x = torch.randn(B, T, C); A = torch.randn(C, 4 * C); Bm = torch.randn(4 * C, C)
ref = F.gelu(x @ A) @ Bm
A_shards = A.chunk(N, dim=1); B_shards = Bm.chunk(N, dim=0)          # column / row splits
partials = [F.gelu(x @ A_shards[i]) @ B_shards[i] for i in range(N)]  # each "GPU"
y = sum(partials)                                                     # all-reduce
print(torch.allclose(y, ref, atol=1e-5))                              # True

# attention: heads split across GPUs; each computes its heads' output @ its rows of W_O; then sum
```

Real implementation: PyTorch's `torch.distributed.tensor.parallel` (`ColwiseParallel`, `RowwiseParallel`, `parallelize_module`) applies these plans to `nn.Linear` layers via DTensor.

### 🔬 Experiment & Observe
Extend the simulation to attention: split the 4 heads into 2 per "GPU", compute each shard's `y_h @ W_O[rows]`, sum, and compare with the full attention output.

### ⚠️ Failure Modes & Debugging
- A non-elementwise op between the column and row splits (e.g. LayerNorm over the full feature dimension) breaks the scheme; it needs communication.
- TP across nodes (slow links) → terrible scaling. Keep TP ≤ GPUs per node (typically 8).

### 🧠 Expert Insight
- **Shoeybi et al. (2019), Megatron-LM.**
- **Sequence parallelism (Korthikanti et al., 2022):** also shard LayerNorm/dropout activations along T within the TP group.
- **Context parallelism / Ring Attention:** shard long sequences across GPUs for million-token training.

### ✅ Check Your Instinct
1. Why can GELU run on column shards without communication?
2. Why keep TP within a node?

<details><summary>Answers</summary>

1. It's elementwise, so each feature slice is independent.
2. TP communicates activations every layer and needs NVLink-class bandwidth.
</details>

### 📌 Recap Card
- Column-split then row-split → one all-reduce per MLP/attention.
- Heads split naturally across GPUs.
- Intra-node only; add sequence parallelism for activations.

> **Core intuition:** *Split each big multiplication so many GPUs work on the same layer at once.*

## 31.4 Pipeline Parallelism and Bubbles

### 🧭 The Problem First
For 100+ layer models across many nodes, even TP+FSDP isn't enough, or the communication is too costly across nodes.

### 💡 Intuition / Instinct
Split the **layers** into stages on different GPUs: GPU0 runs layers 1–10, GPU1 runs 11–20, and so on. Activations flow forward stage to stage, and gradients flow back. Only activations at the stage boundaries are communicated (cheap, point-to-point), which is good across nodes.
The problem: **bubbles**. If one batch goes through the stages sequentially, most GPUs sit idle. Fix: split the batch into **micro-batches** and pipeline them, like an assembly line (GPipe, 1F1B schedules).

### 🖼️ Visual Mental Model

```text
 4 stages, 8 micro-batches (1F1B):
 S0: F1 F2 F3 F4 B1 F5 B2 F6 B3 F7 B4 F8 B5 B6 B7 B8
 S1:    F1 F2 F3 B1 F4 B2 ...
 S2:       F1 F2 B1 ...
 S3:          F1 B1 F2 B2 ...
       └bubble┘                               └bubble┘
 bubble fraction ≈ (p-1)/(m + p - 1)
```

### 📐 The Math, Gently
Bubble fraction for p stages and m micro-batches: $\frac{p-1}{m+p-1}$. p = 4, m = 8: 3/11 ≈ 27%; m = 32: 3/35 ≈ 9%. So use many micro-batches. Interleaved schedules (virtual stages) reduce it further.

### 🛠️ Build It From Scratch

```python
def bubble_fraction(p, m): return (p - 1) / (m + p - 1)
for p in [2, 4, 8, 16]:
    print(p, [f"{bubble_fraction(p, m):.0%}" for m in (4, 16, 64)])

# single-process conceptual pipeline (GPipe): stages as module lists; micro-batches flow through
import torch, torch.nn as nn
stages = [nn.Sequential(*[nn.Linear(64, 64), nn.GELU()]) for _ in range(4)]
def gpipe_forward(x, n_micro=4):
    outs = []
    for mb in x.chunk(n_micro):                   # real systems run stages concurrently on different GPUs
        for s in stages: mb = s(mb)
        outs.append(mb)
    return torch.cat(outs)
print(gpipe_forward(torch.randn(16, 64)).shape)
```

Real implementations: `torch.distributed.pipelining` (PyTorch), DeepSpeed pipeline, Megatron.

### 🔬 Experiment & Observe
Draw the 1F1B schedule for p = 4 and m = 8 on paper, and count the idle slots against the formula.

### ⚠️ Failure Modes & Debugging
- Unbalanced stages (the embedding/LM head make the first/last stages heavier) → the slowest stage sets the pace. Balance by FLOPs.
- A small number of micro-batches → large bubbles.

### 🧠 Expert Insight
- **Huang et al. (2019), GPipe.** **Narayanan et al. (2019/2021), PipeDream/1F1B and interleaved schedules** (Megatron).
- **DeepSeek-V3's DualPipe (2024):** overlaps computation and communication in both directions.
- Zero-bubble pipeline schedules (Qi et al., 2023).

### ✅ Check Your Instinct
1. Bubble fraction for p = 8, m = 32?
2. Why is PP suitable across nodes?

<details><summary>Answers</summary>

1. 7/39 ≈ 18%.
2. It only sends boundary activations point-to-point, which is low bandwidth compared with TP.
</details>

### 📌 Recap Card
- Split the layers into stages; pipeline the micro-batches.
- Bubble ≈ (p−1)/(m+p−1).
- Balance the stages; use many micro-batches.

> **Core intuition:** *An assembly line only works if every station always has something to do.*

## 31.5 3D Parallelism and Choosing a Strategy

### 🧭 The Problem First
Given a model size, a cluster and an interconnect, which combination should you use?

### 💡 Intuition / Instinct
A decision ladder:
1. **Fits on one GPU (with activation checkpointing)?** → DDP (plus accumulation). Done.
2. **Model states don't fit, but a single layer does?** → FSDP/ZeRO-3 (or ZeRO-1/2 if only the optimizer overflows).
3. **Very large models or very large clusters?** → TP within nodes (≤ 8) + PP across nodes + data parallelism (FSDP) across replicas = **3D/4D parallelism**, plus context parallelism for very long sequences, and expert parallelism for MoE (Ch 33).

On a budget: rent a single 8×GPU node → FSDP handles up to ~7–13B-parameter training comfortably.

### 🖼️ Visual Mental Model

```text
 cluster of 64 GPUs = 8 nodes × 8
   TP=8 (within node) × PP=4 (across nodes) × DP=2 (replicas)
   ┌node0 TP group┐ → stage 0
   ┌node1 TP group┐ → stage 1 ...
```

### 📐 The Math, Gently
Total GPUs = TP × PP × DP (× CP × EP). Global batch = DP × micro_batch × accum (or micro-batches per pipeline) × T.
Rule: keep TP communication on NVLink, PP across nodes, and DP (the gradient sync) overlapped with compute.

### 🛠️ Build It From Scratch

```python
def choose_parallelism(n_params, gpu_mem_gb, n_gpus, gpus_per_node=8, act_gb_per_gpu=10):
    states_gb = 16 * n_params / 1e9
    if states_gb + act_gb_per_gpu <= gpu_mem_gb: return "DDP"
    if states_gb / n_gpus + act_gb_per_gpu <= gpu_mem_gb: return f"FSDP (ZeRO-3) over {n_gpus} GPUs"
    tp = min(gpus_per_node, 8)
    for pp in [1, 2, 4, 8, 16, 32]:
        if n_gpus % (tp * pp): continue
        dp = n_gpus // (tp * pp)
        if states_gb / (tp * pp * dp) + act_gb_per_gpu / tp <= gpu_mem_gb:
            return f"TP={tp} x PP={pp} x DP(FSDP)={dp}"
    return "need more GPUs / offloading"
for n, g in [(1e8, 1), (1.3e9, 1), (7e9, 8), (70e9, 64), (405e9, 1024)]:
    print(f"{n:.0e} params on {g} GPUs (80GB): {choose_parallelism(n, 80, g)}")
```

### 🔬 Experiment & Observe
Use the chooser on your Capstone plan. Then, if you have access, rent an 8-GPU node for one hour, run the mini model with DDP and with FSDP, and record the scaling efficiency = (tok/s with 8 GPUs) / (8 × tok/s with 1).

### ⚠️ Failure Modes & Debugging
- Over-parallelizing small models: communication dominates and the efficiency collapses.
- Mismatched global batch sizes when changing the parallel layout → a different training run. Always recompute the accumulation to keep the global batch.

### 🧠 Expert Insight
- **Narayanan et al. (2021), "Efficient Large-Scale Language Model Training on GPU Clusters Using Megatron-LM":** the PTD-P analysis.
- **Llama 3 (2024):** 16K H100s with 4D parallelism (TP 8, CP, PP, FSDP), reaching 38–43% MFU.
- **TorchTitan (2024):** a clean PyTorch-native reference for 4D parallelism, great for study.

### ✅ Check Your Instinct
1. Recommended strategy for 3B params on 4× 24 GB GPUs?
2. Why keep the global batch fixed when changing the layout?

<details><summary>Answers</summary>

1. 48 GB of states → FSDP across 4 GPUs (12 GB each) + activation checkpointing (possibly CPU offload of the optimizer).
2. The global batch defines the optimization problem (the lr, noise); changing it changes the run.
</details>

### 📌 Recap Card
- Ladder: DDP → FSDP → TP × PP × DP (+ CP, EP).
- TP in-node, PP across nodes, DP everywhere.
- Keep the global batch fixed across layouts.

> **Core intuition:** *Split the data, then the optimizer, then the layers, then the matrices, in that order of reluctance.*
