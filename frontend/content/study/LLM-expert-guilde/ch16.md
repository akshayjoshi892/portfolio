## 16.1 Byte-Level BPE: Why It Never Sees an Unknown Token

### 🧭 The Problem First
Older character-level BPE (on Unicode characters) had a base vocab of all characters seen in training. A new emoji or a rare script at inference → `<UNK>` → the model is blind to it.

### 💡 Intuition / Instinct
Start the vocabulary from the **256 byte values**. Any string, in any language, including binary garbage, decomposes into bytes, so there are *never* unknown inputs. The cost: rare scripts get split into many byte tokens (inefficient but lossless).

**Byte fallback** (SentencePiece's approach) is a hybrid: work on characters, but if a character isn't in the vocab, emit its UTF-8 bytes as special `<0xNN>` tokens.

### 🖼️ Visual Mental Model

```text
 input "𓀀" (Egyptian hieroglyph, never seen)
 char-BPE:  <UNK>                 (information lost)
 byte-BPE:  [240, 147, 128, 128]  (4 byte tokens, lossless)
```

### 📐 The Math, Gently
Byte-BPE guarantees $\text{decode}(\text{encode}(s)) = s$ for all byte strings s. Tokens-per-character for unseen scripts ≈ UTF-8 bytes per char (2–4).

### 🛠️ Build It From Scratch
Our `RegexBPE` is already byte-level. Verify it:

```python
import random
from nanoforge.tokenizer.regex_bpe import RegexBPE
tok = RegexBPE().load("tokenizers/shakespeare_2k.json")
for _ in range(1000):
    s = "".join(chr(random.randint(0x20, 0x2FFFF)) for _ in range(random.randint(1, 30)))
    s = s.encode("utf-8", errors="ignore").decode("utf-8")      # drop lone surrogates
    assert tok.decode(tok.encode(s)) == s
print("1000 random unicode round-trips OK")
```

### 🔬 Experiment & Observe
Tokenize some Chinese with the Shakespeare tokenizer: ~3 tokens per character (pure bytes). With a tokenizer trained on Chinese, it's ~1 or fewer. **The training data of the tokenizer determines who pays more.**

### ⚠️ Failure Modes & Debugging
- Decoding a *single* token that is a partial UTF-8 sequence gives `�`. Always decode whole sequences, or buffer while streaming.
- GPT-2's byte→unicode remapping table must be reproduced exactly when loading GPT-2 vocab files.

### 🧠 Expert Insight
Radford et al. (2019) introduced byte-level BPE in GPT-2. Byte-level *models* (no tokenizer), like ByT5 (2021) and MegaByte (2023), and newer byte-latent approaches (BLT, 2024), try to remove tokenizers entirely.

### ✅ Check Your Instinct
1. What's the trade-off of byte-level BPE?

<details><summary>Answers</summary>

1. No UNK (robust) but inefficient for scripts under-represented in the tokenizer's training data.
</details>

### 📌 Recap Card
- 256 byte base tokens → lossless and universal.
- Byte fallback = char-level with bytes as backup.
- Efficiency depends on the tokenizer's training data.

> **Core intuition:** *If you can see bytes, you can read anything, just slowly for unfamiliar scripts.*

## 16.2 WordPiece and Unigram LM (SentencePiece) From Scratch

### 🧭 The Problem First
BPE merges by raw frequency, which may not produce the segmentation that best *models* the language. Other algorithms pick tokens by a likelihood criterion.

### 💡 Intuition / Instinct
- **WordPiece (BERT):** like BPE, but merge the pair maximizing $\frac{\text{count}(ab)}{\text{count}(a)\,\text{count}(b)}$, i.e. prefer pairs that co-occur *more than chance*, not just frequently. Encoding is greedy longest-match-first with `##` continuation prefixes.
- **Unigram LM (SentencePiece, used in T5, Llama 1/2, Gemma):** go *top-down*. Start with a huge candidate vocabulary, model text as a sequence of independently drawn tokens with probabilities p(token), and iteratively **remove** the tokens whose removal hurts the likelihood least. Encoding picks the *most probable segmentation* via Viterbi. It can also *sample* segmentations (subword regularization).

### 🖼️ Visual Mental Model

```text
 BPE:     bottom-up, merge frequent pairs        (256 → 32K)
 Unigram: top-down, prune unlikely pieces       (1M candidates → 32K)
 Viterbi segmentation of "unhappy":
   un|happy  p=0.01·0.02 = 2e-4   ✓ best
   u|n|happy p=... smaller
```

### 📐 The Math, Gently
Unigram segmentation likelihood: $P(\mathbf{x}) = \prod_i p(x_i)$; best segmentation $\arg\max \sum_i \log p(x_i)$ via dynamic programming:
$\text{best}[j] = \max_{i<j,\ s[i:j]\in V} \text{best}[i] + \log p(s[i:j])$.
Vocab pruning uses EM: the E-step computes expected token counts over segmentations; the M-step sets p ∝ counts; tokens are pruned by loss increase.

### 🛠️ Build It From Scratch

```python
# nanoforge/tokenizer/unigram.py
import math
from collections import Counter

def viterbi(word, logp, max_len=16):
    """Best segmentation of `word` under unigram log-probs. Returns list of pieces."""
    n = len(word); best = [0.0] + [-math.inf] * n; back = [0] * (n + 1)
    for j in range(1, n + 1):
        for i in range(max(0, j - max_len), j):
            piece = word[i:j]
            if piece in logp and best[i] + logp[piece] > best[j]:
                best[j], back[j] = best[i] + logp[piece], i
    pieces, j = [], n
    while j > 0:
        i = back[j]; pieces.append(word[i:j]); j = i
    return pieces[::-1], best[n]

def train_unigram(words: Counter, vocab_size=500, init_size=5000, max_len=12, prune_frac=0.2, em_iters=2):
    # 1) candidates: all substrings up to max_len, keep most frequent (plus all single chars)
    cand = Counter()
    for w, f in words.items():
        for i in range(len(w)):
            for j in range(i + 1, min(len(w), i + max_len) + 1):
                cand[w[i:j]] += f
    chars = {c for w in words for c in w}
    vocab = dict(cand.most_common(init_size)); vocab.update({c: cand[c] for c in chars})
    while True:
        # 2) EM (hard-EM with Viterbi for simplicity): re-estimate probabilities
        for _ in range(em_iters):
            total = sum(vocab.values()); logp = {t: math.log(c / total) for t, c in vocab.items()}
            counts = Counter()
            for w, f in words.items():
                for p in viterbi(w, logp, max_len)[0]: counts[p] += f
            vocab = {t: counts.get(t, 0) + 1e-3 for t in vocab}
        if len(vocab) <= vocab_size: break
        # 3) prune: score = loss increase if token removed (approx: its usage count); never drop chars
        total = sum(vocab.values()); logp = {t: math.log(c / total) for t, c in vocab.items()}
        removable = sorted((t for t in vocab if len(t) > 1), key=lambda t: vocab[t])
        n_drop = min(len(vocab) - vocab_size, max(1, int(prune_frac * len(removable))))
        for t in removable[:n_drop]: del vocab[t]
    total = sum(vocab.values())
    return {t: math.log(c / total) for t, c in vocab.items()}
```

```python
import regex as re
from collections import Counter
from nanoforge.tokenizer.unigram import train_unigram, viterbi
text = open("data/raw/shakespeare.txt", encoding="utf-8").read()
words = Counter(re.findall(r" ?\p{L}+| ?[^\s\p{L}]+|\s+", text))
logp = train_unigram(words, vocab_size=800)
for w in [" unhappily", " kingdom", " thee"]:
    print(w, viterbi(w, logp)[0])
```

### 🔬 Experiment & Observe
Compare the BPE vs unigram segmentations of the same words. Unigram tends to find more morphologically sensible splits ("un|happi|ly"). Try sampling segmentations with probability ∝ exp(score/τ) for subword regularization, a data augmentation used in MT.

### ⚠️ Failure Modes & Debugging
- This is a simplified hard-EM; real SentencePiece uses forward–backward (soft EM) and a better pruning score. Use the `sentencepiece` library for production training.
- SentencePiece encodes spaces as "▁" (U+2581). Decoding must convert them back.

### 🧠 Expert Insight
- **Schuster & Nakajima (2012)** WordPiece; **Kudo (2018)** Unigram LM + subword regularization; **Kudo & Richardson (2018)** SentencePiece.
- Llama 1/2 used SentencePiece BPE with byte fallback (32K vocab); Llama 3 switched to tiktoken-style BPE (128K).

### ✅ Check Your Instinct
1. How does WordPiece's merge criterion differ from BPE's?
2. What does Viterbi compute in Unigram tokenization?

<details><summary>Answers</summary>

1. It uses frequency normalized by the parts' frequencies (a likelihood gain), not raw frequency.
2. The most probable segmentation under the unigram token probabilities.
</details>

### 📌 Recap Card
- WordPiece: likelihood-based merges, `##` continuations.
- Unigram: top-down pruning, Viterbi encoding, sampling possible.
- SentencePiece: language-agnostic, "▁" for spaces, byte fallback.

> **Core intuition:** *BPE builds up by frequency; Unigram carves down by likelihood.*

## 16.3 Special Tokens, Chat Tokens, BOS/EOS/PAD

### 🧭 The Problem First
The model needs to know where documents begin and end, where a user's turn ends and the assistant's begins, and which positions are padding. Plain text can't mark these unambiguously, because a user could *type* "Assistant:".

### 💡 Intuition / Instinct
**Special tokens** are reserved ids that ordinary text can never produce: `<|endoftext|>`, `<|im_start|>`, `<|im_end|>`, `<|pad|>`. They act as structural punctuation. Because the encoder of ordinary text never emits them, a user typing the literal string "<|im_end|>" gets harmless ordinary tokens. This is an important **security boundary** against prompt injection.

- **BOS/EOS:** document boundaries (pretraining separates documents with EOS).
- **PAD:** filler for batching (masked out of the loss and attention).
- **Chat tokens:** role delimiters for SFT (Ch 37).

### 🖼️ Visual Mental Model

```text
 <|im_start|>system\nYou are helpful.<|im_end|>\n
 <|im_start|>user\nHi!<|im_end|>\n
 <|im_start|>assistant\nHello!<|im_end|>
      ↑ special ids (never produced by encoding user text)
```

### 📐 The Math, Gently
New special tokens need new rows in the embedding matrix (and the LM head). Initialize them to the *mean* of the existing embeddings rather than random, which is a smaller shock to the model.

### 🛠️ Build It From Scratch

```python
from nanoforge.tokenizer.regex_bpe import RegexBPE
tok = RegexBPE().load("tokenizers/shakespeare_2k.json")
SPECIALS = ["<|endoftext|>", "<|pad|>", "<|im_start|>", "<|im_end|>"]
tok.register_special_tokens(SPECIALS)
msg = "<|im_start|>user\nHello<|im_end|>"
print(tok.encode(msg))                                  # special ids appear
print(tok.encode(msg, allowed_special="none"))          # treated as plain text (safe for user input)

import torch
def resize_embeddings(emb: torch.nn.Embedding, new_V: int):
    old_V, C = emb.weight.shape
    new = torch.nn.Embedding(new_V, C)
    with torch.no_grad():
        new.weight[:old_V] = emb.weight
        new.weight[old_V:] = emb.weight.mean(0, keepdim=True)   # mean-init new rows
    return new
```

### 🔬 Experiment & Observe
Encode untrusted user text with `allowed_special="none"` and confirm that no special ids appear. Then encode the *template* (which you control) with specials enabled.

### ⚠️ Failure Modes & Debugging
- **Prompt injection via special tokens:** encoding user text with specials allowed lets users forge role boundaries.
- **PAD == EOS confusion:** if pad = eos and you mask all pads from the loss, the model never learns to emit EOS, so it never stops generating. Use a distinct pad token or mask carefully.
- Forgetting to resize the LM head after adding tokens gives index errors.

### 🧠 Expert Insight
OpenAI's ChatML (`<|im_start|>`) and Llama 3's `<|start_header_id|>`/`<|eot_id|>` are both special-token chat formats. tiktoken raises an error by default if special tokens appear in text, which is exactly this security design.

### ✅ Check Your Instinct
1. Why must user text be encoded with specials disallowed?
2. Why does pad == eos cause infinite generation?

<details><summary>Answers</summary>

1. Otherwise users can inject role markers and manipulate the conversation structure.
2. If every eos is masked as padding, the model never gets a gradient to predict eos.
</details>

### 📌 Recap Card
- Special tokens = structural markers that ordinary text can't produce.
- Encode untrusted text with specials disallowed.
- Resize and mean-init the embeddings for new tokens.
- Don't mask away EOS.

> **Core intuition:** *Special tokens are punctuation that users cannot type.*

## 16.4 Vocabulary Size Trade-offs

### 🧭 The Problem First
32K? 50K? 128K? 256K? The vocab size affects compute, memory, sequence length and quality, in opposing directions.

### 💡 Intuition / Instinct
A bigger vocab means:
- ✅ shorter sequences (better compression, cheaper attention, more text per context window);
- ✅ better coverage of multilingual text and code;
- ❌ a bigger embedding + LM head (parameters and the softmax cost per token);
- ❌ rarer tokens get fewer training updates (undertrained embeddings).

Small models suffer more from big vocabs (the embeddings dominate their parameters); big models benefit more.

### 🖼️ Visual Mental Model

```text
 vocab ↑ : sequence length ↓, embedding params ↑, softmax FLOPs/token ↑, rare-token undertraining ↑
 sweet spot grows with model size
```

### 📐 The Math, Gently
Embedding + head params = $2VC$ (untied) or $VC$ (tied). For C = 768 and V = 50K that's 38.4M tied; for V = 256K it's 197M, larger than the whole 124M model!
LM-head FLOPs per token = $2VC$. Compare with the transformer body ≈ $24LC^2$ per token (Ch 19).
Tao et al. (2024), "Scaling Laws with Vocabulary": the optimal V grows with compute; many models are under-vocabularied.

### 🛠️ Build It From Scratch

```python
def vocab_budget(V, C, L, tied=True):
    emb = V * C * (1 if tied else 2)
    body = 12 * L * C * C
    return emb, body, emb / (emb + body)
for V in [8_000, 32_000, 50_257, 128_000, 256_000]:
    for (C, L) in [(512, 8), (768, 12), (4096, 32)]:
        e, b, frac = vocab_budget(V, C, L)
        print(f"V={V:7d} C={C:4d} L={L:2d}: embedding share of params {frac:5.1%}")
```

Measure compression vs vocab size on your data:

```python
from nanoforge.tokenizer.regex_bpe import RegexBPE
held = text[-100_000:]
for vs in [512, 1024, 2048, 4096, 8192]:
    t = RegexBPE(); t.train(text[:-100_000], vs)
    print(vs, f"{len(held.encode()) / len(t.encode(held)):.2f} bytes/token")
```

### 🔬 Experiment & Observe
The compression gains flatten (log-like) with vocab size. For a 10M-param Capstone model, the embedding share at V = 32K would be huge, so pick 8K–16K. For 125M+, 32K–50K is reasonable.

### ⚠️ Failure Modes & Debugging
- A vocab size that isn't a multiple of 64/128 slows GPU matmuls. Pad V (e.g. 50257 → 50304) with unused tokens.
- A too-large vocab on small data leaves many tokens nearly unseen (bad embeddings, glitch tokens).

### 🧠 Expert Insight
GPT-2 50,257; Llama 2 32K; GPT-4 ~100K (cl100k); Llama 3 128K; Gemma 256K. Llama 3's jump to 128K improved compression by ~15% on English and much more on other languages.

### ✅ Check Your Instinct
1. Why do small models prefer smaller vocabs?
2. Why pad V to a multiple of 64?

<details><summary>Answers</summary>

1. The embedding/head parameters would dominate their parameter budget, and compute per token rises.
2. GPU matmul efficiency (tensor core tiling).
</details>

### 📌 Recap Card
- Bigger V: shorter sequences but more embedding params and softmax cost.
- The optimal V grows with model size.
- Pad V to a multiple of 64/128.

> **Core intuition:** *The vocabulary is a budget split between the alphabet and the thinker.*

## 16.5 Multilingual Fairness and Code Tokenization

### 🧭 The Problem First
The same sentence costs 1× tokens in English, 3× in Hindi and 5× in Burmese with an English-centric tokenizer. Users of those languages pay more, get less context, and get worse models. Code has its own quirks: indentation, long identifiers, and whitespace significance.

### 💡 Intuition / Instinct
**Tokenizer parity:** the token count for equivalent text should be similar across languages. It depends on (1) the language mix in the tokenizer's training data and (2) the vocab size. For code: allocate tokens for common indentation runs (4, 8 spaces), keywords, and camelCase/snake_case pieces. The regex should keep newlines and indentation sensible.

### 🖼️ Visual Mental Model

```text
 "Hello, how are you?" (EN)  → 6 tokens
 "नमस्ते, आप कैसे हैं?"  (HI)  → 20+ tokens with an English-trained tokenizer
 same meaning, ~4x cost
```

### 📐 The Math, Gently
Parity ratio $= \frac{\text{tokens}(\text{text}_L)}{\text{tokens}(\text{text}_{EN})}$ on parallel text. Petrov et al. (2023) found ratios over 10× for some languages with popular tokenizers.
Sampling for tokenizer training: temperature-based language sampling $p_L \propto n_L^{\alpha}$ (α ≈ 0.3–0.7) upweights low-resource languages.

### 🛠️ Build It From Scratch

```python
import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
parallel = {
    "en": "The weather is very nice today and I want to go for a walk.",
    "hi": "आज मौसम बहुत अच्छा है और मैं टहलने जाना चाहता हूँ।",
    "es": "Hoy hace muy buen tiempo y quiero salir a caminar.",
    "zh": "今天天气很好，我想去散步。",
}
base = len(enc.encode(parallel["en"]))
for k, s in parallel.items():
    print(k, len(enc.encode(s)), f"parity {len(enc.encode(s)) / base:.2f}x")

code = "def fibonacci(n):\n    if n < 2:\n        return n\n    return fibonacci(n - 1) + fibonacci(n - 2)\n"
print([enc.decode([t]) for t in enc.encode(code)])

def sample_mix(counts: dict, alpha=0.5):
    w = {k: v ** alpha for k, v in counts.items()}; z = sum(w.values())
    return {k: round(v / z, 3) for k, v in w.items()}
print(sample_mix({"en": 1000, "hi": 50, "sw": 5}))     # low-resource upweighted vs raw
```

### 🔬 Experiment & Observe
Train two RegexBPE tokenizers (vocab 4K): one on English only, one on English + Hindi text (e.g. from Wikipedia dumps). Measure the parity on parallel sentences. The mixed tokenizer cuts the Hindi cost dramatically with only a small English cost.

### ⚠️ Failure Modes & Debugging
- Whitespace runs tokenized one space at a time make Python code extremely long. Ensure `\s+(?!\S)` style patterns and enough training code to learn indentation tokens.
- Unicode normalization differences in Indic scripts (combining marks): normalize to NFC.

### 🧠 Expert Insight
- **Petrov et al. (2023), "Language Model Tokenizers Introduce Unfairness Between Languages".**
- **Rust et al. (2021):** tokenizer quality strongly affects multilingual model performance.
- Codex/StarCoder tokenizers add whitespace-run tokens; GPT-4's cl100k handles code far better than GPT-2's.

### ✅ Check Your Instinct
1. How do you improve parity for a language?
2. Why do code tokenizers need whitespace tokens?

<details><summary>Answers</summary>

1. Include more of it in the tokenizer's training data (upsampling) and/or use a larger vocab.
2. Indentation is frequent and meaningful; single-space tokens bloat code sequences.
</details>

### 📌 Recap Card
- Measure parity on parallel text.
- Upsample low-resource languages with $n^\alpha$ sampling.
- Code needs whitespace/indent tokens.

> **Core intuition:** *A tokenizer trained on one language taxes every other language.*

## 16.6 Tokenizer Pitfalls: Arithmetic, Trailing Spaces, Glitch Tokens

### 🧭 The Problem First
Why can't an LLM count the r's in "strawberry"? Why does a trailing space in a prompt degrade completions? Why did " SolidGoldMagikarp" make GPT-3 behave bizarrely?

### 💡 Intuition / Instinct
- **Spelling/counting:** "strawberry" might be 2–3 tokens. The model never "sees" the letters; it must have *memorized* the spelling of each token.
- **Arithmetic:** numbers split inconsistently ("1234" → "123"+"4", "12345" → "123"+"45"), so digit positions aren't aligned. Right-to-left or single-digit tokenization helps.
- **Trailing spaces:** in training, the space attaches to the *next* word (" world"). A prompt ending in "Hello " forces an unusual tokenization, and the model must predict "world" without its usual leading space: out of distribution.
- **Glitch tokens:** tokens that were frequent in the *tokenizer's* training data (e.g. Reddit usernames) but rare in the *model's* training data have untrained embeddings and cause bizarre behaviour.

### 🖼️ Visual Mental Model

```text
 "strawberry" → ["str", "aw", "berry"]   letters hidden inside tokens
 "Hello " + "world" : prompt ends with " " token → model sees rare pattern " " then "world"
```

### 📐 The Math, Gently
Detect undertrained tokens: small embedding norm (≈ init) or low training frequency. Land & Bartolo (2024) find these via embedding-norm and "can the model repeat this token" tests.

### 🛠️ Build It From Scratch

```python
import tiktoken
enc = tiktoken.get_encoding("gpt2")
for s in ["strawberry", " strawberry", "1234", "12345", "123456789"]:
    print(repr(s), [enc.decode([t]) for t in enc.encode(s)])
print([enc.decode([t]) for t in enc.encode("Hello ")], [enc.decode([t]) for t in enc.encode("Hello world")])

# find under-trained tokens in YOUR model later: tokens that never appear in the training ids
import torch
def unused_tokens(train_ids: torch.Tensor, V: int):
    counts = torch.bincount(train_ids.flatten(), minlength=V)
    return (counts == 0).nonzero().flatten().tolist()
```

### 🔬 Experiment & Observe
After training your GPT (Ch 20), compare the embedding norms of tokens that never appeared in training against frequent ones: the unused ones stay near initialization. Those are your glitch-token candidates.

### ⚠️ Failure Modes & Debugging
- Strip trailing whitespace from prompts, or use "token healing" (back up one token and constrain generation to extend it).
- Train the tokenizer on the *same distribution* as the model to avoid glitch tokens.

### 🧠 Expert Insight
- **Rumbelow & Watkins (2023):** "SolidGoldMagikarp" glitch tokens.
- **Land & Bartolo (2024), "Fishing for Magikarp":** systematic detection of undertrained tokens.
- **Singh & Strouse (2024):** right-to-left digit tokenization improves arithmetic.
- Llama 1/2 split all digits into single tokens for this reason.

### ✅ Check Your Instinct
1. Why can't models easily count letters?
2. What causes glitch tokens?
3. *(Coding)* Implement "token healing": remove the last prompt token and only allow next tokens whose string starts with it.

<details><summary>Answers</summary>

1. They see token ids, not characters; letter-level info must be memorized per token.
2. A mismatch between the tokenizer's training data and the model's training data, which leaves embeddings untrained.
3. Build an allowed-id mask from `[i for i in range(V) if vocab[i].startswith(last_bytes)]` and apply it to the first generated step.
</details>

### 📌 Recap Card
- Spelling and arithmetic are hampered by tokenization.
- Trailing spaces cause out-of-distribution tokenization.
- Glitch tokens = untrained embeddings.
- Train the tokenizer on the model's data distribution.

> **Core intuition:** *The model only knows the world through its tokens, and every quirk of the tokenizer becomes a quirk of the model.*

## 16.7 Training a Tokenizer on YOUR Data and Measuring Compression

### 🧭 The Problem First
For the Capstone you'll pick a domain (medical notes, code, another language). An off-the-shelf tokenizer may waste tokens on your domain's vocabulary.

### 💡 Intuition / Instinct
Train on a representative sample (tens of MB to a few GB), include the special tokens you'll need, and **measure**: bytes/token on held-out domain text, the fraction of words split into more than 3 tokens, and parity if multilingual. Compare against a strong general tokenizer (cl100k, the Llama 3 tokenizer).

### 🖼️ Visual Mental Model

```text
 sample corpus → pre-tokenize (regex) → count chunks → fast BPE → add specials → save JSON
       → evaluate: bytes/token, fertility (tokens/word), OOD parity
```

### 📐 The Math, Gently
**Fertility** = tokens per whitespace word. English BPE is ~1.2–1.4; above 2 suggests a poor fit.
bytes/token = total UTF-8 bytes / total tokens (higher is better).

### 🛠️ Build It From Scratch

```python
# scripts/train_tokenizer.py
import argparse, glob, random, regex as re
from collections import Counter
from nanoforge.tokenizer.regex_bpe import RegexBPE, GPT4_PATTERN
from nanoforge.tokenizer.fast_train import train_bpe_fast

SPECIALS = ["<|endoftext|>", "<|pad|>", "<|im_start|>", "<|im_end|>", "<|tool|>"]

def iter_texts(pattern, max_bytes):
    files = glob.glob(pattern, recursive=True); random.shuffle(files); seen = 0
    for f in files:
        t = open(f, encoding="utf-8", errors="ignore").read()
        yield t; seen += len(t.encode())
        if seen >= max_bytes: return

def evaluate(tok, texts):
    nb = sum(len(t.encode()) for t in texts); nt = sum(len(tok.encode_ordinary(t)) for t in texts)
    nw = sum(len(t.split()) for t in texts)
    return {"bytes_per_token": nb / nt, "fertility": nt / max(nw, 1)}

if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("--input", required=True); ap.add_argument("--vocab", type=int, default=8192)
    ap.add_argument("--max_bytes", type=int, default=200_000_000); ap.add_argument("--out", required=True)
    a = ap.parse_args()
    texts = list(iter_texts(a.input, a.max_bytes)); random.shuffle(texts)
    held, train = texts[: max(1, len(texts) // 50)], texts[max(1, len(texts) // 50):]
    cc = Counter()
    rx = re.compile(GPT4_PATTERN)
    for t in train: cc.update(rx.findall(t))
    tok = RegexBPE()
    tok.merges = train_bpe_fast(cc, a.vocab - len(SPECIALS))
    for (x, y), i in sorted(tok.merges.items(), key=lambda kv: kv[1]): tok.vocab[i] = tok.vocab[x] + tok.vocab[y]
    tok.register_special_tokens(SPECIALS)
    tok.save(a.out)
    print("held-out:", evaluate(tok, held), "vocab:", tok.vocab_size)
```

### 🔬 Experiment & Observe
Compare your domain tokenizer against `tiktoken` cl100k on held-out domain text. A good domain tokenizer at 8K–32K often matches or beats cl100k's compression *on that domain*, while being much smaller.

### ⚠️ Failure Modes & Debugging
- Training on a non-representative sample (only headers, or only one sub-domain).
- Forgetting special tokens and then needing to resize the model later.
- Vocab size not aligned: we reserve the special ids inside the target vocab, then pad the *model's* V to a multiple of 64.

### 🧠 Expert Insight
Domain models (e.g. BioGPT, Galactica, StarCoder) trained their own tokenizers. When *fine-tuning* an existing model you normally keep its tokenizer (changing it breaks the embeddings), unless you do vocabulary extension with continued pretraining.

### ✅ Check Your Instinct

2. Why keep the original tokenizer when fine-tuning?

<details><summary>Answers</summary>

1. Average tokens per word, i.e. how finely words are split.
2. The model's embeddings are tied to its token ids; a new tokenizer invalidates them.

### 📌 Recap Card
- Train on a representative sample; include the special tokens.
- Evaluate bytes/token, fertility, parity.
- Keep the tokenizer fixed when fine-tuning existing models.
