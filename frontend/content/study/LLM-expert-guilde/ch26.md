## 26.1 Power Laws: Loss vs Parameters, Data, Compute

### 🧭 The Problem First
You have a fixed budget. Will doubling the model size help? By how much? Without a quantitative law, every decision is a guess.

### 💡 Intuition / Instinct
Empirically, test loss falls as a **power law** in model size N, data D and compute C, a straight line on a log–log plot, across many orders of magnitude. Each 10× more compute buys a predictable, *diminishing* loss improvement. Loss never goes below an **irreducible** floor E (the entropy of the text, Ch 5.4).

### 🖼️ Visual Mental Model

```text
 log loss
   │●
   │  ●
   │    ●
   │      ●               straight line on log-log
   │        ●  ●  ● ● ●──── approaches the floor E
   └────────────────────── log compute
```

### 📐 The Math, Gently
Kaplan-style single-variable laws: $L(N) = (N_c/N)^{\alpha_N}$, with $\alpha_N ≈ 0.076$ and similar forms for D and C.
Chinchilla parametric form: $L(N, D) = E + \frac{A}{N^\alpha} + \frac{B}{D^\beta}$, with fitted $E ≈ 1.69$, $A ≈ 406.4$, $B ≈ 410.7$, $\alpha ≈ 0.34$, $\beta ≈ 0.28$ (Hoffmann et al., 2022, MassiveText tokenizer; the numbers are dataset- and tokenizer-specific).
Example: N = 1B, D = 20B: $L ≈ 1.69 + 406.4/10^{9·0.34} + 410.7/(2·10^{10})^{0.28}$. $10^{3.06} ≈ 1148$ → 0.354; $(2·10^{10})^{0.28} = e^{0.28·23.72} ≈ 766$ → 0.536. Total ≈ 2.58.

### 🛠️ Build It From Scratch

```python
# nanoforge/scaling.py
import numpy as np
CHINCHILLA = dict(E=1.69, A=406.4, B=410.7, alpha=0.34, beta=0.28)
def chinchilla_loss(N, D, p=CHINCHILLA):
    return p["E"] + p["A"] / N ** p["alpha"] + p["B"] / D ** p["beta"]
for N in [1e8, 1e9, 1e10, 7e10]:
    print(f"N={N:.0e}: " + "  ".join(f"D={D:.0e}->{chinchilla_loss(N, D):.3f}" for D in [1e10, 1e11, 1e12]))
```

### 🔬 Experiment & Observe
Notice that at fixed N, adding data saturates (the $A/N^\alpha$ term remains), and at fixed D, adding parameters saturates. You need to grow both.

### ⚠️ Failure Modes & Debugging
- Laws fitted on one dataset/tokenizer don't transfer numerically to another. Refit (26.4).
- Extrapolating far beyond the fitted range is risky: fit over ≥ 2 orders of magnitude.

### 🧠 Expert Insight
- **Hestness et al. (2017):** early deep learning scaling laws.
- **Kaplan et al. (2020), "Scaling Laws for Neural Language Models".**
- **Hoffmann et al. (2022), Chinchilla.**
- Scaling laws also hold for downstream *losses*; benchmark accuracies can look "emergent" because of nonlinear metrics (Schaeffer et al., 2023).

### ✅ Check Your Instinct
1. What does the E term represent?
2. Why does adding only data eventually stop helping?

<details><summary>Answers</summary>

1. Irreducible loss: the entropy of the data.
2. The $A/N^\alpha$ term (model capacity) remains.
</details>

### 📌 Recap Card
- Loss follows power laws in N, D, C.
- $L = E + A/N^\alpha + B/D^\beta$.
- Diminishing but predictable returns; refit per dataset.

> **Core intuition:** *Each 10× of compute buys a predictable, smaller slice of loss.*

## 26.2 Kaplan vs Chinchilla: The ~20 Tokens per Parameter Rule

### 🧭 The Problem First
Given compute C, how should you split it between model size N and training tokens D? GPT-3 (175B params, 300B tokens) followed Kaplan's advice to prefer big models. Chinchilla (70B params, 1.4T tokens) used the *same* compute as Gopher (280B) and beat it handily.

### 💡 Intuition / Instinct
Minimize $L(N, D)$ subject to $C = 6ND$. Chinchilla found that **N and D should grow in equal proportion**: roughly $N_{opt} \propto C^{0.5}$ and $D_{opt} \propto C^{0.5}$, which works out to **about 20 tokens per parameter**. Kaplan's earlier result (favouring N) was partly an artefact of not tuning the lr schedule to each run length.

**But:** "compute-optimal" minimizes *training* cost for a given loss. If you'll serve the model to millions of users, a *smaller model trained on far more tokens* (Llama 3 8B: 15T tokens ≈ 1,900 tokens/param) is cheaper overall, because inference costs dominate.

### 🖼️ Visual Mental Model

```text
 at fixed compute (isoFLOP curve):
 loss
   │ \                /
   │  \      ●       /     ● = optimal N for this compute
   │   \___/  \_____/
   └──────────────────── N (log)
   too small: undertrained capacity   too big: too few tokens
```

### 📐 The Math, Gently
Lagrangian with $D = C/(6N)$: $\frac{d}{dN}\left[\frac{A}{N^\alpha} + \frac{B(6N)^\beta}{C^\beta}\right] = 0$ gives $N_{opt} = G\left(\frac{C}{6}\right)^{\frac{\beta}{\alpha+\beta}}$ with $G = \left(\frac{\alpha A}{\beta B}\right)^{\frac{1}{\alpha+\beta}}$.
With α = 0.34, β = 0.28: exponent ≈ 0.45 (the paper's other methods give ≈ 0.5).

### 🛠️ Build It From Scratch

```python
# nanoforge/scaling.py (append)
def chinchilla_optimal(C, p=CHINCHILLA):
    a, b = p["alpha"], p["beta"]
    G = (a * p["A"] / (b * p["B"])) ** (1 / (a + b))
    N = G * (C / 6) ** (b / (a + b)); D = C / (6 * N)
    return N, D

def isoflop_curve(C, Ns, p=CHINCHILLA):
    return [(N, C / (6 * N), chinchilla_loss(N, C / (6 * N), p)) for N in Ns]

for C in [1e18, 1e20, 1e22, 1e24]:
    N, D = chinchilla_optimal(C)
    print(f"C={C:.0e}: N_opt={N:.2e} D_opt={D:.2e} tokens/param={D/N:.1f}")
```

### 🔬 Experiment & Observe
Plot `isoflop_curve` for C = 1e19 with N from 1e7 to 1e11. The U-shape has a flat bottom, so being within ~2× of the optimal N costs little. Also note that the fitted-parameter optimum gives tokens/param varying with C; the "20×" rule is an approximation.

### ⚠️ Failure Modes & Debugging
- Using Chinchilla ratios for deployment-oriented models: you'll overspend on inference. Decide on the objective first.
- Very high tokens/param needs enough *unique* data; repeated data yields diminishing returns beyond ~4 epochs (Muennighoff et al., 2023).

### 🧠 Expert Insight
- **Hoffmann et al. (2022):** three estimation methods (fixed-N envelopes, isoFLOP profiles, parametric fit), all giving ≈ equal scaling of N and D.
- **Besiroglu et al. (2024):** a replication found issues in the parametric fit, and the corrected fit is closer to ~20 tokens/param.
- **Sardana & Frankle (2023), "Beyond Chinchilla-Optimal":** accounting for inference demand favours smaller, longer-trained models.

### ✅ Check Your Instinct
1. Chinchilla-optimal tokens for a 7B model?
2. Why did Llama 3 train 8B on 15T tokens?

<details><summary>Answers</summary>

1. ≈ 140B tokens.
2. To minimize inference cost at a given quality; a smaller model trained longer keeps improving.
</details>

### 📌 Recap Card
- Compute-optimal: N and D scale together, ≈ 20 tokens/param.
- The isoFLOP curve is flat near the optimum.
- Deployment-optimal models are smaller and trained much longer.

> **Core intuition:** *A model's size and its reading list should grow together, unless you'll be paying for its answers forever.*

## 26.3 The FLOPs ≈ 6ND Budget Calculator

### 🧭 The Problem First
"Can I train a 125M model on 10B tokens on my GPU this week?" You need a fast, reliable estimate of the time and cost.

### 💡 Intuition / Instinct
Training FLOPs ≈ 6ND (Ch 19.6). Divide by your *achieved* throughput (peak × MFU). That's your wall-clock time. Multiply by $/GPU-hour for the cost.

### 🖼️ Visual Mental Model

```text
 C = 6 · N · D  ──÷ (peak × MFU × n_gpus)──▶ seconds ──× $/hr──▶ cost
```

### 📐 The Math, Gently
Example: N = 125M, D = 2.5B (20×): C = 6 × 1.25e8 × 2.5e9 = 1.875e18 FLOPs.
One RTX 4090 at 165 TFLOPs × 40% MFU = 66 TFLOP/s: 1.875e18 / 6.6e13 ≈ 28,400 s ≈ **7.9 hours**. ✓ Feasible.
Llama 3 405B (15.6T tokens): 6 × 4.05e11 × 1.56e13 ≈ 3.8e25 FLOPs. On 16K H100s at ~40% MFU (~400 TFLOP/s each): 3.8e25 / 6.4e18 ≈ 5.9e6 s ≈ 69 days.

### 🛠️ Build It From Scratch

```python
# nanoforge/scaling.py (append)
GPU_PEAK_BF16 = {"T4": 65e12, "L4": 121e12, "RTX3090": 71e12, "RTX4090": 165e12, "A100": 312e12, "H100": 989e12}
def budget(N, D, gpu="RTX4090", n_gpus=1, mfu=0.4, usd_per_gpu_hour=0.5, T=None, L=None, C_model=None):
    flops = 6 * N * D + (6 * L * T * C_model * D if T else 0)
    secs = flops / (GPU_PEAK_BF16[gpu] * mfu * n_gpus)
    return {"flops": f"{flops:.2e}", "hours": round(secs / 3600, 2), "days": round(secs / 86400, 2),
            "usd": round(secs / 3600 * n_gpus * usd_per_gpu_hour, 2)}
print(budget(125e6, 2.5e9))
print(budget(1.1e9, 22e9, gpu="A100", n_gpus=8, usd_per_gpu_hour=1.5))
```

### 🔬 Experiment & Observe
Compare the calculator's prediction with your actual micro run from Ch 24 (use your measured MFU). They should agree within ~10%.

### ⚠️ Failure Modes & Debugging
- Forgetting the attention term for long contexts (T ≳ C).
- Using the vendor's *sparse* peak FLOPs (2× the dense figure) inflates the MFU.
- Ignoring evaluation, checkpointing and restarts overhead (add 5–15%).

### 🧠 Expert Insight
Every frontier model card now reports training compute in FLOPs; EU and US policy thresholds (e.g. 10²⁵–10²⁶ FLOPs) are defined in these units.

## 26.4 Fitting Your Own Mini Scaling Law

### 🧭 The Problem First
Published constants don't apply to *your* data and tokenizer. Before a big Capstone run, can you predict its loss from cheap small runs?

### 💡 Intuition / Instinct
Train a *family* of small models (e.g. 5 sizes × 3 token budgets), each with its own tuned or appropriately scaled lr and a schedule matched to its length (WSD makes this cheap: one run with multiple decays). Fit $L(N, D) = E + A/N^\alpha + B/D^\beta$ to the final losses with a robust (Huber) loss in log space. Extrapolate to your target, and validate on one held-out, larger run.

### 🖼️ Visual Mental Model

```text
 runs:  N ∈ {1M, 3M, 10M, 30M}  ×  D ∈ {20N, 50N}      → ~8 cheap runs
 fit (E, A, α, B, β) → predict L(100M, 2B) → run it → compare
```

### 📐 The Math, Gently
Fit in log space: minimize $\sum_i \text{Huber}_\delta\big(\log \hat L_i - \log L_i\big)$ with $\hat L = \exp(e) + \exp(a - \alpha\log N) + \exp(b - \beta\log D)$ (a LogSumExp parameterization keeps the terms positive).

### 🛠️ Build It From Scratch

```python
# nanoforge/scaling.py (append)
import torch
def fit_scaling_law(Ns, Ds, Ls, steps=5000, lr=0.05, delta=1e-3, inits=8, seed=0):
    Ns, Ds, Ls = (torch.tensor(v, dtype=torch.float64) for v in (Ns, Ds, Ls))
    best = None; g = torch.Generator().manual_seed(seed)
    for _ in range(inits):
        p = torch.randn(5, dtype=torch.float64, generator=g) * 0.5 + torch.tensor([0.5, 5.0, 0.3, 5.0, 0.3], dtype=torch.float64)
        p.requires_grad_(True); opt = torch.optim.Adam([p], lr=lr)
        for _ in range(steps):
            e, a, al, b, be = p
            pred = torch.logsumexp(torch.stack([e.expand_as(Ns), a - al * Ns.log(), b - be * Ds.log()]), 0)
            loss = torch.nn.functional.huber_loss(pred, Ls.log(), delta=delta)
            opt.zero_grad(); loss.backward(); opt.step()
        if best is None or loss.item() < best[0]: best = (loss.item(), p.detach().clone())
    e, a, al, b, be = best[1].tolist()
    return dict(E=np.exp(e), A=np.exp(a), alpha=al, B=np.exp(b), beta=be)

# sanity check on synthetic data from known constants
rng = np.random.default_rng(0)
Ns = np.repeat([1e6, 3e6, 1e7, 3e7], 3); Ds = Ns * np.tile([10, 30, 100], 4)
Ls = chinchilla_loss(Ns, Ds) * np.exp(rng.normal(0, 0.005, len(Ns)))
print(fit_scaling_law(Ns, Ds, Ls))
```

Workflow for real runs:

```bash
# scripts/scaling_sweep.sh: sizes x budgets on your data (edit CONFIGS to add tiny sizes)
for size in nano micro; do for mult in 20 50; do
  python -m nanoforge.train --model_size=$size --max_steps=<computed from mult*N/tokens_per_step> --out_dir=checkpoints/sweep_${size}_${mult}
done; done
```

### 🔬 Experiment & Observe
With your fitted law, predict the val loss of the Capstone "mini" model *before training it*. Afterwards, compare. Getting within ~0.05 nats is a great result and gives you real engineering confidence.

### ⚠️ Failure Modes & Debugging
- Using the same lr schedule *length* for all runs (a Kaplan-style mistake): shorter runs must decay fully within their own budget.
- Too-small models (< 1M params) behave differently (embedding-dominated). Use the non-embedding N, or start at ~1M.
- Fits are ill-conditioned with few points; fix E from a prior if needed.

### 🧠 Expert Insight
Frontier labs predict their flagship models' losses from runs using 1,000–10,000× less compute (GPT-4 technical report, Fig. 1). The **Llama 3** paper fit scaling laws on *downstream* metrics too, via a two-step loss → accuracy mapping.

### ✅ Check Your Instinct
1. Why must each small run have its own full LR decay?
2. Why fit in log space?

<details><summary>Answers</summary>

1. The final loss depends heavily on completing the decay; truncated schedules under-estimate what each (N, D) can reach.
2. The losses span scales multiplicatively; log-space residuals weight the runs evenly and match the power-law structure.
</details>

### 📌 Recap Card
- Sweep small N × D with properly scheduled runs.
- Fit $E + A/N^\alpha + B/D^\beta$ in log space with Huber.
- Validate on one larger run before the big one.

> **Core intuition:** *Spend 1% of your compute learning how the other 99% will behave.*

## 26.5 Hyperparameter Selection, Batch Size, and the Critical Batch Size

### 🧭 The Problem First
What learning rate, batch size, warmup and weight decay should a 125M model use? A 1B model? Tuning every size from scratch is too expensive.

### 💡 Intuition / Instinct
- **Learning rate:** larger models need *smaller* lrs (in standard parameterization). Typical AdamW peaks: ~1e-3 to 3e-3 at 10–100M params, ~6e-4 at 125M–350M, ~3e-4 at 1–7B, ~1.5e-4 at 70B.
- **Batch size:** bigger batches reduce gradient noise, but past the **critical batch size** $B_{crit}$, doubling the batch no longer halves the number of steps needed. You waste compute. $B_{crit}$ grows as the loss falls (and roughly with the amount of training).
- **Warmup:** ~1–5% of steps. **Weight decay:** 0.1. **β₂:** 0.95. **Clip:** 1.0.

### 🖼️ Visual Mental Model

```text
 steps to reach loss L vs batch size:
 steps
   │\
   │ \___              ← perfect scaling region (B < B_crit): 2× batch = ½ steps
   │     \____
   │          ‾‾‾───── ← diminishing returns (B > B_crit): 2× batch ≈ same steps
   └──────────────────── batch size (log)
```

### 📐 The Math, Gently
McCandlish et al. (2018): $\frac{S}{S_{min}} - 1 = \left(\frac{E}{E_{min}} - 1\right)^{-1}$, with the trade-off governed by $B_{noise} = \frac{\text{tr}(\Sigma)}{|G|^2}$ (gradient variance / squared gradient norm).
Kaplan: $B_{crit}(L) ≈ B_*/L^{1/\alpha_B}$, with $B_* ≈ 2\times10^8$ tokens and $\alpha_B ≈ 0.21$ (their tokenizer and data). At L = 3 nats, B_crit is roughly a few hundred thousand tokens; at L = 2, millions.

### 🛠️ Build It From Scratch

```python
# nanoforge/scaling.py (append): estimate the gradient noise scale B_noise from two batch sizes
def gradient_noise_scale(model, get_batch, loss_fn, B_small=4, B_big=64, trials=8):
    """McCandlish 'simple noise scale': uses |G|^2 estimates at two batch sizes."""
    def grad_sq(B):
        tot = 0.0
        for _ in range(trials):
            model.zero_grad(); x, y = get_batch(B); loss_fn(model, x, y).backward()
            tot += sum((p.grad.float() ** 2).sum().item() for p in model.parameters() if p.grad is not None)
        return tot / trials
    gs, gb = grad_sq(B_small), grad_sq(B_big)
    G2 = (B_big * gb - B_small * gs) / (B_big - B_small)          # unbiased |G|^2
    S = (gs - gb) / (1 / B_small - 1 / B_big)                     # tr(Sigma)
    return S / max(G2, 1e-12)                                      # B_noise in sequences
```

### 🔬 Experiment & Observe
Measure $B_{noise}$ at steps 100, 1000 and 5000 of your micro run: it grows as the loss falls. Then run a batch sweep (micro_batch × accum = 8, 32, 128, 512 sequences) with the lr scaled by √(batch ratio) for Adam, and plot the steps to reach val loss 1.6. You'll see the perfect-scaling region end near your measured $B_{noise}$.

### ⚠️ Failure Modes & Debugging
- Scaling the lr linearly with batch for Adam can overshoot; √-scaling is a safer starting point (then tune).
- A huge batch with a small dataset gives too few optimizer steps, so the model underfits.

### 🧠 Expert Insight
- **McCandlish et al. (2018)**, **Kaplan et al. (2020)** for B_crit.
- **DeepSeek LLM (2024):** fitted power laws for the optimal lr and batch *as functions of compute*: $B_{opt}$ increases and $\eta_{opt}$ decreases with C.
- **Zhang et al. (2024), "How Does Critical Batch Size Scale in Pre-training?":** B_crit scales primarily with data size.

### ✅ Check Your Instinct
1. What happens above the critical batch size?
2. How should the lr change with model size in standard parameterization?

<details><summary>Answers</summary>

1. Larger batches no longer reduce the steps proportionally, which wastes compute.
2. Decrease it as models get wider/larger.
</details>

### 📌 Recap Card
- Defaults: AdamW β = (0.9, 0.95), wd = 0.1, clip = 1, warmup ~1–5%.
- The lr decreases with model size; the batch can grow as the loss falls.
- Measure the gradient noise scale to find B_crit.

> **Core intuition:** *A bigger batch is only worth it while its extra samples still tell you something new.*

## 26.6 µP: Transferring Hyperparameters From Small to Large

### 🧭 The Problem First
The optimal lr shifts as you widen a model, so tuning on a small proxy doesn't transfer, and tuning the big model directly is unaffordable.

### 💡 Intuition / Instinct
**Maximal Update Parameterization (µP)** rescales the initializations, per-layer learning rates and output multipliers with width so that *every layer's update size stays constant as width grows*. Then the optimal hyperparameters (lr, init scale) become approximately **width-independent**: tune a 10M model, then train a 1B one with the same values ("µTransfer").

The key rules (for Adam, relative to a base width $C_0$, with width multiplier $m = C/C_0$):
- **hidden (matrix-like) weights:** init std ∝ $1/\sqrt{C}$, and **Adam lr ∝ 1/m**;
- **output logits:** multiply by $1/m$ (or init the readout ∝ 1/C);
- **attention scores:** scale by $1/d$ instead of $1/\sqrt d$;
- **embeddings:** lr and init constant in width.

### 🖼️ Visual Mental Model

```text
 standard param:   optimal lr  │ ●               µP:   optimal lr │ ● ● ● ●
                                │   ●                             │
                                │     ●  (shifts with width)       │ (flat across width)
                                └──────── width                    └──────── width
```

### 📐 The Math, Gently
Intuition: with Adam, each weight's update is ~lr regardless of the gradient scale. A matrix update $\Delta W$ with entries ~lr, applied to an input with C coordinates, changes the output by ~lr·C (the coordinates add coherently after training aligns them). To keep the output change O(1), you need lr ∝ 1/C for hidden matrices.

### 🛠️ Build It From Scratch

```python
# nanoforge/mup.py: minimal µP for our GPT (Adam), relative to base width C0
import torch
def mup_param_groups(model, base_lr, base_width, weight_decay=0.1):
    m = model.cfg.n_embd / base_width
    hidden, vector, emb = [], [], []
    for n, p in model.named_parameters():
        if n.endswith("wte.weight") or n.endswith("wpe.weight"): emb.append(p)
        elif p.dim() >= 2: hidden.append(p)
        else: vector.append(p)
    return [
        {"params": hidden, "lr": base_lr / m, "weight_decay": weight_decay, "lr_mult": 1 / m},
        {"params": emb,    "lr": base_lr,     "weight_decay": weight_decay, "lr_mult": 1.0},
        {"params": vector, "lr": base_lr,     "weight_decay": 0.0,          "lr_mult": 1.0},
    ]
# Also required: logits = lm_head(x) / m  (output multiplier), attention scale 1/D (not 1/sqrt(D)),
# and hidden init std = sigma_base * sqrt(base_width / width). With tied embeddings, the output multiplier
# handles the readout scaling. When applying the LR schedule, set g["lr"] = lr_at(step) * g["lr_mult"].
```

### 🔬 Experiment & Observe
**The coordinate check:** train widths 128, 256, 512, 1024 for 10 steps and plot the mean |activation| of each layer vs width. In µP these curves are flat; in standard parameterization some blow up with width. Then sweep the lr for widths 128 and 512 under both parameterizations: under µP the optimum lines up.

### ⚠️ Failure Modes & Debugging
- Partial µP (only the lr scaling, forgetting the output multiplier) breaks the transfer. Always run the coordinate check.
- µP transfers across *width*; depth transfer needs extra rules (depth-µP: scale the residual branches by $1/\sqrt{L}$).

### 🧠 Expert Insight
- **Yang et al. (2021), "Tensor Programs V: Tuning Large Neural Networks via Zero-Shot Hyperparameter Transfer".**
- Cerebras-GPT, MiniCPM and others used µP.
- **Everett et al. (2024):** with proper per-layer lr scaling, several parameterizations can transfer; the key is the layer-wise lr.

### ✅ Check Your Instinct
1. In µP with Adam, how does a hidden layer's lr scale with width?
2. What diagnostic verifies a µP implementation?

<details><summary>Answers</summary>

1. ∝ 1/width.
2. The coordinate check: activation scales stay flat across widths.
</details>

### 📌 Recap Card
- µP makes the optimal hyperparameters width-independent.
- Adam: hidden lr ∝ 1/m, output ÷ m, attention 1/d.
- Verify with coordinate checks; tune small, transfer big.

> **Core intuition:** *Parameterize so that every layer learns at the same speed at any width, and one tuning serves all sizes.*
