## 29.1 Kernel Fusion and Why Memory Traffic Dominates

### 🧭 The Problem First
`y = gelu(x @ W + b)` in eager PyTorch launches three kernels: matmul, add, gelu. The add and gelu each read the full (B, T, 4C) tensor from HBM and write it back, which is pure memory traffic.

### 💡 Intuition / Instinct
**Fusion** = do several operations in one kernel while the data sits in registers/SRAM: read once, compute add + gelu + dropout, write once. For memory-bound chains, fusing k ops gives up to ~k× speedup. Compilers (`torch.compile`, XLA) do this automatically; hand-written kernels do it for complex patterns (attention, cross-entropy).

### 🖼️ Visual Mental Model

```text
 unfused:  HBM→[add]→HBM→[gelu]→HBM→[dropout]→HBM    (6 transfers of the tensor)
 fused:    HBM→[add+gelu+dropout]→HBM                 (2 transfers)
```

### 📐 The Math, Gently
For a tensor of S bytes with k memory-bound elementwise ops: unfused traffic ≈ 2kS, fused ≈ 2S (in + out).

### 🛠️ Build It From Scratch

```python
import torch, torch.nn.functional as F, time
def bench(fn, *a, it=100):
    for _ in range(10): fn(*a)
    torch.cuda.synchronize(); t = time.time()
    for _ in range(it): fn(*a)
    torch.cuda.synchronize(); return (time.time() - t) / it * 1e3
def unfused(x, b): return F.dropout(F.gelu(x + b), 0.1, True)
fused = torch.compile(unfused)
if torch.cuda.is_available():
    x = torch.randn(32, 1024, 3072, device="cuda", dtype=torch.bfloat16); b = torch.randn(3072, device="cuda", dtype=torch.bfloat16)
    print(f"eager {bench(unfused, x, b):.2f} ms | compiled {bench(fused, x, b):.2f} ms")
```

### 🔬 Experiment & Observe
Expect a 2–3× speedup from fusion on this chain. Inspect the generated Triton code: `TORCH_LOGS="output_code" python script.py`.

### ⚠️ Failure Modes & Debugging
The first call to a compiled function is slow (compilation). Always warm up before timing.

### 🧠 Expert Insight
Fused kernels in production LLM training include fused LayerNorm/RMSNorm, fused RoPE, fused SwiGLU, **fused linear + cross-entropy** (never materializing the logits), and fused AdamW (`fused=True`).

### ✅ Check Your Instinct
1. Why does fusion help memory-bound ops but barely help large matmuls?

<details><summary>Answers</summary>

1. Memory-bound ops are limited by HBM traffic, which fusion reduces; large matmuls are compute-bound already.
</details>

### 📌 Recap Card
- Fusion: read once, compute many, write once.
- Big wins on elementwise/norm chains.
- Compilers fuse automatically.

> **Core intuition:** *Don't send data back to the warehouse between every step on the assembly line.*

## 29.2 FlashAttention: Tiling and Online Softmax

### 🧭 The Problem First
Standard attention materializes S = QKᵀ of shape (B, H, T, T) in HBM, then the softmax (read/write T²), then P @ V. At T = 8K with 32 heads, that is 2 billion entries per sequence. The memory is O(T²) and the traffic dominates the runtime.

### 💡 Intuition / Instinct
Never materialize the T×T matrix. Split Q into row-blocks and K/V into column-blocks that fit in SRAM. For each Q block, stream through the K/V blocks, computing partial scores in SRAM and maintaining a **running (online) softmax**: a running max m, a running normalizer ℓ, and a running output accumulator. When a new block arrives with a larger max, rescale the previous accumulators by $e^{m_{old} - m_{new}}$. At the end, divide by ℓ. The result is *exact*, not approximate. Backward recomputes the scores blockwise (cheap) instead of storing them.

### 🖼️ Visual Mental Model

```text
          K/V blocks →
 Q blk 1 [■][■][■][■]   for each (Q blk, K blk): s = q kᵀ in SRAM → update (m, ℓ, acc)
 Q blk 2 [■][■][■][■]   causal: skip blocks above the diagonal entirely
 ...
 HBM traffic: O(T²·d²/SRAM) instead of O(T²) score writes; memory O(T) instead of O(T²)
```

### 📐 The Math, Gently
Online softmax, for scores arriving in chunks $s^{(1)}, s^{(2)}, \dots$:
$m^{new} = \max(m, \max s^{(j)})$
$\ell^{new} = \ell\, e^{m - m^{new}} + \sum e^{s^{(j)} - m^{new}}$
$o^{new} = o\, e^{m - m^{new}} + \sum_k e^{s^{(j)}_k - m^{new}} v_k$
Final: $\text{out} = o/\ell$. It is identical to $\text{softmax}(s)V$, which you can prove by induction.

### 🛠️ Build It From Scratch

```python
# nanoforge/kernels/flash_sim.py : FlashAttention forward, simulated in PyTorch (block loops)
import math, torch
def flash_attention_sim(q, k, v, block_q=64, block_k=64, causal=True):
    """q,k,v: (T, D). Exact attention via tiling + online softmax. Returns (T, D)."""
    T, D = q.shape; scale = 1 / math.sqrt(D)
    out = torch.zeros_like(q)
    for qs in range(0, T, block_q):
        qb = q[qs:qs + block_q] * scale                       # (bq, D) "loaded into SRAM"
        m = torch.full((qb.size(0),), float("-inf"))           # running max
        l = torch.zeros(qb.size(0))                            # running normalizer
        acc = torch.zeros(qb.size(0), D)                       # running output
        k_end = min(T, qs + block_q) if causal else T
        for ks in range(0, k_end, block_k):
            kb, vb = k[ks:ks + block_k], v[ks:ks + block_k]
            s = qb @ kb.T                                      # (bq, bk) scores in SRAM
            if causal:
                qi = torch.arange(qs, qs + qb.size(0))[:, None]; kj = torch.arange(ks, ks + kb.size(0))[None, :]
                s = s.masked_fill(kj > qi, float("-inf"))
            m_new = torch.maximum(m, s.max(1).values)
            p = torch.exp(s - m_new[:, None])                  # (bq, bk)
            corr = torch.exp(m - m_new)                        # rescale old stats
            l = l * corr + p.sum(1)
            acc = acc * corr[:, None] + p @ vb
            m = m_new
        out[qs:qs + block_q] = acc / l[:, None]
    return out

torch.manual_seed(0)
T, D = 256, 32
q, k, v = torch.randn(T, D), torch.randn(T, D), torch.randn(T, D)
ref = torch.softmax((q @ k.T / math.sqrt(D)).masked_fill(torch.triu(torch.ones(T, T, dtype=torch.bool), 1), float("-inf")), -1) @ v
print("max diff:", (flash_attention_sim(q, k, v) - ref).abs().max().item())    # ~1e-6
```

### 🔬 Experiment & Observe
- Change the block sizes: the result is identical (it's exact).
- Compare the memory use of manual attention vs `F.scaled_dot_product_attention` at T = 4096, 8192 on GPU. The manual version runs out of memory; SDPA (flash) doesn't.

### ⚠️ Failure Modes & Debugging
- The flash kernel only activates for supported dtypes (fp16/bf16), head dims (≤ 256), and mask types. A custom boolean mask can force the slower "math" path. Check with `torch.backends.cuda.sdp_kernel` contexts or the profiler.
- Numerical differences vs manual attention of ~1e-3 in bf16 are normal.

### 🧠 Expert Insight
- **Dao et al. (2022), FlashAttention:** IO-aware exact attention.
- **FlashAttention-2 (2023):** better parallelism (~2× faster).
- **FlashAttention-3 (2024):** Hopper-specific async + FP8.
- **Milakov & Gimelshein (2018):** online softmax.
- **FlexAttention (PyTorch, 2024):** write custom masks/scores (document masks, ALiBi, soft-capping) as Python functions compiled into flash-style kernels.

### ✅ Check Your Instinct
1. Is FlashAttention an approximation?
2. Why does the old accumulator get multiplied by $e^{m_{old}-m_{new}}$?
3. *(Coding)* Extend `flash_attention_sim` to return the log-sum-exp per row (needed by the backward pass).

<details><summary>Answers</summary>

1. No, it's exact up to floating-point rounding.
2. The earlier terms were exponentiated relative to the old max; rescaling puts them relative to the new max.
3. Return `m + torch.log(l)`.
</details>

### 📌 Recap Card
- Tile Q, K, V into SRAM; never write T×T to HBM.
- Online softmax with a running (m, ℓ, acc) is exact.
- Memory O(T); much faster; recompute in backward.

> **Core intuition:** *Attention can be computed a block at a time if you keep a running softmax.*

## 29.3 `torch.compile` and CUDA Graphs

### 🧭 The Problem First
Eager PyTorch runs Python for every op: overhead of 5–20 µs per op, thousands of ops per step, and no cross-op optimization. Small models in particular are **overhead-bound**.

### 💡 Intuition / Instinct
`torch.compile(model)` traces your Python into a graph (TorchDynamo), then generates fused Triton kernels (TorchInductor). **CUDA graphs** (`mode="reduce-overhead"`) record a whole sequence of kernel launches once and replay them with a single CPU call, which eliminates launch overhead (great for inference and small models).

### 🖼️ Visual Mental Model

```text
 eager:    Python → op → kernel → Python → op → kernel ...      (CPU-bound for small ops)
 compile:  graph capture → fused kernels → (optional) CUDA graph replay
```

### 📐 The Math, Gently
Overhead-bound regime: step time ≈ (number of kernels) × (launch overhead) when each kernel's GPU time < its launch time. Fusion reduces the kernel count; CUDA graphs reduce the per-launch cost to ~0.

### 🛠️ Build It From Scratch

```python
import torch, time
from nanoforge.models.gpt import GPT, GPTConfig, CONFIGS
if torch.cuda.is_available():
    cfg = GPTConfig(**CONFIGS["micro"], vocab_size=4096)
    for mode in [None, "default", "max-autotune"]:
        m = GPT(cfg).cuda(); opt = torch.optim.AdamW(m.parameters(), fused=True)
        mm = torch.compile(m, mode=mode) if mode else m
        x = torch.randint(0, 4096, (32, 256), device="cuda")
        for i in range(25):
            if i == 5: torch.cuda.synchronize(); t = time.time()
            with torch.autocast("cuda", dtype=torch.bfloat16): _, loss = mm(x, x)
            loss.backward(); opt.step(); opt.zero_grad(set_to_none=True)
        torch.cuda.synchronize(); print(f"mode={mode}: {(time.time()-t)/20*1e3:.1f} ms/step")
```

### 🔬 Experiment & Observe
Typical: default compile gives 1.3–2× over eager for micro; `max-autotune` spends more compile time searching kernel configs. Enable `--compile=true` in `train.py` and compare the MFU.

### ⚠️ Failure Modes & Debugging
- **Graph breaks:** Python features Dynamo can't trace (data-dependent control flow, `.item()` in forward, unsupported libraries) split the graph and reduce the gains. Diagnose with `torch._dynamo.explain(model)(x)` or `TORCH_LOGS="graph_breaks"`.
- **Recompilation** when shapes change (e.g. variable sequence length). Use `dynamic=True` or pad to fixed buckets.
- Windows: Triton isn't officially supported, so use WSL2.

### 🧠 Expert Insight
- **Ansel et al. (2024), PyTorch 2 paper.**
- nanoGPT and llm.c-style speedruns rely on compile + fused kernels to reach 50%+ MFU on small GPT-2 runs.

### ✅ Check Your Instinct
1. When do CUDA graphs help most?
2. What is a graph break?

<details><summary>Answers</summary>

1. When the CPU launch overhead dominates: small models, small batches, decoding.
2. A point where Dynamo can't capture the code, forcing a fallback to eager and splitting the graph.
</details>

### 📌 Recap Card
- `torch.compile` = capture + fuse + codegen.
- CUDA graphs remove the launch overhead.
- Watch for graph breaks and recompilations.

> **Core intuition:** *Let the compiler see the whole recipe so it can cook everything in one pot.*

## 29.4 A First Triton Kernel: Fused Softmax

### 🧭 The Problem First
Sometimes you need an operation the compiler doesn't fuse well, or you want to understand what the compiler generates. CUDA C++ is a steep climb.

### 💡 Intuition / Instinct
**Triton** lets you write GPU kernels in Python at the *block* level: each program instance handles a block of data, and you express loads, math and stores on whole blocks (vectors/tiles). Triton handles the thread-level details, memory coalescing and shared memory. A fused softmax: one program per row, which loads the row into SRAM once, computes max → exp → sum → divide, and writes once.

### 🖼️ Visual Mental Model

```text
 grid = (n_rows,)
 program i: row = load(X[i, :BLOCK]) → m = max(row) → e = exp(row - m) → out = e / sum(e) → store
```

### 📐 The Math, Gently
Traffic: read the row once + write it once = 2 × row bytes (vs ~5–8× for unfused eager softmax, which makes multiple passes).

### 🛠️ Build It From Scratch

```python
# nanoforge/kernels/softmax_triton.py  (Linux/WSL2 + NVIDIA GPU)
import torch, triton, triton.language as tl

@triton.jit
def softmax_kernel(out_ptr, in_ptr, in_stride, out_stride, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(in_ptr + row * in_stride + cols, mask=mask, other=-float("inf")).to(tl.float32)
    x = x - tl.max(x, axis=0)
    num = tl.exp(x)
    y = num / tl.sum(num, axis=0)
    tl.store(out_ptr + row * out_stride + cols, y.to(out_ptr.dtype.element_ty), mask=mask)

def softmax(x: torch.Tensor):
    assert x.dim() == 2 and x.is_cuda
    n_rows, n_cols = x.shape
    BLOCK = triton.next_power_of_2(n_cols)
    out = torch.empty_like(x)
    softmax_kernel[(n_rows,)](out, x, x.stride(0), out.stride(0), n_cols, BLOCK=BLOCK,
                              num_warps=4 if BLOCK <= 2048 else 8)
    return out

if __name__ == "__main__":
    x = torch.randn(4096, 1000, device="cuda", dtype=torch.float16)
    print(torch.allclose(softmax(x), torch.softmax(x.float(), -1).half(), atol=1e-3))
    print(triton.testing.do_bench(lambda: softmax(x)), "ms  vs torch",
          triton.testing.do_bench(lambda: torch.softmax(x, -1)), "ms")
```

### 🔬 Experiment & Observe
Benchmark it across n_cols = 256…16384. Your kernel is competitive with PyTorch's (which is also fused). Then compare against a naive three-op implementation (`exp(x - max) / sum`) in eager mode: your kernel wins clearly.

### ⚠️ Failure Modes & Debugging
- A BLOCK that isn't a power of two → a compile error. Rows larger than the SRAM capacity need a looped (online) version, the same idea as FlashAttention.
- Forgetting the `mask` on loads/stores → out-of-bounds memory access.

### 🧠 Expert Insight
- **Tillet et al. (2019), Triton.**
- Unsloth and Liger Kernel provide Triton kernels (RoPE, RMSNorm, SwiGLU, fused cross-entropy) that speed up fine-tuning and cut memory significantly.
- The official Triton tutorials (fused softmax → matmul → FlashAttention) are the natural next step.

### ✅ Check Your Instinct
1. What does one Triton program instance process here?
2. Why load with `other=-inf`?

<details><summary>Answers</summary>

1. One row of the input.
2. So the padded lanes don't affect the max, and they give exp(−inf) = 0 in the sum.
</details>

### 📌 Recap Card
- Triton: block-level GPU programming in Python.
- Fused softmax: one read, one write per row.
- Next steps: matmul and FlashAttention tutorials.

> **Core intuition:** *You describe what happens to a block; Triton handles the thousands of threads.*

## 29.5 Profiling With the PyTorch Profiler

### 🧭 The Problem First
Training runs at 25% MFU. Is it the data loader? The attention? The optimizer? Too many small kernels? Without measurement you'll optimize the wrong thing.

### 💡 Intuition / Instinct
Profile a few steps. The profiler records CPU ops, CUDA kernels and memory, with timelines. Look for: (1) **GPU idle gaps** (the data loader, CPU overhead, synchronizations), (2) **top kernels by time** (are the matmuls dominant, as they should be?), (3) **memory peaks**. Fix the largest item first.

### 🖼️ Visual Mental Model

```text
 timeline (chrome://tracing or Perfetto):
 CPU  ▇▇ ▇▇▇ ▇ ▇▇▇▇▇▇▇▇▇ (dataloader) ▇▇
 GPU  ██ ███ █ ______________________ ██   ← idle gap = GPU starved → fix the loader
```

### 📐 The Math, Gently
Ideal: GPU busy > 95% of the step time, and matmuls (gemm kernels) > 60–70% of the GPU time for transformer training.

### 🛠️ Build It From Scratch

```python
# scripts/profile_step.py
import torch
from torch.profiler import profile, ProfilerActivity, schedule, tensorboard_trace_handler
from nanoforge.models.gpt import GPT, GPTConfig, CONFIGS
cfg = GPTConfig(**CONFIGS["micro"], vocab_size=4096)
m = GPT(cfg).cuda(); opt = torch.optim.AdamW(m.parameters(), fused=True)
x = torch.randint(0, 4096, (32, 256), device="cuda")
def step():
    with torch.autocast("cuda", dtype=torch.bfloat16): _, loss = m(x, x)
    loss.backward(); opt.step(); opt.zero_grad(set_to_none=True)
with profile(activities=[ProfilerActivity.CPU, ProfilerActivity.CUDA], schedule=schedule(wait=1, warmup=2, active=3),
             on_trace_ready=tensorboard_trace_handler("profiles/micro"), record_shapes=True, profile_memory=True) as prof:
    for _ in range(6): step(); prof.step()
print(prof.key_averages().table(sort_by="cuda_time_total", row_limit=15))
```

Open `profiles/micro/*.json` in https://ui.perfetto.dev to see the timeline.

### 🔬 Experiment & Observe
Profile eager vs compiled. In eager you'll see many small elementwise kernels (layernorm, gelu, add, dropout) taking a surprising share of the time; after compile they're fused. Then profile *with the real data loader* at `num_workers=0` and look for the idle gaps.

### ⚠️ Failure Modes & Debugging
- Profiling the first steps (compile/autotune warmup) misleads. Use the schedule's warmup.
- Hidden synchronizations: `.item()`, printing tensors, and `torch.cuda.synchronize()` in the loop show up as gaps.

### 🧠 Expert Insight
Frontier teams run continuous profiling and track MFU regressions per commit. NVIDIA Nsight Systems/Compute give deeper kernel-level insight (occupancy, memory throughput per kernel).

### ✅ Check Your Instinct
1. What does a GPU idle gap during a training step indicate?

<details><summary>Answers</summary>

</details>

### 📌 Recap Card
- Profile with a schedule (skip warmup).
- Look for idle gaps, top kernels, memory peaks.
- Fix the biggest bottleneck first; re-measure.

> **Core intuition:** *Measure, don't guess: the profiler shows where every millisecond goes.*
