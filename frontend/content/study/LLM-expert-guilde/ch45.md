## 45.1 Static vs Continuous Batching

### 🧭 The Problem First
Ch 43.1 showed that decoding 32 sequences at once costs about the same per step as decoding one. So batch requests together. But requests arrive at random times and want different numbers of output tokens: one user wants "yes/no", another wants a 1,000-word essay. How do you batch *those*?

### 💡 Intuition / Instinct
**Static (request-level) batching** is a bus that only leaves when full and only takes new passengers when *everyone* has got off. The "yes/no" user's slot sits empty for 999 steps while the essay finishes, and new arrivals wait at the stop.

**Continuous (iteration-level) batching** is a bus that stops at every step: after each decode iteration, finished sequences get off and waiting ones get on. The batch composition changes every step. The GPU stays full, and short requests don't wait for long ones.

What makes this possible is that decode iterations are *independent across sequences*: every sequence only needs its own KV cache. The scheduler is free to reshuffle the batch between any two steps.

### 🖼️ Visual Mental Model

```text
 STATIC (batch of 4)                          CONTINUOUS (4 slots)
 step: 1 2 3 4 5 6 7 8 9                      step: 1 2 3 4 5 6 7 8 9
 A     █ █ ░ ░ ░ ░ ░ ░ ░   (done at 2, idle)  A     █ █ E E E F F F F
 B     █ █ █ █ █ █ █ █ █                      B     █ █ █ █ █ █ █ █ █
 C     █ █ █ █ ░ ░ ░ ░ ░                      C     █ █ █ █ G G H H H
 D     █ █ █ ░ ░ ░ ░ ░ ░                      D     █ █ █ I I I I J J
 E,F,G,... wait for step 10                   new requests fill freed slots immediately
 █ = useful work   ░ = wasted slot
```

### 📐 The Math, Gently
Let the output lengths in a batch of size b be $L_1, \dots, L_b$. Static batching takes $\max_i L_i$ steps and does $\sum_i L_i$ useful token-steps, so its slot utilization is

$$U_{static} = \frac{\sum_i L_i}{b \cdot \max_i L_i} = \frac{\bar L}{\max_i L_i}$$

For long-tailed lengths (typical of chat), the max of 16 samples is several times the mean, so utilization collapses. Continuous batching approaches $U \to 1$ as long as the queue is non-empty.

The catch: when a new request joins, it needs a **prefill**, which is a much heavier operation than a decode step (Ch 43.1). Running a long prefill inside a decode iteration stalls everyone's next token. Schedulers limit prefills per step, or split them into chunks (chunked prefill).

### 🛠️ Build It From Scratch
A step-level simulation makes the difference concrete before we write the real engine:

```python
# nanoforge/serve/batching_sim.py
import random

def simulate(policy, lengths, max_batch=8):
    """Count decode steps to finish all requests, one token per active slot per step.
    policy='static': a batch is formed, and no one joins until every member is done.
    policy='continuous': a finished slot is refilled from the queue at the next step."""
    queue, slots, steps = list(lengths), [], 0
    while queue or slots:
        if policy == "continuous" or not slots:                 # static only refills an empty batch
            while queue and len(slots) < max_batch: slots.append(queue.pop(0))
        steps += 1
        slots = [r - 1 for r in slots if r > 1]
    return {"steps": steps, "utilization": sum(lengths) / (steps * max_batch)}

if __name__ == "__main__":
    rng = random.Random(0)
    lengths = [min(1024, int(rng.expovariate(1 / 150)) + 1) for _ in range(512)]   # long-tailed output lengths
    for p in ("static", "continuous"):
        print(p, simulate(p, lengths, max_batch=16))
```

Output (512 requests, exponential lengths with mean 150, 16 slots):

```text
static     {'steps': 16591, 'utilization': 0.30}
continuous {'steps': 5312,  'utilization': 0.94}
```

Same hardware, same requests, ~3× the throughput from scheduling alone.

### 🔬 Experiment & Observe
1. Change the length distribution to a constant (every request wants 150 tokens). The two policies become nearly identical: static batching is only bad when lengths vary.
2. Increase `max_batch` from 4 to 64 and plot the utilization of both. Static batching gets *worse* with larger batches (the expected max of more samples grows).
3. Add a per-step prefill cost to the simulation (e.g. a new request costs 5 extra step-units when it joins) and see how much it eats into continuous batching's advantage.

### ⚠️ Failure Modes & Debugging
- **Padding-based implementations** of static batching also waste compute on pad tokens and must mask them correctly; a mis-masked pad token silently changes outputs.
- **Head-of-line blocking:** with FIFO admission, one giant request at the front of the queue can hold everyone back if it doesn't fit. Real schedulers allow smaller requests to skip ahead (with fairness limits).
- **Different sampling parameters per request** (temperature, top-p, stop sequences) must be applied per row, not per batch.

### 🧠 Expert Insight
- **Yu et al. (2022), Orca:** introduced iteration-level scheduling (continuous batching) and selective batching.
- **Hugging Face TGI, vLLM, TensorRT-LLM and SGLang** all use continuous batching; it's the single largest throughput improvement in LLM serving.
- Modern schedulers mix prefill chunks and decode tokens in the *same* forward pass under a token budget per step (e.g. 512–8,192 tokens), which keeps both TTFT and TPOT stable.

### ✅ Check Your Instinct
1. Why does static batching get worse when output lengths vary more?
2. What makes it legal to change the batch composition between decode steps?

<details><summary>Answers</summary>

1. Each batch runs for as long as its longest member, so utilization is mean/max, which falls as the spread grows.
2. Each sequence's next step depends only on its own tokens and KV cache, so sequences can join and leave independently.
</details>

### 📌 Recap Card
- Static: a batch waits for its slowest member; utilization = mean/max length.
- Continuous: refill slots every iteration; utilization → 1.
- Prefills are heavy: limit or chunk them to protect running decodes.

> **Core intuition:** *Schedule per token, not per request. The GPU should never wait for the slowest passenger.*

## 45.2 PagedAttention: Virtual Memory for the KV Cache

### 🧭 The Problem First
Continuous batching needs a KV cache per sequence, but you don't know in advance how long each sequence will get. The Ch 30 `KVCache` preallocates `T_max` positions per sequence. With T_max = 4,096 and the average conversation using 500 tokens, ~88% of the reserved KV memory holds nothing, and it's the KV memory that limits how many sequences fit in a batch.

### 💡 Intuition / Instinct
Operating systems solved exactly this problem decades ago with **virtual memory**: programs see contiguous memory, but physically it's scattered fixed-size pages, allocated on demand and tracked in a page table.

**PagedAttention** does the same for the KV cache:
- The GPU memory for KV is one big pool of **blocks**, each holding K/V for `block_size` tokens (e.g. 16).
- Each sequence has a **block table**: a list of the block ids holding its tokens, in order.
- A sequence gets a new block only when its last one fills up. The waste is at most one partially filled block per sequence.
- When a sequence finishes, its blocks go straight back to the free list.
- Attention kernels read K/V by following the block table.

Bonus: blocks can be **shared**. Two requests with the same system prompt can point at the same physical blocks for the shared prefix (prefix caching), and parallel samples of one prompt can share the prompt's blocks (copy-on-write when they diverge).

### 🖼️ Visual Mental Model

```text
 physical KV pool (block_size = 4 tokens)
 ┌────┬────┬────┬────┬────┬────┬────┬────┐
 │ b0 │ b1 │ b2 │ b3 │ b4 │ b5 │ b6 │ b7 │ ...
 └────┴────┴────┴────┴────┴────┴────┴────┘
 seq A (10 tokens): block table [b3, b0, b6]   → positions 0-3 in b3, 4-7 in b0, 8-9 in b6 (2 slots free)
 seq B ( 5 tokens): block table [b1, b5]
 free list: [b2, b4, b7, ...]
 logical position p of a sequence → block table[p // 4], offset p % 4
```

### 📐 The Math, Gently
**KV bytes per token** (Ch 30.2): $2 \cdot L \cdot H_{kv} \cdot D \cdot \text{bytes}$. For Llama-mini in bf16 (L = 8, H_kv = 2, D = 64): 2·8·2·64·2 = 4 KB per token.

**How many sequences fit?** With a KV budget M bytes and $\bar T$ tokens per sequence on average:
- Preallocated: $M / (T_{max}\cdot \text{bytes/token})$ sequences.
- Paged: $\approx M / ((\bar T + \text{block\_size}/2)\cdot\text{bytes/token})$ sequences.

With $T_{max}$ = 4,096 and $\bar T$ = 500, paging fits ~8× more concurrent sequences, which (since decode is memory-bound) is up to ~8× the throughput.

**Choosing block_size:** smaller blocks waste less memory (≤ block_size − 1 tokens per sequence) but make the block table longer and the kernel's memory accesses less contiguous. 16 is the common default.

**When the pool runs out:** some running sequence must give its memory back. Either **swap** its blocks to CPU memory, or **recompute**: free its blocks and later re-prefill its prompt + output-so-far. Recomputation is simple and often faster than swapping for short contexts, because prefill is compute-efficient.

### 🛠️ Build It From Scratch
The block manager:

```python
# nanoforge/serve/paged.py
import math, torch

class PagedKVCache:
    """A pool of fixed-size KV blocks shared by all sequences.
    k/v: (n_layer, n_blocks, block_size, H_kv, D). Each sequence owns a list of block ids: its block table."""
    def __init__(self, n_layer, n_blocks, block_size, H_kv, D, device, dtype):
        self.k = torch.zeros(n_layer, n_blocks, block_size, H_kv, D, device=device, dtype=dtype)
        self.v = torch.zeros_like(self.k)
        self.bs, self.free = block_size, list(range(n_blocks - 1, -1, -1))
        self.tables, self.lens = {}, {}                     # seq_id -> [block ids], seq_id -> tokens stored

    def reserve(self, sid, new_len):
        """Ensure capacity for `new_len` tokens. Allocates nothing and returns False if the pool is too small."""
        need = max(0, math.ceil(new_len / self.bs) - len(self.tables.get(sid, [])))
        if need > len(self.free): return False
        self.tables.setdefault(sid, []).extend(self.free.pop() for _ in range(need))
        self.lens.setdefault(sid, 0)
        return True

    def slots(self, sid, start, n):
        """Physical (block, offset) of logical positions start..start+n-1 of sequence sid."""
        pos = torch.arange(start, start + n)
        table = torch.tensor(self.tables[sid])
        return table[pos // self.bs].to(self.k.device), (pos % self.bs).to(self.k.device)

    def write(self, layer, blk, off, k, v):                 # k, v: (n, H_kv, D)
        self.k[layer, blk, off] = k; self.v[layer, blk, off] = v

    def gather(self, layer, sid, length):
        """(length, H_kv, D) keys and values of one sequence, stitched together from its blocks."""
        t = torch.tensor(self.tables[sid], device=self.k.device)
        return self.k[layer, t].flatten(0, 1)[:length], self.v[layer, t].flatten(0, 1)[:length]

    def release(self, sid):
        self.free.extend(reversed(self.tables.pop(sid, []))); self.lens.pop(sid, None)

    def utilization(self):
        total = self.k.size(1); used = total - len(self.free)
        return {"blocks_used": used, "blocks_total": total,
                "internal_waste": (1 - sum(self.lens.values()) / (used * self.bs)) if used else 0.0}
```

The model side: a forward pass over the Llama weights (Ch 32) that reads and writes K/V through the block tables. Prefill handles one new sequence; decode handles a ragged batch where every sequence is at a different position, so each row gets its own RoPE angle and its own attention mask.

```python
# nanoforge/serve/paged_model.py
import torch, torch.nn.functional as F
from nanoforge.models.attention import repeat_kv

def rope_tokens(x, cos, sin):
    """x: (N, H, D) with interleaved pairs; cos/sin: (N, D/2), one row per token (each token has its own position)."""
    x1, x2 = x[..., 0::2], x[..., 1::2]
    c, s = cos[:, None, :], sin[:, None, :]
    return torch.stack([x1 * c - x2 * s, x1 * s + x2 * c], -1).flatten(-2).type_as(x)

def _qkv(blk, h, cos, sin):
    a, N = blk.attn, h.size(0)
    q = a.q_norm(a.wq(h).view(N, a.H, a.D)); k = a.k_norm(a.wk(h).view(N, a.Hkv, a.D))
    v = a.wv(h).view(N, a.Hkv, a.D)
    return rope_tokens(q, cos, sin), rope_tokens(k, cos, sin), v

@torch.no_grad()
def paged_prefill(model, cache, sid, ids):
    """Process a whole prompt (1-D ids) for one sequence, from position 0. Returns the last token's logits (V,)."""
    T = ids.numel(); pos = torch.arange(T, device=ids.device)
    cos, sin = model.rope_cos[pos], model.rope_sin[pos]
    blk_ids, offs = cache.slots(sid, 0, T)
    x = model.tok_emb(ids)                                                    # (T, C)
    for li, blk in enumerate(model.layers):
        a = blk.attn
        q, k, v = _qkv(blk, blk.attn_norm(x), cos, sin)
        cache.write(li, blk_ids, offs, k, v)
        q, k, v = (t.transpose(0, 1)[None] for t in (q, k, v))                 # (1, H|Hkv, T, D)
        k, v = repeat_kv(k, a.H // a.Hkv), repeat_kv(v, a.H // a.Hkv)
        y = F.scaled_dot_product_attention(q, k, v, is_causal=True)           # (1, H, T, D)
        x = x + a.wo(y[0].transpose(0, 1).reshape(T, -1))
        x = x + blk.mlp(blk.mlp_norm(x))
    cache.lens[sid] = T
    return model.lm_head(model.norm(x[-1]))

@torch.no_grad()
def paged_decode(model, cache, sids, last_tokens):
    """One decode step for a batch of sequences of different lengths. last_tokens: (B,). Returns logits (B, V)."""
    B, dev = len(sids), last_tokens.device
    pos = torch.tensor([cache.lens[s] for s in sids], device=dev)             # each sequence's own position
    cos, sin = model.rope_cos[pos], model.rope_sin[pos]
    slots = [cache.slots(s, cache.lens[s], 1) for s in sids]
    blk_ids, offs = torch.cat([b for b, _ in slots]), torch.cat([o for _, o in slots])
    Tmax = int(pos.max()) + 1
    mask = torch.arange(Tmax, device=dev)[None, :] <= pos[:, None]            # (B, Tmax): each row's valid keys
    x = model.tok_emb(last_tokens)                                             # (B, C)
    for li, blk in enumerate(model.layers):
        a = blk.attn
        q, k, v = _qkv(blk, blk.attn_norm(x), cos, sin)                        # (B, H|Hkv, D)
        cache.write(li, blk_ids, offs, k, v)
        K = torch.zeros(B, Tmax, a.Hkv, a.D, device=dev, dtype=k.dtype); V = torch.zeros_like(K)
        for b, s in enumerate(sids):                                           # stitch each ragged sequence
            kb, vb = cache.gather(li, s, int(pos[b]) + 1)
            K[b, :kb.size(0)], V[b, :vb.size(0)] = kb, vb
        K, V = repeat_kv(K.transpose(1, 2), a.H // a.Hkv), repeat_kv(V.transpose(1, 2), a.H // a.Hkv)
        y = F.scaled_dot_product_attention(q[:, :, None], K, V, attn_mask=mask[:, None, None, :])   # (B, H, 1, D)
        x = x + a.wo(y.reshape(B, -1))
        x = x + blk.mlp(blk.mlp_norm(x))
    for s in sids: cache.lens[s] += 1
    return model.lm_head(model.norm(x))
```

The Python loop that stitches each sequence's blocks into a padded tensor is the part a real PagedAttention kernel replaces: the kernel reads K/V directly from the scattered blocks via the block table, with no copy.

### ⚠️ Failure Modes & Debugging
- **Off-by-one in slot mapping** (writing position p to block `p // bs` of the wrong table) corrupts another sequence's cache: outputs look plausible but are wrong. The equality test with plain generation catches it.
- **A request that needs more blocks than the whole pool** can never run and blocks the queue. Reject it at submission (`submit` asserts on the context length; also check it against the pool size).
- **Forgetting to free blocks on cancellation** leaks memory until the server stalls. Every exit path (finish, EOS, cancel, error) must call `release`.
- **Prefix sharing without reference counts:** freeing a shared block while another sequence still reads it. Shared blocks need refcounts and copy-on-write.

### 🧠 Expert Insight
- **Kwon et al. (2023), "Efficient Memory Management for LLM Serving with PagedAttention" (vLLM):** reported 2–4× throughput over prior systems, mostly from fitting more sequences into memory.
- **Zheng et al. (2024), SGLang RadixAttention:** stores cached prefixes in a radix tree, so any shared prefix (system prompts, few-shot examples, multi-turn history) is reused automatically.
- **Prompt caching** offered by API providers is the same idea at the product level: repeated prefixes skip prefill and are billed at a discount.
- Some newer engines use contiguous virtual memory with on-demand physical pages (vAttention, 2024) to keep standard attention kernels while avoiding fragmentation.

### 📌 Recap Card
- KV pool of fixed-size blocks + a block table per sequence = virtual memory for attention.
- Waste < 1 block per sequence → far more concurrent sequences.
- Out of blocks → preempt (recompute or swap).
- Shared prefixes can share blocks (refcounts, copy-on-write).

> **Core intuition:** *Don't reserve memory for tokens that don't exist yet. Hand out pages as the conversation grows.*

## 45.3 Latency (TTFT, TPOT) vs Throughput

### 🧭 The Problem First
Your boss wants "maximum tokens per second per GPU". Your users want "the first word to appear instantly and text to stream faster than they can read". These goals conflict. How do you choose the operating point?

### 💡 Intuition / Instinct
- **Throughput** (total tokens/s across all users) rises with batch size, because decode is memory-bound: more rows per weight read.
- **TPOT** (time per output token per user) also rises with batch size: each step does more work, and once the batch is large enough to become compute-bound, step time grows linearly.
- **TTFT** (time to first token) depends on the queue: if the server is saturated, new requests wait for a free slot before their prefill even starts. Near saturation, TTFT explodes.

So there's a curve, not a single number: as the load (requests/s) increases, throughput rises and then plateaus, while latency is flat and then shoots up. The job of capacity planning is to run just below the knee.

Human reading speed gives a useful target: ~4–7 words/s ≈ 5–10 tokens/s. A TPOT under ~50–100 ms feels fluid for chat. TTFT under ~1 s feels responsive. Agents and batch jobs care about throughput and total completion time, not TPOT.

### 🖼️ Visual Mental Model

```text
 throughput                         p99 latency
   │           ___________            │                     /
   │         /                        │                    /
   │       /                          │                   /
   │     /                            │ ________________/
   │   /                              │
   └──────────────────▶ load          └──────────────────▶ load
                 ▲ knee: operate just below here (the SLO sets where)
```

### 📐 The Math, Gently
**Per-request latency:** $E2E = TTFT + (n_{out} - 1)\cdot TPOT$.

**Little's law** links load, latency and concurrency: the average number of requests in the system is $N = \lambda \cdot W$ (arrival rate × average time in system). If each request spends 10 s generating and 5 requests/s arrive, you need ~50 concurrent slots; if you have fewer, a queue builds without bound.

**Utilization and queueing:** for a server at utilization ρ (fraction of capacity used), simple queueing models give waiting times proportional to $\rho/(1-\rho)$: going from 50% to 90% load multiplies the queueing delay by 9. That's why p99 latency explodes near saturation.

**SLOs:** real deployments specify targets like "p99 TTFT < 2 s and p50 TPOT < 50 ms", then find the maximum load (**goodput**: requests/s that meet the SLO) rather than the raw maximum throughput.

### 🛠️ Build It From Scratch
An in-process load generator with Poisson arrivals, running the engine from 45.4:

```python
# nanoforge/serve/loadtest.py
import random, statistics, time
from nanoforge.serve.engine import Engine, Request

def pct(xs, p):
    xs = sorted(xs); return xs[min(len(xs) - 1, int(p / 100 * len(xs)))]

def load_test(model, rate, n_requests=64, prompt_len=(32, 256), out_len=(16, 256), seed=0, **engine_kw):
    """Poisson arrivals at `rate` requests/s against an in-process Engine. Returns latency/throughput stats."""
    rng = random.Random(seed)
    V = model.cfg.vocab_size
    t, arrivals = 0.0, []
    for _ in range(n_requests):
        t += rng.expovariate(rate)
        arrivals.append((t, [rng.randrange(V) for _ in range(rng.randint(*prompt_len))], rng.randint(*out_len)))
    eng = Engine(model, **engine_kw)
    reqs, i, t0 = [], 0, time.perf_counter()
    while i < len(arrivals) or eng.has_work():
        now = time.perf_counter() - t0
        while i < len(arrivals) and arrivals[i][0] <= now:     # submit everyone who has "arrived"
            r = Request(arrivals[i][1], arrivals[i][2]); r.t_arrive = t0 + arrivals[i][0]
            reqs.append(eng.submit(r)); i += 1
        if eng.has_work(): eng.step()
        else: time.sleep(max(0.0, min(0.01, arrivals[i][0] - now)))
    wall = time.perf_counter() - t0
    ttft = [1e3 * (r.t_first - r.t_arrive) for r in reqs]
    tpot = [1e3 * (r.t_done - r.t_first) / (len(r.output) - 1) for r in reqs if len(r.output) > 1]
    e2e = [r.t_done - r.t_arrive for r in reqs]
    return {"rate": rate, "throughput_tok_s": sum(len(r.output) for r in reqs) / wall,
            "ttft_p50_ms": pct(ttft, 50), "ttft_p99_ms": pct(ttft, 99),
            "tpot_p50_ms": pct(tpot, 50), "tpot_p99_ms": pct(tpot, 99), "e2e_mean_s": statistics.mean(e2e)}
```

### ⚠️ Failure Modes & Debugging
- **Closed-loop load testing** (each client waits for its response before sending the next) hides queueing collapse, because the load automatically drops when the server slows down. Use **open-loop** arrivals (Poisson) like the code above.
- **Reporting averages only:** users feel the tail. Always report p50 and p99.
- **Benchmarking with fixed prompt/output lengths** that don't match production. Use a realistic length distribution (log your real traffic).
- **The Python scheduler becoming the bottleneck:** with tiny models, per-step Python overhead dominates. Production engines move scheduling off the critical path and use CUDA graphs for decode steps.

### 🧠 Expert Insight
- **Goodput** under SLOs (DistServe, 2024) is the metric that matters for real services, not peak tokens/s.
- **Disaggregated prefill/decode** (DistServe, Splitwise, Mooncake): separate GPU pools for prefill and decode, with the KV cache transferred between them, so prefills never interrupt decodes.
- **Priority and fairness:** production schedulers give interactive traffic priority over batch jobs, and cap per-tenant usage.
- Throughput-oriented offline jobs (evals, synthetic data generation) should run with huge batches at night on the same hardware: the knee doesn't matter when nobody is waiting.

## 45.4 A Mini Serving Engine With FastAPI and Streaming

### 🧭 The Problem First
You have all the pieces: a paged cache, a continuous-batching loop, sampling, a chat template. Now wire them into something a browser or another program can call, with tokens streaming out as they're generated, requests cancellable, and the GPU shared across all callers.

### 💡 Intuition / Instinct
Three layers, each simple:
1. **Engine (scheduler):** owns the model and the KV pool; `step()` admits waiting requests (prefill), then runs one decode step for all running ones, and delivers each new token through a per-request callback.
2. **Server (async web layer):** each HTTP request becomes an engine `Request` with an `asyncio.Queue`. A single background task calls `engine.step()` in a loop. The handler reads tokens from its queue and streams them to the client as **Server-Sent Events (SSE)**.
3. **Detokenizer:** converts the growing token list into text *deltas*, holding back partial UTF-8 characters.

Only one task touches the GPU, so there are no locks; the web handlers just wait on queues.

### 🖼️ Visual Mental Model

```text
 client A ──POST /v1/generate──▶ handler A ── submit(Request, on_token=qA.put) ──┐
 client B ──POST /v1/generate──▶ handler B ── submit(Request, on_token=qB.put) ──┤
                                                                                  ▼
                                   engine loop task:  while True: engine.step()
                                     ├─ admit + prefill (paged)
                                     ├─ decode step for the whole batch
                                     └─ on_token(tok) → qA / qB
 handler A ◀── await qA.get() ── detokenize ── "data: {\"text\": \"Hel\"}\n\n" ──▶ client A (streaming)
```

### 📐 The Math, Gently
No new math. The key numbers to expose per request are the ones from 45.3: prompt tokens, completion tokens, TTFT and TPOT, which you'll aggregate into dashboards.

One subtlety with **streaming text**: token boundaries don't align with characters. A byte-level BPE token can contain half of a multi-byte UTF-8 character (common for emoji, CJK text, accented letters). Decoding the full id list each time and emitting only the new suffix is O(n²) in the output length, but trivially correct. Emit nothing while the text ends in the replacement character U+FFFD.

### 🛠️ Build It From Scratch
The engine:

```python
# nanoforge/serve/engine.py
import itertools, time, torch, torch.nn.functional as F
from dataclasses import dataclass, field
from nanoforge.serve.paged import PagedKVCache
from nanoforge.serve.paged_model import paged_prefill, paged_decode
from nanoforge.sampling import top_p_filter

_ids = itertools.count()

@dataclass
class Request:
    prompt: list
    max_new_tokens: int = 128
    temperature: float = 0.0
    top_p: float = 1.0
    eos_id: int = None
    on_token: object = None                    # callback(token_id or None at the end), for streaming
    id: int = field(default_factory=lambda: next(_ids))
    output: list = field(default_factory=list)
    t_arrive: float = field(default_factory=time.perf_counter)
    t_first: float = None
    t_done: float = None
    done: bool = False

class Engine:
    """Continuous batching over a paged KV cache. New requests join between decode steps;
    finished ones leave immediately and return their blocks to the pool."""
    def __init__(self, model, n_blocks=512, block_size=16, max_batch=32, max_prefills_per_step=1):
        cfg, p = model.cfg, next(model.parameters())
        self.model = model.eval()
        self.cache = PagedKVCache(cfg.n_layer, n_blocks, block_size, cfg.n_kv_head, cfg.n_embd // cfg.n_head, p.device, p.dtype)
        self.max_batch, self.max_prefills = max_batch, max_prefills_per_step
        self.waiting, self.running, self.device = [], [], p.device

    def submit(self, req):
        assert len(req.prompt) + req.max_new_tokens <= self.model.cfg.block_size, "request exceeds the context length"
        self.waiting.append(req); return req

    def has_work(self): return bool(self.waiting or self.running)

    def _sample(self, logits, reqs):
        out = []
        for l, r in zip(logits.float(), reqs):                 # per-request sampling parameters
            if r.temperature == 0: out.append(int(l.argmax())); continue
            l = top_p_filter((l / r.temperature)[None], r.top_p)[0]
            out.append(int(torch.multinomial(F.softmax(l, -1), 1)))
        return out

    def _emit(self, r, tok):
        if r.t_first is None: r.t_first = time.perf_counter()
        if tok == r.eos_id: return self._finish(r)
        r.output.append(tok)
        if r.on_token: r.on_token(tok)
        if len(r.output) >= r.max_new_tokens: self._finish(r)

    def _finish(self, r):
        r.done, r.t_done = True, time.perf_counter()
        self.cache.release(r.id)
        if r.on_token: r.on_token(None)                        # end-of-stream signal

    def _preempt(self, r):
        """Recompute-style preemption: free its blocks and requeue it at the front.
        On re-admission, prompt + output-so-far is prefilled again and generation continues where it stopped."""
        self.cache.release(r.id); self.running.remove(r)
        self.waiting.insert(0, r)

    def cancel(self, r):
        if r.done: return
        if r in self.waiting: self.waiting.remove(r)
        if r in self.running: self.running.remove(r)
        self._finish(r)

    def step(self):
        # 1) admission: prefill waiting requests while there are batch slots and free blocks
        admitted = 0
        while self.waiting and len(self.running) < self.max_batch and admitted < self.max_prefills:
            r = self.waiting[0]
            ctx = r.prompt + r.output                                       # output is non-empty only after a preemption
            if not self.cache.reserve(r.id, len(ctx) + 1): break           # pool full: wait for a finisher
            self.waiting.pop(0); admitted += 1
            logits = paged_prefill(self.model, self.cache, r.id, torch.tensor(ctx, device=self.device))
            self._emit(r, self._sample(logits[None], [r])[0])
            if not r.done: self.running.append(r)
        # 2) every running sequence needs room for one more token; preempt the newest ones if the pool is full
        for r in reversed(list(self.running)):
            if not self.cache.reserve(r.id, self.cache.lens[r.id] + 1): self._preempt(r)
        # 3) one decode step for the whole ragged batch
        batch = list(self.running)
        if batch:
            last = torch.tensor([r.output[-1] for r in batch], device=self.device)
            logits = paged_decode(self.model, self.cache, [r.id for r in batch], last)
            for r, tok in zip(batch, self._sample(logits, batch)): self._emit(r, tok)
        self.running = [r for r in self.running if not r.done]

    def run_until_done(self):
        while self.has_work(): self.step()
```

The server:

```python
# nanoforge/serve/server.py
import asyncio, contextlib, json, time
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from nanoforge.serve.engine import Engine, Request

class GenerateBody(BaseModel):
    prompt: str | None = None
    messages: list[dict] | None = None         # [{"role": "user", "content": "..."}] -> chat template
    max_tokens: int = 256
    temperature: float = 0.7
    top_p: float = 0.95
    stream: bool = True

class IncrementalDetokenizer:
    """Turns a growing list of token ids into text deltas. Holds back text while the tail is an
    incomplete UTF-8 sequence (a byte-level BPE token can end in the middle of a character)."""
    def __init__(self, tok): self.tok, self.ids, self.sent = tok, [], ""
    def push(self, t):
        self.ids.append(t)
        text = self.tok.decode(self.ids)
        if text.endswith("\ufffd"): return ""
        delta, self.sent = text[len(self.sent):], text
        return delta

def create_app(model, tok, chat=None, eos_id=None, **engine_kw):
    engine = Engine(model, **engine_kw)

    async def engine_loop():
        while True:
            if engine.has_work():
                engine.step()                     # one scheduler iteration (blocking GPU work)
                await asyncio.sleep(0)            # let request handlers run between steps
            else:
                await asyncio.sleep(0.002)

    @contextlib.asynccontextmanager
    async def lifespan(app):
        task = asyncio.create_task(engine_loop())
        yield
        task.cancel()

    app = FastAPI(lifespan=lifespan)

    @app.get("/health")
    def health():
        return {"waiting": len(engine.waiting), "running": len(engine.running), **engine.cache.utilization()}

    @app.post("/v1/generate")
    async def generate(body: GenerateBody):
        ids = chat.prompt_for_generation(body.messages) if body.messages else tok.encode(body.prompt)
        q = asyncio.Queue()
        req = engine.submit(Request(ids, body.max_tokens, body.temperature, body.top_p, eos_id, on_token=q.put_nowait))
        detok = IncrementalDetokenizer(tok)

        def usage():
            ttft = (req.t_first - req.t_arrive) * 1e3 if req.t_first else None
            tpot = ((req.t_done - req.t_first) * 1e3 / max(1, len(req.output) - 1)) if req.t_done and req.t_first else None
            return {"prompt_tokens": len(ids), "completion_tokens": len(req.output), "ttft_ms": ttft, "tpot_ms": tpot}

        async def events():
            try:
                while (t := await q.get()) is not None:
                    if delta := detok.push(t):
                        yield f"data: {json.dumps({'text': delta})}\n\n"
                yield f"data: {json.dumps({'done': True, 'usage': usage()})}\n\n"
            finally:
                if not req.done: engine.cancel(req)          # client went away: free the slot and its KV blocks

        if body.stream:
            return StreamingResponse(events(), media_type="text/event-stream")
        while await q.get() is not None: pass
        return {"text": tok.decode(req.output), "usage": usage()}

    app.state.engine = engine
    return app

if __name__ == "__main__":
    import argparse, torch, uvicorn
```

## 45.5 Cost Estimation: $/Million Tokens on Your Own Hardware vs Cloud

### 🧭 The Problem First
Should you serve your model on the RTX 4090 under your desk, rent an H100 by the hour, or just call an API? The answer depends on arithmetic most people never do.

### 💡 Intuition / Instinct
Cost per token = (cost per hour) ÷ (tokens per hour). Everything hides in the second term:
- **Tokens per hour depends on utilization.** A rented GPU that's busy 10% of the time costs 10× more per token than one that's busy all the time. APIs price per token, so you only pay for what you use.
- **Input and output tokens cost differently.** Prefill tokens are cheap (compute-bound, thousands per second); output tokens are expensive (memory-bound). APIs price output tokens at several times input tokens for this reason.
- **Owned hardware** turns into an hourly cost via amortization (purchase price over its useful life) plus electricity.

### 🖼️ Visual Mental Model

```text
 $/M tokens
   │ ╲  rented GPU (fixed $/h)
   │  ╲
   │   ╲___
   │       ╲____
   │ ─ ─ ─ ─ ─ ─╲─ ─ ─ ─ ─ ─  API price (flat per token)
   │              ╲_________ owned GPU (amortized + power)
   └────────────────────────▶ utilization / traffic volume
      low traffic → API wins        steady high traffic → self-hosting wins
```

### 📐 The Math, Gently
**Hourly cost of owned hardware:**

$$C_{hour} = \frac{\text{price}}{\text{lifetime hours}} + \text{kW} \cdot \text{PUE} \cdot \$/\text{kWh}$$

(PUE ≈ 1.1–1.5 accounts for cooling and power supply losses; at home, use ~1.1.)

**Effective throughput:** $\text{tok/h} = 3600 \cdot \text{tok/s}_{\text{at your batch}} \cdot \text{utilization}$.

**Cost per million output tokens:** $\$/M = 10^6 \cdot C_{hour} / \text{tok/h}$.

Example: a 4090 at $1,800 amortized over 3 years (≈ 26,000 h) = $0.07/h; 450 W × 1.1 at $0.20/kWh = $0.10/h; total ≈ $0.17/h. If it serves a 7B INT4 model at 600 output tok/s with batching and is busy 50% of the time: 3600 × 600 × 0.5 = 1.08M tok/h → **≈ $0.16 per million output tokens**. At 5% utilization, the same GPU costs ≈ $1.6/M.

**Break-even vs an API** at price P ($/M): self-hosting wins when $10^6 C_{hour} / (3600\cdot r \cdot u) < P$, i.e. when utilization $u > 10^6 C_{hour}/(3600\cdot r\cdot P)$. Don't forget the costs that aren't per token: engineering time, monitoring, on-call, and the capability gap between your model and a frontier API model.

### 🛠️ Build It From Scratch

```python
# nanoforge/serve/cost.py
from dataclasses import dataclass

@dataclass
class Hardware:
    name: str
    hourly: float = None          # rented: $/h (all-in)
    price: float = None           # owned: purchase price in $
    life_years: float = 3.0
    watts: float = 0.0
    pue: float = 1.1
    kwh_price: float = 0.20

    def cost_per_hour(self):
        if self.hourly is not None: return self.hourly
        amort = self.price / (self.life_years * 365 * 24)
        power = self.watts / 1000 * self.pue * self.kwh_price
        return amort + power

def cost_per_million(hw, out_tok_s, utilization, in_tok_s=None, in_out_ratio=0.0):
    """$ per 1M output tokens. Optionally charge for prefill time: in_out_ratio input tokens per output token
    processed at in_tok_s (prefill throughput)."""
    seconds_per_out_token = 1 / out_tok_s + (in_out_ratio / in_tok_s if in_tok_s else 0.0)
    tokens_per_hour = 3600 / seconds_per_out_token * utilization
    return 1e6 * hw.cost_per_hour() / tokens_per_hour

def breakeven_utilization(hw, out_tok_s, api_price_per_m):
    return 1e6 * hw.cost_per_hour() / (3600 * out_tok_s * api_price_per_m)

if __name__ == "__main__":
    gpus = [Hardware("RTX 4090 (owned)", price=1800, watts=450),
            Hardware("Cloud 80GB GPU (rented)", hourly=2.50),
            Hardware("Free Colab T4", hourly=0.0)]
    for hw in gpus:
        for u in (0.05, 0.5, 0.9):
            print(f"{hw.name:26s} util {u:4.0%}: ${cost_per_million(hw, 600, u, in_tok_s=8000, in_out_ratio=3):7.3f} / M output tokens")
    print("4090 break-even utilization vs a $0.60/M API:", breakeven_utilization(gpus[0], 600, 0.60))
```
