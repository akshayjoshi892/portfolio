## 38.1 Low-Rank Updates: Why Fine-Tuning Changes Live in a Small Subspace

### 🧭 The Problem First
Full fine-tuning of a 7B model needs ~112 GB for the model states (Ch 28.3) and produces a full 14 GB copy per task.

### 💡 Intuition / Instinct
The *change* a fine-tune makes, $\Delta W = W_{ft} - W_0$, tends to have low effective rank: adapting behaviour or style needs only a few "directions" of change (Ch 3.5). So freeze $W_0$ and learn $\Delta W = BA$ with a tiny rank r. Only A and B get gradients and optimizer states, which cuts the trainable parameters by 100–1000×.

### 🖼️ Visual Mental Model

```text
 y = x W0ᵀ  +  (α/r) · x Aᵀ Bᵀ
     frozen      trainable: A (r×in), B (out×r)
 d=4096, r=16: 16.7M → 131K trainable per matrix
```

### 📐 The Math, Gently
Params per adapted matrix: $r(d_{in} + d_{out})$. The scaling $\frac{\alpha}{r}$ keeps the update magnitude stable when you change r.
Initialization: A ~ small random (Kaiming), **B = 0**, so ΔW = 0 at the start and the model begins exactly as the base model.

### 🛠️ Build It From Scratch

```python
import torch
torch.manual_seed(0)
# empirical check: SVD of a real fine-tuning delta concentrates energy in few directions
def energy_in_top_k(delta, k):
    s = torch.linalg.svdvals(delta.float()); return (s[:k] ** 2).sum().item() / (s ** 2).sum().item()
# after SFT (Ch 37), compare a layer's weights:
#   delta = sft_model.layers[4].attn.wq.weight - base_model.layers[4].attn.wq.weight
#   print([round(energy_in_top_k(delta, k), 3) for k in (1, 4, 16, 64)])
```

### 🔬 Experiment & Observe
Run the SVD energy analysis on your Ch 37 full SFT delta. Typically a large share of the energy sits in the top few dozen directions, which supports the low-rank hypothesis (it's not perfectly low-rank, which is why LoRA can "learn less").

### ⚠️ Failure Modes & Debugging
Initializing both A and B randomly → ΔW ≠ 0 at step 0, so the model starts off perturbed.

### 🧠 Expert Insight
- **Hu et al. (2021), LoRA.** **Aghajanyan et al. (2020):** the intrinsic dimension of fine-tuning.
- **Biderman et al. (2024):** LoRA "learns less and forgets less" than full fine-tuning; for large knowledge-heavy adaptation (code, math continued pretraining), full fine-tuning wins.

<details><summary>Answers</summary>

</details>

### 📌 Recap Card
- ΔW = BA, rank r, scaled by α/r.
- B = 0 at init.
- 100–1000× fewer trainable params.

> **Core intuition:** *Adapt a big model by learning a small correction in a few directions.*

## 38.2 A LoRA Layer From Scratch; Rank, Alpha, Target Modules

### 🧭 The Problem First
We need a drop-in replacement for `nn.Linear` and a way to inject it into chosen layers of any model.

### 💡 Intuition / Instinct
Wrap each target Linear: keep the original weight frozen, add the A and B parameters, and in forward compute `base(x) + dropout(x) @ Aᵀ @ Bᵀ · scale`. Target modules: attention projections (q, k, v, o) and, for more capacity, the MLP projections (gate, up, down). Including the MLP usually helps quality noticeably.

### 🖼️ Visual Mental Model

```text
 Llama block targets:  wq wk wv wo | w_gate w_up w_down
 "attention-only" LoRA: fewer params, less capacity
 "all-linear" LoRA:     recommended default
```

### 📐 The Math, Gently
Typical: r ∈ {8, 16, 64}, α = 2r (or α = r), dropout 0.05, lr 1e-4 to 3e-4 (higher than full fine-tuning, since only the small matrices are trained).
**rsLoRA:** scale by $\alpha/\sqrt r$ instead of $\alpha/r$ for stable learning at higher ranks.

### 🛠️ Build It From Scratch

```python
# nanoforge/posttrain/lora.py
import math, torch, torch.nn as nn

class LoRALinear(nn.Module):
    def __init__(self, base: nn.Linear, r=16, alpha=32, dropout=0.05, rslora=False):
        super().__init__()
        self.base = base
        for p in self.base.parameters(): p.requires_grad_(False)
        self.r = r
        self.scale = alpha / (math.sqrt(r) if rslora else r)
        self.lora_A = nn.Parameter(torch.empty(r, base.in_features))
        self.lora_B = nn.Parameter(torch.zeros(base.out_features, r))
        nn.init.kaiming_uniform_(self.lora_A, a=math.sqrt(5))
        self.drop = nn.Dropout(dropout)
        self.merged = False
    def forward(self, x):
        y = self.base(x)
        if self.merged: return y
        return y + (self.drop(x) @ self.lora_A.T @ self.lora_B.T) * self.scale
    @torch.no_grad()
    def merge(self):
        if not self.merged:
            self.base.weight += (self.lora_B @ self.lora_A).to(self.base.weight.dtype) * self.scale; self.merged = True
    @torch.no_grad()
    def unmerge(self):
        if self.merged:
            self.base.weight -= (self.lora_B @ self.lora_A).to(self.base.weight.dtype) * self.scale; self.merged = False

DEFAULT_TARGETS = ("wq", "wk", "wv", "wo", "w_gate", "w_up", "w_down")

def apply_lora(model, targets=DEFAULT_TARGETS, **kw):
    for p in model.parameters(): p.requires_grad_(False)
    replaced = 0
    for name, module in list(model.named_modules()):
        for child_name, child in list(module.named_children()):
            if isinstance(child, nn.Linear) and child_name in targets:
                setattr(module, child_name, LoRALinear(child, **kw)); replaced += 1
    trainable = sum(p.numel() for p in model.parameters() if p.requires_grad)
    total = sum(p.numel() for p in model.parameters())
    print(f"LoRA: replaced {replaced} layers; trainable {trainable:,} / {total:,} ({100*trainable/total:.2f}%)")
    return model

def lora_state_dict(model):
    return {k: v for k, v in model.state_dict().items() if "lora_" in k}

def merge_lora(model):
    for m in model.modules():
        if isinstance(m, LoRALinear): m.merge()
    return model
```

Use it with the SFT trainer from Ch 37 unchanged, since `sft_train` optimizes only the params with `requires_grad`:

### 🔬 Experiment & Observe
Sweep r ∈ {4, 16, 64} × targets ∈ {attention-only, all-linear} on your domain SFT data. Compare the custom-eval scores and general forgetting against full fine-tuning (Ch 37). Typical: all-linear r = 16 is close to full fine-tuning on the domain evals, with less forgetting.

### ⚠️ Failure Modes & Debugging
- Forgetting to freeze the base → it's not really LoRA (huge memory).
- Weight tying + LoRA on the lm_head/embeddings needs care; usually leave them frozen.
- The LoRA lr is too low (e.g. 1e-5 copied from full fine-tuning) → almost no learning.

### 🧠 Expert Insight
- **Dettmers et al. (2023)** found applying LoRA to *all* linear layers was key to matching full fine-tuning.
- **Kalajdzievski (2023), rsLoRA.**
- HF PEFT implements this same design (`LoraConfig(r, lora_alpha, target_modules)`).

<details><summary>Answers</summary>

### 📌 Recap Card
- `LoRALinear`: frozen base + A, B, scale α/r.
- Inject into the attention + MLP linears.
- Save only the adapter weights.

> **Core intuition:** *Freeze the giant; train a small, sharp tool attached to each of its hands.*

## 38.3 Merging Adapters

### 🧭 The Problem First
At inference, the extra adapter matmuls add latency. And you may want to ship a single standard model file.

### 💡 Intuition / Instinct
Since ΔW = BA·scale is just a matrix, **add it into the base weight**: $W' = W_0 + \frac{\alpha}{r}BA$. After merging, the model is a normal model, with zero inference overhead. Keep the unmerged base + adapters if you want to hot-swap many tasks on one base (multi-LoRA serving).

### 🖼️ Visual Mental Model

```text
 unmerged: x → W0 → + x→A→B·s   (two paths)       merged: x → (W0 + s·BA) → (one path)
```

### 📐 The Math, Gently
Merging is exact in full precision. When merging into a *quantized* base (QLoRA), you must dequantize, merge, then requantize (or keep it in bf16), which introduces small errors.

### 🛠️ Build It From Scratch

```python
import copy, torch
x = torch.randint(0, 100, (1, 16))
m = copy.deepcopy(model).eval()
with torch.no_grad():
    y1, _ = m(x, all_logits=True); merge_lora(m); y2, _ = m(x, all_logits=True)
print("merge max diff:", (y1 - y2).abs().max().item())      # ~1e-6 in fp32
```

Multi-adapter hot-swapping:

```python
def load_adapter(model, path):
    sd = torch.load(path, map_location="cpu"); missing = model.load_state_dict(sd, strict=False)
    return model
# serve one base; per request, load/choose adapter weights (or batch many adapters: S-LoRA / Punica)
```

### 🔬 Experiment & Observe
Measure the decode latency unmerged vs merged: a small but measurable difference (the extra small matmuls per layer).

### ⚠️ Failure Modes & Debugging
- Merging twice → the update is doubled. Track the `merged` flag (done).
- Merging in bf16 loses precision when ΔW is tiny relative to W0. Merge in fp32, then cast.

### 🧠 Expert Insight
- **Sheng et al. (2023), S-LoRA:** serving thousands of adapters concurrently from one base.
- **Model merging** (task arithmetic, TIES, DARE) combines several fine-tunes' deltas into one model, a cheap way to combine skills.

### ✅ Check Your Instinct
1. Why does merging remove the inference overhead?

<details><summary>Answers</summary>

1. The adapter becomes part of the single weight matrix, so there are no extra computations.
</details>

### 📌 Recap Card
- Merge: W' = W0 + s·BA (in fp32).
- Unmerged adapters allow hot-swapping.
- Track the merge state.

> **Core intuition:** *A LoRA is a patch you can wear, or sew in permanently.*

## 38.4 QLoRA: 4-bit NF4 Base Plus LoRA; DoRA Preview

### 🧭 The Problem First
Even with LoRA, the frozen base weights must sit in GPU memory: 14 GB for 7B in bf16, 140 GB for 70B.

### 💡 Intuition / Instinct
Store the frozen base in **4-bit** (dequantized to bf16 on the fly, block by block, for each matmul), and train bf16 LoRA adapters on top. The gradients flow *through* the dequantized weights into the adapters; the 4-bit weights never change. QLoRA's ingredients:
1. **NF4 (NormalFloat4):** 16 quantization levels placed at the quantiles of a normal distribution. Weights are roughly normal, so every level is used equally: information-theoretically optimal for normal data.
2. **Block-wise scaling:** one absmax scale per block of 64 weights (outliers only hurt their own block).
3. **Double quantization:** quantize the scales too, to save ~0.4 bits/param.
4. **Paged optimizers:** spill optimizer states to CPU on memory spikes.

### 🖼️ Visual Mental Model

```text
 W (bf16) → blocks of 64 → scale = absmax/1 → normalized → nearest of 16 NF4 levels → 4-bit codes
 forward: codes → NF4 lookup × scale → bf16 W_block → matmul (+ LoRA path in bf16)
 memory: 7B ≈ 3.5 GB (weights) + adapters + activations
```

### 📐 The Math, Gently
NF4 levels ≈ the quantiles $q_i = \frac12\left[\Phi^{-1}\!\left(\frac{i}{2^4+1}\right) + \Phi^{-1}\!\left(\frac{i+1}{2^4+1}\right)\right]$, normalized to [−1, 1], with an exact zero included (the published table is asymmetric: 8 positive and 7 negative levels plus 0).
Bits per param ≈ 4 + 32/64 (the fp32 absmax per 64 weights) = 4.5, or ≈ 4.127 with double quantization.

### 🛠️ Build It From Scratch

```python
# nanoforge/quant/nf4.py
import torch, torch.nn as nn, torch.nn.functional as F
NF4_LEVELS = torch.tensor([-1.0, -0.6961928009986877, -0.5250730514526367, -0.39491748809814453,
    -0.28444138169288635, -0.18477343022823334, -0.09105003625154495, 0.0, 0.07958029955625534,
    0.16093020141124725, 0.24611230194568634, 0.33791524171829224, 0.44070982933044434,
    0.5626170039176941, 0.7229568362236023, 1.0])

def nf4_quantize(W, block=64):
    flat = W.float().flatten(); pad = (-flat.numel()) % block
    flat = F.pad(flat, (0, pad)).view(-1, block)
    absmax = flat.abs().max(1, keepdim=True).values.clamp_min(1e-12)
    normed = flat / absmax                                            # [-1, 1]
    codes = (normed.unsqueeze(-1) - NF4_LEVELS.to(W.device)).abs().argmin(-1).to(torch.uint8)
    packed = (codes[:, 0::2] << 4) | codes[:, 1::2]                   # two 4-bit codes per byte
    return packed, absmax.squeeze(1), W.shape, pad

def nf4_dequantize(packed, absmax, shape, pad, dtype=torch.bfloat16):
    hi, lo = packed >> 4, packed & 0xF
    codes = torch.stack([hi, lo], -1).view(packed.size(0), -1).long()
    vals = NF4_LEVELS.to(packed.device)[codes] * absmax[:, None]
    flat = vals.flatten(); flat = flat[:flat.numel() - pad] if pad else flat
    return flat.view(shape).to(dtype)

class Linear4bit(nn.Module):
    """Frozen NF4 weight; dequantizes per forward (slow in pure PyTorch, but exact semantics)."""
    def __init__(self, linear: nn.Linear, block=64):
        super().__init__()
        packed, absmax, shape, pad = nf4_quantize(linear.weight.data, block)
        self.register_buffer("packed", packed); self.register_buffer("absmax", absmax)
        self.shape, self.pad = shape, pad
        self.in_features, self.out_features = linear.in_features, linear.out_features
        self.bias = linear.bias
    def forward(self, x):
        W = nf4_dequantize(self.packed, self.absmax, self.shape, self.pad, x.dtype)
        return F.linear(x, W, self.bias)

W = torch.randn(512, 512) * 0.02
p, a, s, pad = nf4_quantize(W); Wq = nf4_dequantize(p, a, s, pad, torch.float32)
print("rel error:", ((W - Wq).norm() / W.norm()).item(), "bytes:", p.numel() + a.numel() * 4, "vs bf16", W.numel() * 2)
```

QLoRA = quantize the base's linears to `Linear4bit`, then wrap them with `LoRALinear` (whose `base` is now the 4-bit layer):

```python
def apply_qlora(model, targets=DEFAULT_TARGETS, r=16, alpha=32):
    for name, module in list(model.named_modules()):
        for cn, child in list(module.named_children()):
            if isinstance(child, nn.Linear) and cn in targets:
                # LoRALinear only needs base(x), base.in_features, base.out_features: Linear4bit provides all three
                setattr(module, cn, LoRALinear(Linear4bit(child), r=r, alpha=alpha))
    for n, p in model.named_parameters(): p.requires_grad_("lora_" in n)
    return model
```

(For production speed use `bitsandbytes` 4-bit kernels, which fuse the dequantization into the matmul.)

**DoRA (Weight-Decomposed LoRA):** decompose W into magnitude m (per output column norm) and direction V/‖V‖; apply LoRA to the direction and train m separately: $W' = m\frac{W_0 + BA}{\|W_0 + BA\|_c}$. It often gives a small but consistent gain over LoRA at the same rank.

### 🔬 Experiment & Observe
Compare LoRA (bf16 base) and QLoRA (NF4 base) at the same r on your domain SFT: the scores should be within noise, with ~3.5× less memory for the base weights. Also quantize with a uniform 4-bit grid instead of NF4 and compare the reconstruction error: NF4 is lower for normally distributed weights.

### ⚠️ Failure Modes & Debugging
- The pure-PyTorch dequantization per forward pass is slow; fine for learning, use fused kernels for real runs.
- Merging LoRA into an NF4 base requires dequantization and gives a bf16 model (or requantize and accept a small error).

### 🧠 Expert Insight
- **Dettmers et al. (2023), QLoRA:** Guanaco 65B fine-tuned on a single 48 GB GPU.
- **Liu et al. (2024), DoRA.**
- **LoftQ (2023)** initializes LoRA to compensate for the quantization error.

### ✅ Check Your Instinct
1. Why NF4 rather than uniform 4-bit?
2. Do the 4-bit weights receive gradient updates in QLoRA?

<details><summary>Answers</summary>

1. The weights are roughly normal; quantile-placed levels minimize the expected error for that distribution.
2. No. The gradients flow through them to the LoRA adapters, which are the only thing trained.
</details>

### 📌 Recap Card
- QLoRA: NF4 block-quantized frozen base + bf16 LoRA.
- ~4.1–4.5 bits/param for the base.
- DoRA: magnitude/direction decomposition for extra quality.

> **Core intuition:** *Compress the giant you don't train; spend precision only on the small part you do.*
