## 28.1 GPU Anatomy: SMs, HBM, SRAM, Tensor Cores

### 🧭 The Problem First
You treat the GPU as a magic box that "does math fast". Then you can't explain why a softmax takes as long as a matmul 10× its FLOPs, or why batch size changes throughput.

### 💡 Intuition / Instinct
A GPU is a **factory with thousands of workers and a slow warehouse**:
- **SMs (streaming multiprocessors):** ~100+ independent workshops, each running many threads in lockstep groups (warps of 32).
- **Tensor cores:** specialized units in each SM that do small matrix multiplies (e.g. 16×16) extremely fast in bf16/fp8.
- **HBM (global memory):** the warehouse. Large (24–80+ GB) and fast by CPU standards (1–3+ TB/s), but *slow relative to compute*.
- **SRAM (shared memory / L1, registers):** each workshop's workbench. Tiny (~100–256 KB per SM) but ~10× faster than HBM.

The golden rule: **moving data costs more than computing on it.** Fast kernels load a tile from HBM into SRAM once, do as much math on it as possible, and write back once.

### 🖼️ Visual Mental Model

```text
 ┌──────────────────── GPU ─────────────────────┐
 │ SM ─ SM ─ SM ─ ... ─ SM   (each: tensor cores, registers, ~200KB SRAM)
 │   ↑↓ ~20+ TB/s aggregate on-chip bandwidth
 │ L2 cache (~50 MB)
 │   ↑↓ ~1–3 TB/s
 │ HBM (24–80 GB)
 └──────────────────────────────────────────────┘
          ↑↓ PCIe ~32–64 GB/s / NVLink ~900 GB/s
        CPU RAM / other GPUs
```

### 📐 The Math, Gently
Approximate specs:

| GPU | bf16 dense TFLOPs | HBM GB/s | HBM GB |
|---|---|---|---|
| T4 | 65 | 320 | 16 |
| RTX 4090 | 165 | 1,008 | 24 |
| A100 80GB | 312 | 2,039 | 80 |
| H100 SXM | 989 | 3,350 | 80 |

Ratio (FLOPs per byte moved) for an A100: 312e12 / 2.0e12 ≈ **153 FLOPs/byte**. An op must do ~150 FLOPs per byte it reads or writes to keep the tensor cores busy.

### 🛠️ Build It From Scratch

```python
import torch, time
def bench(fn, *args, iters=50):
    for _ in range(5): fn(*args)
    torch.cuda.synchronize(); t = time.time()
    for _ in range(iters): fn(*args)
    torch.cuda.synchronize(); return (time.time() - t) / iters

if torch.cuda.is_available():
    n = 4096
    a = torch.randn(n, n, device="cuda", dtype=torch.bfloat16); b = torch.randn_like(a)
    t_mm = bench(torch.matmul, a, b)
    print(f"matmul: {2*n**3/t_mm/1e12:.1f} TFLOP/s")
    x = torch.randn(64 * 1024 * 1024, device="cuda", dtype=torch.bfloat16)
    t_add = bench(torch.add, x, x)
    print(f"elementwise add: {3 * x.numel() * 2 / t_add / 1e9:.0f} GB/s  ({x.numel()/t_add/1e12:.2f} TFLOP/s)")
    print(torch.cuda.get_device_properties(0))
```

### 🔬 Experiment & Observe
The matmul reaches a large fraction of peak TFLOPs; the elementwise add achieves only ~0.1–1 TFLOP/s but near-peak *bandwidth*. **Same GPU, completely different bottlenecks.**

### ⚠️ Failure Modes & Debugging
Benchmarking without warmup (the first calls include CUDA init/autotuning) or without synchronization.

### 🧠 Expert Insight
Horace He's "Making Deep Learning Go Brrrr From First Principles" (2022) frames performance as compute-, memory-bandwidth- or overhead-bound. It's essential reading.

### ✅ Check Your Instinct
1. Why is SRAM important for fast kernels?
2. FLOPs/byte needed to saturate an H100?

<details><summary>Answers</summary>

1. Reusing data from fast on-chip memory avoids slow HBM traffic.
2. ≈ 989e12 / 3.35e12 ≈ 295.
</details>

### 📌 Recap Card
- SMs + tensor cores (compute); HBM (big, slow); SRAM (tiny, fast).
- Data movement dominates.
- ~150–300 FLOPs/byte to be compute-bound.

> **Core intuition:** *The GPU is a genius chef with a slow waiter; fast code minimizes the waiter's trips.*

## 28.2 Compute-Bound vs Memory-Bound: The Roofline Model

### 🧭 The Problem First
Which parts of your model are slow because of arithmetic, and which because of memory traffic? Optimizing the wrong one wastes effort.

### 💡 Intuition / Instinct
**Arithmetic intensity** $I$ = FLOPs / bytes moved. The **roofline**: achievable FLOP/s = min(peak compute, I × bandwidth). Below the "ridge point" (≈ 150 for an A100) you are memory-bound; above it, compute-bound.
- Big matmuls: high I → compute-bound ✓.
- Elementwise ops, softmax, LayerNorm, GELU, the dropout mask: I ≈ 1 → memory-bound.
- **Decoding one token at a time:** matrix × *vector*, so I ≈ 1–2 → memory-bound! That's why generation is slow and batching helps (Ch 45).

### 🖼️ Visual Mental Model

```text
 FLOP/s
   │            ___________ peak compute
   │          /
   │        /   ← slope = bandwidth
   │      /
   │    /  • softmax (I≈1)       • big matmul (I≈1000)
   └──────────────┬─────────────▶ arithmetic intensity (FLOPs/byte)
               ridge ≈ 150
```

### 📐 The Math, Gently
Matmul (M×K)@(K×N) in bf16: FLOPs = 2MKN; bytes ≈ 2(MK + KN + MN).
Square n = 4096: I ≈ $\frac{2n^3}{6n^2} = n/3 ≈ 1365$ → compute-bound.
Decode: (1×C)@(C×C) with C = 4096: FLOPs 2C², bytes ≈ 2C² (the weights dominate) → I ≈ 1 → memory-bound. **With batch B, I ≈ B**, so batching decode requests up to ~150 is nearly free.

### 🛠️ Build It From Scratch

```python
def matmul_intensity(M, K, N, bytes_per=2):
    return 2 * M * K * N / (bytes_per * (M * K + K * N + M * N))
def roofline(I, peak=312e12, bw=2.0e12): return min(peak, I * bw)
for (M, K, N, name) in [(4096, 4096, 4096, "square matmul"), (1, 4096, 4096, "decode B=1"),
                        (64, 4096, 4096, "decode B=64"), (8192, 768, 3072, "GPT2 MLP fc")]:
    I = matmul_intensity(M, K, N)
    print(f"{name:14s} I={I:7.1f} FLOPs/B  attainable {roofline(I)/1e12:6.1f} TFLOP/s")
```

### 🔬 Experiment & Observe
Benchmark (B×4096)@(4096×4096) for B = 1, 8, 64, 512 and plot the achieved TFLOP/s vs B. It rises linearly (memory-bound) until the ridge, then flattens (compute-bound). You've measured the roofline.

### ⚠️ Failure Modes & Debugging
- Optimizing FLOPs in memory-bound code (no gain).
- Tiny batch sizes in training give low MFU.

### 🧠 Expert Insight
Williams et al. (2009), "Roofline". The prefill/decode split in inference (Ch 43, 45) is the roofline in action: prefill is compute-bound, decode is memory-bound.

### ✅ Check Your Instinct
1. Is LayerNorm compute- or memory-bound?
2. Why does batching decode requests increase throughput almost for free?

<details><summary>Answers</summary>

1. Memory-bound (few FLOPs per byte).
2. The weights are read once per step regardless of the batch; the extra FLOPs are nearly free until the compute-bound limit.
</details>

### 📌 Recap Card
- Intensity = FLOPs/byte; ridge ≈ peak/bandwidth.
- Matmuls: compute-bound; elementwise/norm/softmax/decode: memory-bound.
- Batch to raise the intensity.

> **Core intuition:** *Is your GPU waiting on math or on memory? The roofline tells you.*

## 28.3 Memory Math: Params + Grads + Optimizer States + Activations

### 🧭 The Problem First
"Will a 1B model fit on my 24 GB GPU for training, with batch 8 × 2048?" You need an exact answer before launching.

### 💡 Intuition / Instinct
Training memory = **model states** + **activations** (+ temporary buffers).
- Model states (mixed precision with AdamW): FP32 master weights (4) + FP32 grads (4; or bf16, 2) + Adam m (4) + v (4) = **16 bytes/param** (the Ch 1.3 figure), plus bf16 copies if you keep them.
- Activations: everything saved during forward for backward. They scale with **B × T × L × C** (and B × H × T² for naive attention).

### 🖼️ Visual Mental Model

```text
 1B-param model, bs 8 × T 2048:
 ┌ weights fp32  4 GB ┐
 │ grads fp32    4 GB │ 16 GB model states
 │ Adam m        4 GB │
 └ Adam v        4 GB ┘
 + activations: ~34·B·T·C·L bytes (bf16, with flash attention)   → often the larger part!
```

### 📐 The Math, Gently
Per-layer activation memory for a transformer block in bf16, without recomputation (Korthikanti et al., 2022): ≈ $sbh(34 + 5\frac{as}{h})$ bytes, where s = T, b = B, h = C, a = heads. The $5as/h$ term is the attention matrix, eliminated by FlashAttention, which leaves ≈ **34·B·T·C bytes per layer**.
Example: B = 8, T = 2048, C = 2048, L = 24: 34 × 8 × 2048 × 2048 × 24 ≈ 27.4 GB. Model states for ~1.2B params: ~19 GB. **Total ≈ 46 GB, which doesn't fit in 24 GB.** Hence activation checkpointing (28.4), a smaller micro-batch with accumulation, or sharding (Ch 31).

### 🛠️ Build It From Scratch

```python
# nanoforge/memory.py
def training_memory_gb(N, L, C, H, B, T, V, bytes_state=16, flash=True, ckpt=False, logits_bytes=4):
    states = N * bytes_state
    per_layer = 34 * B * T * C + (0 if flash else 5 * B * H * T * T)
    acts = (2 * B * T * C * L) if ckpt else per_layer * L          # ckpt: keep only layer inputs (bf16)
    logits = B * T * V * logits_bytes * 2                             # logits + grad of logits (fp32)
    return {"states_gb": states / 1e9, "acts_gb": acts / 1e9, "logits_gb": logits / 1e9,
            "total_gb": (states + acts + logits) / 1e9}
print(training_memory_gb(N=1.2e9, L=24, C=2048, H=16, B=8, T=2048, V=32000))
print(training_memory_gb(N=1.2e9, L=24, C=2048, H=16, B=8, T=2048, V=32000, ckpt=True))
```

Measure real memory to validate:

```python
import torch
from nanoforge.models.gpt import GPT, GPTConfig
if torch.cuda.is_available():
    cfg = GPTConfig(n_layer=8, n_head=8, n_embd=512, block_size=1024, vocab_size=8192)
    m = GPT(cfg).cuda(); opt = torch.optim.AdamW(m.parameters())
    x = torch.randint(0, 8192, (8, 1024), device="cuda")
    torch.cuda.reset_peak_memory_stats()
    with torch.autocast("cuda", dtype=torch.bfloat16): _, loss = m(x, x)
    loss.backward(); opt.step()
    print("peak GB:", torch.cuda.max_memory_allocated() / 1e9)
    print("estimate:", training_memory_gb(sum(p.numel() for p in m.parameters()), 8, 512, 8, 8, 1024, 8192))
```

### 🔬 Experiment & Observe
Compare the estimate with the measurement; expect agreement within ~20–30% (allocator fragmentation, CUDA context ~0.5–1 GB, and temporaries). Note how the **logits** (B × T × V in fp32) can be huge for large vocabularies. That is why production code computes the cross-entropy in chunks.

### ⚠️ Failure Modes & Debugging
- OOM on the *first backward* but not the forward: activations + grads peak there.
- OOM appearing only on longer batches: memory scales with T (and T² without flash attention).
- Fragmentation: set `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`.

### 🧠 Expert Insight
- **Rajbhandari et al. (2020), ZeRO:** the 16-byte accounting.
- **Korthikanti et al. (2022), "Reducing Activation Recomputation in Large Transformer Models":** the 34sbh formula and selective recomputation.
- Liger Kernel / fused linear + cross-entropy avoid materializing the full logits.

### ✅ Check Your Instinct
1. Model-state memory for 3B params with AdamW mixed precision?
2. Why can the logits dominate memory for small models with big vocabularies?

<details><summary>Answers</summary>

1. ≈ 48 GB.
2. B·T·V fp32 values (plus their gradients) can exceed all the other activations when V ≫ C.
</details>

### 📌 Recap Card
- Model states ≈ 16 bytes/param.
- Activations ≈ 34·B·T·C bytes/layer (bf16, flash).
- Logits B·T·V can be huge; measure and compare.

> **Core intuition:** *Memory = what you are (params + optimizer) + what you remember (activations).*

## 28.4 Activation Checkpointing: Trading Compute for Memory

### 🧭 The Problem First
The activations for long sequences and deep models exceed the GPU memory, even at micro-batch 1.

### 💡 Intuition / Instinct
Don't store every intermediate activation. Save only each block's **input**. During backward, **recompute** the block's forward from that input to regenerate what's needed. You pay ~one extra forward pass (+33% compute) and save most of the activation memory. It's like remembering only the start of each chapter and rereading it when needed.

**Selective checkpointing:** only recompute the cheap-but-memory-hungry parts (e.g. attention softmax, GELU), which saves memory at a small compute cost.

### 🖼️ Visual Mental Model

```text
 normal:       store all intermediates of all blocks   (memory ∝ L × 34BTC)
 checkpointed: store block inputs only                  (memory ∝ L × 2BTC + one block's intermediates)
               backward: recompute block l forward → backward block l → free
```

### 📐 The Math, Gently
Compute: training ≈ 6N → with full recomputation ≈ 8N per token (one extra forward), so MFU accounting uses 6N while "HFU" counts 8N.
Memory: from $34BTCL$ to ≈ $2BTCL + 34BTC$.

### 🛠️ Build It From Scratch

```python
# in GPT.forward: optional checkpointing per block
import torch.utils.checkpoint as ckpt
# ...
for block in self.transformer.h:
    if self.training and getattr(self.cfg, "grad_checkpoint", False):
        x = ckpt.checkpoint(block, x, use_reentrant=False)
    else:
        x = block(x)
```

Add `grad_checkpoint: bool = False` to `GPTConfig`. Measure it:

```python
for gc in [False, True]:
    cfg = GPTConfig(n_layer=12, n_head=12, n_embd=768, block_size=1024, vocab_size=8192); cfg.grad_checkpoint = gc
    m = GPT(cfg).cuda(); torch.cuda.reset_peak_memory_stats()
    x = torch.randint(0, 8192, (8, 1024), device="cuda")
    with torch.autocast("cuda", dtype=torch.bfloat16): _, loss = m(x, x)
    loss.backward()
    print(f"checkpointing={gc}: peak {torch.cuda.max_memory_allocated()/1e9:.2f} GB")
```

### 🔬 Experiment & Observe
Expect a large memory reduction (often 2–4× for activations) and ~20–35% slower steps. Use the freed memory for a larger micro-batch, which can recover some of the throughput.

### ⚠️ Failure Modes & Debugging
- Dropout inside checkpointed blocks must replay the same RNG. PyTorch's checkpoint preserves the RNG state by default (`preserve_rng_state=True`).
- `use_reentrant=True` (the old default) has sharp edges with inputs that don't require grad. Use `False`.

### 🧠 Expert Insight
- **Chen et al. (2016), "Training Deep Nets with Sublinear Memory Cost":** √L checkpointing.
- Megatron's **selective recomputation** recomputes only the attention core, reducing the overhead to a few percent.
- Many frontier training runs use a mix of checkpointing, sequence parallelism and offloading.

### ✅ Check Your Instinct
1. Compute overhead of full recomputation?
2. What's stored per block with checkpointing?

<details><summary>Answers</summary>

1. ~one extra forward pass: ≈ +33% of the training FLOPs (6N → 8N).

</details>

### 📌 Recap Card
- Store block inputs, recompute the internals in backward.
- ~+33% compute, large memory savings.
- Selective recomputation for cheap wins.

> **Core intuition:** *Forget the details, remember the chapter starts, and reread when needed.*
