## 36.1 Designing Evals for Your Domain

### 🧭 The Problem First
Your Capstone model is for (say) answering questions about your domain's manuals. MMLU says nothing about that. How do you know whether a change improved the thing you care about?

### 💡 Intuition / Instinct
Treat evals like unit tests for capabilities:
1. **Define the behaviours** you need (facts from the manuals, refusing out-of-scope questions, correct formatting, citing sources).
2. **Write items** for each behaviour, with *verifiable* answers where possible (exact match, a regex, a numeric tolerance, unit tests) and rubrics otherwise.
3. **Cover the difficulty spread**: easy (sanity), medium, hard (frontier of ability), and adversarial (tricky or out-of-scope).
4. **Hold them out**: never train on them; check for contamination (Ch 35.4).
5. **Size:** 100–500 items per behaviour gives a usable signal (±3–5%).

### 🖼️ Visual Mental Model

```text
 eval suite
 ├── knowledge_qa.jsonl    (exact/regex match)          150 items
 ├── reasoning_numeric.jsonl (numeric tolerance)         100 items
 ├── format_json.jsonl     (schema validation)            80 items
 ├── refusal_oos.jsonl     (should decline)               60 items
 └── open_ended.jsonl      (rubric + LLM judge)          100 items
```

### 📐 The Math, Gently
To detect a 5-point improvement with ~80% power at α = 0.05 on binary items (p ≈ 0.5), you need roughly $n ≈ \frac{(z_{0.975} + z_{0.8})^2\cdot 2p(1-p)}{\Delta^2} = \frac{(1.96 + 0.84)^2\cdot0.5}{0.0025} ≈ 1570$ unpaired. Paired designs need far fewer (often a few hundred).

### 🛠️ Build It From Scratch

```python
# nanoforge/eval/custom.py
import json, re

def check_answer(pred: str, item: dict) -> bool:
    kind = item.get("check", "exact")
    gold = item["answer"]
    p = pred.strip()
    if kind == "exact":   return p.lower() == str(gold).strip().lower()
    if kind == "contains": return str(gold).lower() in p.lower()
    if kind == "regex":   return re.search(gold, p, flags=re.I | re.S) is not None
    if kind == "numeric":
        m = re.findall(r"-?\d+\.?\d*", p.replace(",", ""))
        return bool(m) and abs(float(m[-1]) - float(gold)) <= item.get("tol", 1e-6)
    if kind == "json":
        try: obj = json.loads(p[p.index("{"): p.rindex("}") + 1])
        except Exception: return False
        return all(k in obj for k in gold)                          # gold = list of required keys
    if kind == "refusal":
        return any(s in p.lower() for s in ["i can't", "i cannot", "not able to", "outside", "don't have information"])
    raise ValueError(kind)

def load_suite(paths):
    return {p.split("/")[-1].replace(".jsonl", ""): [json.loads(l) for l in open(p, encoding="utf-8")] for p in paths}
```

Example item formats:

```json
{"id": "kb-001", "prompt": "What is the maximum operating temperature of the X200 pump?", "answer": "85", "check": "numeric", "tol": 0.5, "tags": ["facts", "easy"]}
{"id": "fmt-004", "prompt": "Return a JSON object with keys name and part_id for the X200 impeller.", "answer": ["name", "part_id"], "check": "json"}
{"id": "oos-010", "prompt": "What's the best stock to buy today?", "answer": "", "check": "refusal"}
```

### 🔬 Experiment & Observe
Write 50 items for your domain *before* any post-training. Evaluate your base Capstone model (few-shot prompted) to get the baseline. This baseline makes every later improvement measurable.

### ⚠️ Failure Modes & Debugging
- Items that are ambiguous or have wrong gold answers: have a second person (or a careful review pass) check them; ~5% of the items in public benchmarks have label errors.
- Evals too easy (everything passes) or too hard (nothing passes) give no gradient of signal.
- Overfitting to the eval: when you iterate against it, keep a *hidden* split for the final report.

### 🧠 Expert Insight
Frontier labs maintain hundreds of internal evals per capability area and run them automatically on every checkpoint. Many product teams find a small custom eval more predictive of user satisfaction than any public benchmark.

### ✅ Check Your Instinct
1. Why prefer verifiable answers?
2. Why keep a hidden split?

<details><summary>Answers</summary>

1. They're cheap, objective and reproducible, with no judge noise.
2. Iterating against an eval overfits your decisions to it; the hidden split gives an unbiased final estimate.
</details>

### 📌 Recap Card
- Behaviours → items → verifiable checks.
- Cover the difficulty spread and adversarial cases.
- Hold out, dedupe, and keep a hidden split.

> **Core intuition:** *An eval is a unit test for a capability; write it before you train for it.*

## 36.2 LLM-as-Judge: Rubrics, Pairwise Comparison, Biases

### 🧭 The Problem First
For open-ended outputs (explanations, summaries, helpfulness) there's no exact answer. Human raters are slow and expensive. Can a strong LLM grade outputs reliably?

### 💡 Intuition / Instinct
Yes, with care. A strong judge model scores a response against a **rubric** (single-answer grading, e.g. 1–10 with criteria) or compares two responses (**pairwise**, usually more reliable). Known biases:
- **Position bias:** it prefers the first (or second) answer. Mitigate by judging both orders and requiring consistency.
- **Verbosity bias:** it prefers longer answers. Mitigate with length-controlled scoring or rubric instructions.
- **Self-preference:** it prefers its own style or model family.
- **Formatting bias:** markdown and lists look "better".

Validate the judge: measure its agreement with human labels on 50–100 items.

### 🖼️ Visual Mental Model

```text
 question + answer A + answer B + rubric ─▶ judge ─▶ "A" | "B" | "tie"
 swap order ─▶ judge ─▶ consistent? keep : count as tie
```

### 📐 The Math, Gently
Pairwise results → win rate, or **Bradley–Terry** strengths: $P(i \succ j) = \frac{e^{\beta_i}}{e^{\beta_i} + e^{\beta_j}}$, fit by logistic regression (the basis of Chatbot Arena's Elo-style ratings, and also of reward models, Ch 39).
Judge–human agreement: Cohen's κ, or the raw agreement vs the human–human agreement.

### 🛠️ Build It From Scratch

```python
# nanoforge/eval/judge.py
import json, re, math, random

PAIRWISE_TEMPLATE = """You are an impartial judge. Compare two responses to the user's question.
Criteria: correctness (most important), helpfulness, clarity, conciseness. Do not favour length or position.

[Question]
{question}

[Response A]
{a}

[Response B]
{b}

Think briefly, then output a final line exactly: VERDICT: A, VERDICT: B, or VERDICT: TIE"""

def parse_verdict(text):
    m = re.search(r"VERDICT:\s*(A|B|TIE)", text.upper())
    return m.group(1) if m else "TIE"

def judge_pair(judge_fn, question, a, b):
    """judge_fn(prompt:str)->str. Judges both orders; returns +1 (a wins), -1 (b wins), 0 (tie/inconsistent)."""
    v1 = parse_verdict(judge_fn(PAIRWISE_TEMPLATE.format(question=question, a=a, b=b)))
    v2 = parse_verdict(judge_fn(PAIRWISE_TEMPLATE.format(question=question, a=b, b=a)))
    s1 = {"A": 1, "B": -1, "TIE": 0}[v1]; s2 = {"A": -1, "B": 1, "TIE": 0}[v2]
    return s1 if s1 == s2 else 0

def bradley_terry(matches, models, iters=2000, lr=0.1):
    """matches: list of (winner, loser). Returns strength scores (log-scale)."""
    beta = {m: 0.0 for m in models}
    for _ in range(iters):
        grad = {m: 0.0 for m in models}
        for w, l in matches:
            p = 1 / (1 + math.exp(beta[l] - beta[w]))
            grad[w] += 1 - p; grad[l] -= 1 - p
        for m in models: beta[m] += lr * grad[m] / max(1, len(matches))
    mean = sum(beta.values()) / len(beta)
    return {m: round(v - mean, 3) for m, v in beta.items()}
```

`judge_fn` can wrap any capable model: a local open model served by your engine (Ch 45), or an API model you have access to.

### 🔬 Experiment & Observe
Label 50 pairwise comparisons yourself. Run the judge with and without order swapping and compute its agreement with your labels. Then test the verbosity bias: pad the worse answer with filler and see whether the judge flips.

### ⚠️ Failure Modes & Debugging
- Using a judge *weaker* than the models being judged gives noisy, unreliable verdicts.
- Judge prompts leaking the "reference answer" style lead the judge to reward mimicry.
- Using the same judge as the reward in RL → reward hacking of the judge's biases (Ch 39).

### 🧠 Expert Insight
- **Zheng et al. (2023), "Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena":** strong judges reach human-level agreement (~80%) on pairwise tasks, with documented biases.
- **Dubois et al. (2024):** length-controlled AlpacaEval.
- **Chiang et al. (2024), Chatbot Arena:** crowdsourced pairwise preferences + Bradley–Terry.

### ✅ Check Your Instinct
1. How do you mitigate position bias?
2. How do you validate a judge?

<details><summary>Answers</summary>

1. Evaluate both orders and only count consistent verdicts (otherwise a tie).
2. Measure its agreement with human labels on a sample; compare it with the human–human agreement.
</details>

### 📌 Recap Card
- Rubric or pairwise; pairwise is usually more reliable.
- Swap the order; watch for verbosity/self-preference bias.
- Validate against human labels; aggregate with Bradley–Terry.

> **Core intuition:** *A judge is an instrument; calibrate it before trusting its readings.*

## 36.3 Building an Eval Harness for the Project

### 🧭 The Problem First
You'll produce dozens of checkpoints (SFT variants, LoRA ranks, DPO betas). Evaluating them by hand is impossible, and inconsistent evaluation makes comparisons meaningless.

### 💡 Intuition / Instinct
One command: `python scripts/eval_harness.py --ckpt X --suite evals/`. It produces a JSON report with every metric, its CI, the sampling settings, the eval versions, and a sample of the outputs. The same prompts, decoding settings and seeds for every checkpoint. Compare the reports with paired statistics.

### 🖼️ Visual Mental Model

```text
 checkpoint ─▶ harness(config: decoding, prompts, suites) ─▶ report.json
                                                               ├─ bpb (domain, general)
                                                               ├─ mc tasks ± CI
                                                               ├─ custom suite per-tag accuracy ± CI
                                                               ├─ judge win-rate vs baseline
                                                               └─ sample outputs
 compare(report_A, report_B) → paired diffs with CIs
```

### 📐 The Math, Gently
Per-tag accuracy with CIs; overall = the macro average over the behaviours (so that big suites don't dominate).

### 🛠️ Build It From Scratch

```python
# scripts/eval_harness.py
import argparse, glob, json, time, torch
from nanoforge.eval.custom import check_answer, load_suite
from nanoforge.eval.stats import accuracy_ci, paired_bootstrap
from nanoforge.eval.perplexity import bits_per_byte
from nanoforge.sampling import generate

def load_model(ckpt_path, device):
    ck = torch.load(ckpt_path, map_location=device, weights_only=False)
    from nanoforge.models.llama import Llama, LlamaConfig
    model = Llama(LlamaConfig(**ck["model_config"])).to(device); model.load_state_dict(ck["model"]); model.eval()
    return model

def run_generation(model, tok, prompt, max_new, device, chat_format=None):
    text = chat_format(prompt) if chat_format else prompt
    ids = torch.tensor([tok.encode(text)], device=device)
    out = generate(model, ids, max_new, model.cfg.block_size, temperature=0.0,
                   eos_id=tok.special_tokens.get("<|im_end|>") or tok.special_tokens.get("<|endoftext|>"))
    return tok.decode(out[0, ids.size(1):].tolist()).replace("<|im_end|>", "").strip()

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--ckpt", required=True); ap.add_argument("--tokenizer", required=True)
    ap.add_argument("--suite", default="evals/*.jsonl"); ap.add_argument("--val_texts", default=None)
    ap.add_argument("--chat", action="store_true"); ap.add_argument("--out", required=True)
    ap.add_argument("--max_new", type=int, default=128)
    a = ap.parse_args(); dev = "cuda" if torch.cuda.is_available() else "cpu"
    from nanoforge.tokenizer.regex_bpe import RegexBPE
    tok = RegexBPE().load(a.tokenizer); model = load_model(a.ckpt, dev)
    chat = (lambda p: f"<|im_start|>user\n{p}<|im_end|>\n<|im_start|>assistant\n") if a.chat else None
    report = {"ckpt": a.ckpt, "time": time.ctime(), "decoding": {"temperature": 0, "max_new": a.max_new}, "suites": {}}
    for name, items in load_suite(sorted(glob.glob(a.suite))).items():
        results = []
        for it in items:
            pred = run_generation(model, tok, it["prompt"], a.max_new, dev, chat)
            results.append({"id": it["id"], "correct": check_answer(pred, it), "pred": pred[:300]})
        acc, ci = accuracy_ci([r["correct"] for r in results])
        report["suites"][name] = {"acc": acc, "ci": ci, "n": len(results), "results": results}
    if a.val_texts:
        texts = [json.loads(l)["text"] for l in open(a.val_texts, encoding="utf-8")][:200]
        report["bpb"] = bits_per_byte(model, tok, texts, model.cfg.block_size, dev)
    report["macro_acc"] = sum(s["acc"] for s in report["suites"].values()) / max(1, len(report["suites"]))
    json.dump(report, open(a.out, "w"), indent=1)
    print(json.dumps({k: (v["acc"], v["ci"]) for k, v in report["suites"].items()}, indent=1), "macro", report["macro_acc"])

if __name__ == "__main__": main()
```

```python
# scripts/compare_reports.py
import json, sys
from nanoforge.eval.stats import paired_bootstrap
A, B = json.load(open(sys.argv[1])), json.load(open(sys.argv[2]))
for s in A["suites"]:
    ca = {r["id"]: r["correct"] for r in A["suites"][s]["results"]}; cb = {r["id"]: r["correct"] for r in B["suites"][s]["results"]}
    ids = sorted(set(ca) & set(cb))
    d, ci = paired_bootstrap([ca[i] for i in ids], [cb[i] for i in ids])
    print(f"{s:25s} diff {d:+.3f}  95% CI [{ci[0]:+.3f}, {ci[1]:+.3f}]", "✓ significant" if ci[0] > 0 or ci[1] < 0 else "")
```

### 🔬 Experiment & Observe
Run the harness on two checkpoints of your base model (e.g. steps 3,000 and 6,000) and compare them. Even base models improve on knowledge items with more pretraining. Keep all the reports in `evals/reports/` as the history of your model.

### ⚠️ Failure Modes & Debugging
- Changing the decoding settings or prompts between checkpoints invalidates comparisons. Version the harness config.
- Greedy decoding can hide abilities that appear with sampling. Consider pass@k for generative items.

### 🧠 Expert Insight
Tools such as lm-evaluation-harness, OpenAI simple-evals, Inspect (UK AISI) and HELM formalize exactly this: versioned tasks, fixed prompts, logged samples and aggregated reports.

### ✅ Check Your Instinct

2. What must stay fixed across compared checkpoints?

<details><summary>Answers</summary>

1. So each behaviour counts equally regardless of how many items it has.
2. Prompts, decoding settings, item sets, tokenizer/chat formatting and judge configuration.

### 📌 Recap Card
- One command → a versioned JSON report with CIs and samples.
- Paired comparisons between reports.
- Fixed configs; keep the history.

> **Core intuition:** *Automate evaluation so every decision is backed by the same ruler.*
